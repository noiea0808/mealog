## 대전제

> **이 앱이 통제할 수 없는 모든 대기 — 직접 쓴 네트워크 호출이든, 서드파티 SDK가 내부적으로
> 하는 대기든 — 는 영원히 끝나지 않을 수 있다고 가정한다. 그 가정이 깨지는 자리를 증상이
> 나타난 뒤 패치하지 않고, 새 의존성을 들일 때 미리 봉쇄한다.**

## 왜 이 문장이 필요했는가

`docs/sync-outbox-design.md` §4.8은 관문(`withDeadline`)을 만들고 "관문 밖 직접 await는
ESLint로 금지한다"고 했습니다. 그런데 그 관문은 **앱이 직접 쓴 `await`만** 감쌌습니다.

2026-08 App Check 교착 사고의 실제 원인은 그 경계 밖에 있었습니다 — `auth._getAppCheckToken()`,
`db._appCheckCredentials.getToken()` 같은 **SDK 내부**의 대기입니다. 앱 코드 어디에도 그런
대기가 존재한다는 사실 자체가 적혀 있지 않았고, ESLint 셀렉터에도 `getToken`이 빠져 있었습니다
(문서에는 처음부터 있었는데도). "관문을 만들었다"와 "경계를 올바르게 그었다"는 다른 문제라는
것이 이 사고로 드러났습니다.

즉 관문의 경계는 **"내가 쓴 await"가 아니라 "내가 통제권을 넘긴 지점"**이어야 합니다.

## 파생 규칙

### 1. 새 의존성을 들일 때, 그게 내부적으로 뭘 기다리는지 먼저 묻는다

대기 지점이 내 코드 밖에 있으면(서드파티 SDK 내부), 넘기는 객체 자체를 상한으로 감싼다.

패턴: `js/firebase.js`의 `DeadlineBoundedAppCheckProvider` — App Check 제공자를 감싸
`getToken()`을 상한 안에 가둔다. 상한 초과 시 직접 더미 값을 만들지 않고 **거절**한다 —
SDK가 실패를 어떤 모양(문자열/객체/코드)으로 기대하는지는 SDK가 제일 잘 알기 때문이다.
`{ token: undefined }` 같은 직접 조작은 내부 assertion을 깨뜨릴 수 있다(실측:
`INTERNAL ASSERTION FAILED`).

### 2. 방어/보안 계층은 "동작할 때"가 아니라 "실패했을 때 뭐가 죽는가"로 설계한다

App Check가 이 실수의 표본이었다. 켜는 것 자체가 목표였고 실패 모드는 설계되지 않았다.
그리고 그 계층이 **실제로 뭘 지키고 있는지** 주기적으로 확인한다 — Firebase 콘솔 App Check
API 적용 상태가 전부 `모니터링`(강제 적용 0곳, 보호 효과 0%)이라는 것을 6개월 만에 처음
확인했다. 아무 이득 없이 전체 쓰기 경로를 얼릴 수 있는 부품이 그만큼 오래 방치됐다는 뜻이다.

### 3. 반복 실패하는 서브시스템은 계측을 기능보다 먼저 넣는다

"고쳤다"의 판정은 코드 리뷰가 아니라 필드 데이터(diag 이벤트)로 한다. 2026년 6~8월
동기화 서브시스템의 13차례 수정이 전부 증거 없이 추론만으로 이뤄진 이유가 계측 부재였다
(`docs/sync-outbox-design.md` §4.9).

### 4. 반복 실패하는 서브시스템은 불변식·폐기된 접근·그 이유를 문서로 남긴다

`docs/sync-outbox-design.md`가 이 형식의 선례다. "작은 패치가 그럴듯해 보이면 그건 이미
여러 번 그럴듯했던 것과 같은 종류일 가능성이 높다"는 경고를 문서 맨 위에 두는 것도 같은
이유 — 재발명·재시도를 막기 위함이다.
