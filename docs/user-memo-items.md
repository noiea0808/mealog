# 사용자 메모 항목 설계 — 기록 항목 목록에 '식사가 아닌 것'을 들인다

작성: 2026-08-30 · **설계 단계** (구현 전)
전제: [user-slot-plan.md](user-slot-plan.md) 0~4단계 완료 (사용자 슬롯·기록 항목 설정)
관련: [sync-outbox-design.md](sync-outbox-design.md), [admin-local-mirror.md](admin-local-mirror.md)

## 0. 문제

하루에 남기고 싶은 것이 밥만은 아니다. 체중·혈당·배변·운동·약·수면 —
사람마다 다르고, 우리가 목록을 정해 줄 수 없다.

지금 이 자리에 있는 것은 **하루 소감** 하나다. 거기에 체중·혈당이 하드코딩으로
박혀 있고(`js/modals/daily-journal.js` `METRIC_CONFIG`), 그 둘 말고는 어떤 것도
남길 자리가 없다. 셋째 항목을 원하는 사용자는 소감 본문에 "오늘 8천보"라고
적는 수밖에 없다.

게다가 하루 소감은 **하루의 끝**에 붙는다. 타임라인에서 늘 마지막이다. 아침
먹고 → 운동하고 → 점심 먹은 하루를 그 순서대로 남길 방법이 없다.

## 1. 대전제 — 층을 하나 더 얹지 않는다

user-slot-plan §1 이 층을 둘로 갈랐다: **집계축(base, 7개 고정)** 과
**표시축(사용자 슬롯)**. 메모는 셋째 층이 아니라 **표시축의 두 번째 종류**다.

| | 사용자 슬롯 | **메모 항목** |
|---|---|---|
| 무엇 | 끼니·간식 | 그 밖의 모든 것 |
| 이름 | 사용자 | 사용자 |
| 아이콘 | base 의 것(고정) | **사용자** |
| base(집계축) | 있다 — 정확히 하나 | **없다** |
| 늘리는 법 | 원본 복제 | 새로 만들기 |
| 기록 서식 | 음식·평점·포만감·함께·장소… | 텍스트·사진·시간 |

**같은 목록에 산다.** 순서도 하나다. 아침 · 운동 · 점심 · 체중 · 저녁 을
사용자가 끌어서 그대로 세울 수 있다 — "중간에 넣는다"가 이 설계의 출발점이고,
그 순서를 이미 소유한 자료구조가 `slotPlan` 의 `slots` 배열이다(§2.3).

### 불변식 갱신

user-slot-plan 의 불변식 2 를 고쳐 쓴다. 지금 문장은 이미 사실이 아니다 —
하루 소감 미러가 `slotId: 'daily_journal'` 로 `meals` 에 들어가 있다.

> **불변식 2′.** `meals.slotId` 는 `기준 슬롯 7개` ∪ `{'memo', 'daily_journal'}` 이다.
> 뒤의 둘은 **"이것은 식사가 아니다"** 라는 표식이며, 식사를 세는 모든 코드는
> 이 둘을 명시적으로 뺀다. 뺄 곳의 전수표는 §6 이다.

불변식 1(모든 사용자 슬롯은 정확히 하나의 base 에 속한다)은 **슬롯에만**
적용된다고 좁힌다. 메모에는 base 가 없다.

불변식 3(사용자 슬롯을 모르는 코드는 `slotId` 만 읽고도 정상 동작)과
불변식 4(어떤 설정으로도 기존 기록이 화면에서 사라지지 않는다)는 그대로다.

## 2. 데이터 모델

### 2.1 정의는 같은 목록에 산다 — `kind` 한 글자

```js
// userSettings.slotPlan.revisions['2026-09-01'].slots
[
  { key: '000000000morning', base: 'morning', label: '아침', enabled: true },
  { key: '0mtek3x9',  kind: 'memo', icon: 'dumbbell', label: '운동',  enabled: true },
  { key: '000000000lunch',   base: 'lunch',   label: '점심', enabled: true },
  { key: '0mtek4a1',  kind: 'memo', icon: 'scale',    label: '몸무게', enabled: true }
]
```

- `kind` 가 없으면 `'slot'` 이다 — 기존 데이터를 한 건도 안 고친다.
- 메모에는 `base` 가 없고, 슬롯에는 `icon`·`kind` 가 없다.
- `key` 는 슬롯과 **같은 생성기**(`generateSlotKey`)를 쓰고 같은 이름공간을
  공유한다. 사용자 문서 안에서 영구 유일.
- 개정판(날짜 키 맵)·적용 시작일·뒤 개정판 통일·`retired` — user-slot-plan §2.1,
  §4.2.3~5 가 그대로 메모에도 적용된다. **새 기계장치가 하나도 없다.**

`memoPlan` 을 따로 두는 안을 버린 이유는 셋이다.

1. **순서.** 목록이 둘이면 타임라인에서 둘을 섞는 규칙이 필요하다. 시간순은
   답이 아니다 — 지금 타임라인의 식사 그룹은 시간이 아니라 **목록 순서**로
   늘어선다(user-slot-plan §2.3). 정직한 병합 규칙이 없다.
2. **이름 보존.** 메모 이름은 100% 사용자가 지은 것이라 슬롯보다 더 잃으면 안
   된다. 그 장치(전 개정판 key 탐색 → `retired` → 폴백)는 §3 에 이미 있고,
   같은 목록에 살면 **한 줄도 안 짜고** 얻는다.
3. **동기화.** 날짜 키 맵이라는 구조 하나로 다기기 병합이 성립한다
   (user-slot-plan §5.2). 두 번째 맵을 만들면 같은 함정을 두 번 밟는다.

버린 대가는 §9-1 에 적는다 — 구버전 클라이언트가 메모 정의를 지운다.

### 2.2 기록은 `meals` 문서다 — `userSettings` 가 아니다 ★

하루 소감은 `userSettings.dailyComments[date]` 에 산다. 메모를 같은 자리에 두는
것이 언뜻 자연스러워 보이지만, **이 선택은 되돌릴 수 없고 한도가 있다.**

`userSettings` 는 **문서 하나**이고 Firestore 문서 한도는 1MB 다. 하루 소감
본문·사진 URL 이 이미 거기 있다(user-slot-plan §5.6 이 개정판 크기를 걱정한
바로 그 문서다). 메모를 넣으면:

| | 하루치 | 1년치 |
|---|---|---|
| 메모 4종 × 본문 40자 + 사진 URL 1개 | ~600B | **~220KB** |
| 여기에 하루 소감·개정판·프로필… | | 1MB 까지 3~4년 |

3년 뒤에 터지는 한도는 "나중에 고치면 된다"가 안 되는 종류다. 그때는 이미
사용자 데이터가 그 안에 있다.

`meals` 서브컬렉션은 반대다. 문서가 늘어날 뿐이고, 사진 업로드·아웃박스·
낙관적 UI·삭제 툼스톤·관리자 미러가 **전부 이미 거기에** 있다.

> **결정.** 메모 기록은 `artifacts/{appId}/users/{uid}/meals/{id}` 문서다.
> 대가는 "식사를 세는 코드가 메모를 빼야 한다" 하나이고, 그 목록은 유한하고
> 열거 가능하다(§6).

```js
// 메모 기록 = meals 문서
{
  id, date: '2026-09-01',
  slotId: 'memo',            // 불변식 2′ — "식사가 아니다"
  slotKey: '0mtek3x9',       // 어느 메모 항목인지 (§2.3)
  comment: '30분 뛰었다',      // 본문 — 식사의 comment 를 그대로 쓴다
  photos: [...], photoAspectRatio: '1:1', photoMeta: [...],
  mealClock: '오전 7:20',      // 표시용 (기존 시계 휠 그대로)
  time: '07:20:00',           // 정렬용
  recordedAt, updatedAt
}
```

식사 고유 필드(`mealType`·`rating`·`satiety`·`category`·`withWhom`·`place`…)는
**넣지 않는다.** 없는 필드는 없는 채로 둔다.

### 2.3 `memoKey` 를 새로 만들지 않는다 — `slotKey` 그대로

메모 기록이 어느 항목인지 가리키는 필드는 `slotKey` 다. 새 이름을 붙이고 싶은
충동이 있지만, 그러면 §3 의 해석기를 두 벌 만들어야 한다.

같은 필드를 쓰면 `resolveSlotView(record)` 가 **손대지 않고** 동작한다:
전 개정판에서 `slotKey` 를 찾고(1), 없으면 `retired`(2.5), 그래도 없으면
폴백(3). 메모는 base 가 없으니 2번(같은 base 의 원본 슬롯) 단계만 건너뛴다.

바뀌는 것은 폴백 한 줄이다. 어디서도 못 찾은 `slotId: 'memo'` 기록은
`{ label: '메모', icon: 'sticky-note' }` 로 떨어진다 — **폴백은 반드시
성공한다**는 §3 의 성질을 유지한다.

### 2.4 아이콘은 화이트리스트다

`icon` 은 Lucide 이름 문자열이고, **우리가 고른 30개 안**에서만 유효하다.
모르는 값은 `sticky-note` 로 떨어진다.

- 자유 문자열을 그대로 `<i data-lucide="...">` 에 꽂지 않는다. 화면에 나가는
  값은 화이트리스트를 통과한 것뿐이다.
- 이모지를 쓰지 않는 이유: 기기마다 그림이 다르고, 앱의 나머지가 전부 Lucide
  단색 선화다. 목록에 이모지 하나가 끼면 그것만 튄다.

후보 30개(초안): `scale` `droplet` `activity` `heart-pulse` `pill` `syringe`
`dumbbell` `footprints` `bike` `waves` `moon` `bed` `alarm-clock` `smile`
`frown` `brain` `thermometer` `stethoscope` `toilet` `glass-water` `coffee`
`cigarette` `wine` `sun` `cloud-rain` `book-open` `pen-line` `camera`
`map-pin` `sticky-note`

### 2.5 상한

| 상한 | 지금 | 메모 도입 후 |
|---|---|---|
| 사용 중 항목 (피커에 뜨는 수) | 12 | **16** (슬롯+메모 합산) |
| 개정판 배열 총 길이 | 24 | **32** |
| 항목 이름 | 12자 | 그대로 (슬롯·메모 공통) |

합산으로 세는 이유: 피커는 한 목록이고, 사용자에게 "슬롯 12개, 메모 4개"라는
두 개의 예산은 설명할 수 없다. 피커는 이미 스크롤되므로(`max-h-[min(80vh,36rem)]`)
16개가 한 화면을 넘어도 깨지지 않는다.

## 3. 읽기 경로

바뀌는 함수는 둘뿐이다.

**`resolveSlotView`** — §2.3. base 폴백을 건너뛰고 메모 기본값으로 떨어지는
가지 하나.

**`groupMealsByUserSlotForDate`** — 지금은 `BASE_IDS.has(m.slotId)` 가 아닌
기록을 **버린다**(그래서 하루 소감 미러가 타임라인에 두 번 안 나온다).
여기에 가지를 하나 연다:

```
slotId === 'memo' → 그룹 키 = `k:${slotKey}`
                    순서    = 유효 개정판에서 그 key 의 인덱스
                    (개정판에 없으면 = 지금 지워진 메모) 목록 끝
```

그룹의 `slot` 은 `{ id:'memo', type:'memo', label, key, icon }` 이다.
타임라인·사진 뷰어·일간 공유 캡처가 **같은 순회 함수 하나**를 쓰고 있으므로
(user-slot-plan §3), 이 한 곳을 고치면 세 화면이 함께 따라온다.

`type: 'memo'` 라는 세 번째 값이 생긴다. `slot.type === 'main' ? A : B` 로
갈라지는 호출부를 전수 확인해 3분기로 바꾼다 — 놓치면 메모가 간식 카드로
그려진다(깨지진 않지만 틀린 그림이다).

## 4. 화면

### 4.1 피커 — 같은 격자, 다른 낯

```
┌──────────────┐ ┌──────────────┐
│      아침     │ │     운동      │
│  ☁            │ │  🏋  (점선)   │
│      1건      │ │    아직 없음  │
└──────────────┘ └──────────────┘
┌──────────────┐ ┌──────────────┐
│      점심     │ │    몸무게     │
│  🍲           │ │  ⚖  (점선)    │
└──────────────┘ └──────────────┘
        ── 하루 소감 (전체 폭) ──
```

- 메모도 **같은 2열 격자에, 목록 순서 그대로** 놓는다. 순서가 곧 설계의 핵심
  기능이므로 종류별로 구역을 나누지 않는다.
- 메모 카드는 **중성 색(slate) + 점선 테두리**로 슬롯과 구분한다. 색을 쓰지
  않는 이유: 아이콘이 이미 각자 다르다. 거기에 색까지 다르면 격자가 시끄럽다.
- 건수 배지는 같은 규칙(`n건` / `아직 없음`).

### 4.2 기록 항목 설정 — 한 시트, 두 종류

```
기록 항목 설정   사용 중 9 / 16          (?)
⠿  ☁  아침 ✎              사용 중   ⧉
⠿  🏋  운동 ✎              사용 중   🗑     ← 메모 (복제 없음, 삭제만)
⠿  🍲  점심 ✎              사용 중   ⧉
⠿  ⚖   몸무게 ✎            사용 중   🗑

              [ + 메모 항목 만들기 ]

적용 시작일  [ 2026-09-01 ▾ ]
9월 1일 기록부터 적용됩니다. …
                        [ 취소 ]  [ 저장 ]
```

시트를 따로 만들지 않는다. "메모 설정"이 별도 메뉴가 되면 **순서를 편집할 수
있는 화면이 두 개**가 되고, 둘 사이의 순서는 어느 화면에서도 못 정한다.
한 목록에서 끌어야 아침과 점심 **사이**에 운동을 넣을 수 있다.

행의 차이는 이미 있는 규칙을 따른다(user-slot-plan §4.2.1 — 한 자리에 하나만):

| 종류 | 아이콘 | 오른쪽 끝 | 이름 |
|---|---|---|---|
| 원본 슬롯 | base 고정 | 사용 중 / 사용 안 함 | 편집 |
| 복제 슬롯 | base 고정 | 삭제 | 편집 |
| **메모** | **눌러서 고름** | **삭제** | 편집 |

메모에 사용 토글을 두지 않는다. 메모는 전부 사용자가 만든 것이라 되돌리는
수단이 삭제 하나면 충분하고 — 원본 슬롯이 삭제 대신 토글을 갖는 이유(복제할
씨앗·폴백 귀속처)가 메모에는 없다.

> 다만 **삭제해도 기록과 이름은 남는다**(§3 · `retired`). 이 점이 사용자에게
> 안 보이면 삭제를 무서워한다 — 도움말 팝업(user-slot-plan §4.2.6)에 한 줄
> 넣는다.

### 4.3 메모 항목 만들기 — 프리셋 먼저, 이름은 사용자

'+ 메모 항목 만들기' → 설정 시트 **위에 겹치는 팝업**(도움말과 같은 층,
`--z-slot-picker-help`).

```
새 메모 항목
[체중] [혈당] [운동] [배변] [수면] [약] [물] [기분]   ← 프리셋 칩
이름  [ 운동          ]  (12자)
아이콘 ⚖ 💧 🏃 🚽 🌙 💊 🥤 🙂 …                     ← 30개 격자
                          [ 취소 ]  [ 만들기 ]
```

프리셋 칩은 **이름과 아이콘을 한 번에 채우는 지름길**일 뿐이다. 채운 뒤에도
이름은 그대로 편집 가능하다 — "타이틀은 사용자가 직접"이라는 요구를 지키면서,
가장 흔한 여덟 가지에서 타이핑을 없앤다.

### 4.4 메모 기록 시트 — 세 칸

```
운동                                    ✕
시간   [ 오전 7:20 ]      ← 기존 시계 휠 그대로
내용   [                     ]
사진   [＋카메라] [＋앨범]   0/5
                     [ 삭제 ]  [ 저장 ]
```

식사 시트(2단계·9축)를 재사용하지 않는다. 메모는 축이 셋뿐이라 그 시트에
태우면 빈 칸이 대부분이다. 새 모달 하나(`memoRecordModal`)를 만들되 **부품은
전부 기존 것**을 쓴다 — 시계 휠(`meal-clock-wheel-picker`), 사진 고르기
(`image-source-picker`), 사진 업로드(`entry-save-photos` 경로), 저장
(`dbOps.save`).

**저장 경로를 새로 파지 않는다.** `dbOps.save` 안에 아웃박스 내구화·사진
업로드·낙관적 반영이 다 있다(sync-outbox-design §1). 메모용 두 번째 저장기를
만드는 순간 그 불변식이 두 벌이 된다. 다른 것은 토스트 문구와
`bumpUserMealCount` 뿐이고, 둘 다 `opts` 로 가른다.

### 4.5 타임라인 카드

간식 카드보다 한 단 낮은 밀도로 한 줄:

```
│ 🏋  운동            오전 7:20
│    30분 뛰었다                     [사진]
```

같은 항목을 하루에 여러 번 남길 수 있다(혈당 3회). 그룹 안 정렬은 식사와 같은
규칙(시간순)이고, 같은 그룹 다건에 붙는 서수도 같은 규칙을 따른다.

### 4.6 빈 메모는 '있었다'는 기록이다

배변·복약처럼 **유/무만** 남기고 싶은 항목이 있다. 여기에 체크박스를 새로
만들지 않는다.

> 본문도 사진도 없이 저장한 메모는 **유효한 기록**이다. 항목을 눌러 시간만
> 찍고 저장하면 그 자체가 "있었다"가 된다.

카드에는 아이콘·이름·시간만 남는다. 새 필드 없이 새 쓰임이 열리는 자리라,
이것을 규칙으로 못 박아 둔다. (식사 기록은 반대로 빈 저장을 막는다 — 그쪽은
"뭘 먹었는지"가 본체이기 때문이다.)

## 5. 저장·동기화

기존 경로를 그대로 탄다. 새로 정할 것이 사실상 없다는 것이 §2.2 결정의 값이다.

| 무엇 | 어디로 | 아웃박스 |
|---|---|---|
| 메모 **정의**(이름·아이콘·순서·삭제) | `userSettings.slotPlan` | `settings` · `mergePayload` |
| 메모 **기록**(본문·사진·시간) | `meals/{id}` | `meal` · content 등급 |

- 충돌 규칙은 하나 그대로: **같은 날짜 개정판은 마지막 편집이 이긴다**(§5.3).
- 정의와 기록의 도착 순서를 강제하지 않는다(§5.4). 기록이 먼저 오면 폴백
  이름('메모')이 잠깐 뜨고, 정의가 도착하면 교정된다.
- `slotPlan` 부분 손상 보호(§5.1)가 메모 이름까지 함께 지킨다.

## 6. 서버·집계에 미치는 영향 — 전수표 ★

이 표가 §2.2 결정의 **전체 비용**이다. 메모 도입 전에 이 표의 '조치'를 먼저
넣는다 — 기능이 먼저 들어가면 통계가 조용히 틀어진다.

| 위치 | 지금 | 메모가 오면 | 조치 |
|---|---|---|---|
| `functions/mealStats.js` `getMealDelta` | 슬롯 무관 `count += 1` | **총 기록 수 부풀림** | `slotId: 'memo'` 는 `null` 반환 |
| `functions/index.js` `isDietAnalyzableMeal` | `daily_journal` 제외 | 메모 본문이 식단분석 입력에 섞임 | `'memo'` 제외 추가 |
| `js/db/ops.js` `bumpUserMealCount` | 저장마다 +1 | `mealCount` 부풀림 | `opts.skipCount` |
| `js/analytics/dashboard.js` `mealFiltered` | 범위 내 **전** 기록 | 차트 분모 오염 | `'memo'`·`daily_journal` 제외 |
| `js/utils/slot-plan.js` 그룹 순회 | `BASE_IDS` 아니면 버림 | 메모가 안 그려짐 | 메모 가지 추가 (§3, 의도된 변경) |
| `js/admin/feed-moderation.js` | `daily_journal` 특례 | 메모 사진·본문이 모니터링 목록에 | 같은 특례 추가 |
| `js/admin/moment-analytics.js:815` | `daily_journal` 제외 | 분석 오염 | `'memo'` 제외 추가 |
| `js/analytics/charts.js` 웰컴 슬라이드 | `MEAL/SNACK_SLOTS` 필터 | 영향 없음 | — |
| `js/analytics/best-share.js` | `rating` 필터 | 영향 없음 | — |
| `js/utils/diet-record-score.js` | `MAIN_SLOT_IDS` | 영향 없음 | — |
| 관리자 로컬 미러 `meals` 스토어 | 전부 담음 | 그대로 담김 | 조치 없음 — **소비 지점**에서 거른다 |
| `onMealWritten` 툼스톤 | 전부 | 그대로 | 조치 없음 |
| `firestore.rules` `meals` | 필드 제한 없음 | 그대로 저장됨 | 조치 없음 |
| 모먼트 공유(`sharePhotos`) | 식사 전제 | — | v1 **공유 버튼 없음** |

**한 가지 미해결이 표에 딸려 나온다.** `getMealDelta` 는 지금도 하루 소감
미러를 `count` 에 세고 있다 — 메모와 무관한 기존 과다계수다. 여기서 함께
고치되, **과거 집계는 소급하지 않는다**(재집계는 별건이다). 고치는 순간
사용자의 '총 기록 수'가 하루 소감 수만큼 줄어 보이므로, 고칠지 말지는 실제
분포를 보고 정한다 — 이 문서는 "여기 있다"까지만 정한다.

## 7. 하루 소감을 이 목록에 넣을 것인가

**결론: 자리는 v1 에 넣고, 저장소는 넣지 않는다.**

넣고 싶은 이유는 분명하다 — 하루 소감은 이미 "텍스트 + 사진"이고, 메모가
정확히 그 모양이다. 순서를 사용자가 정할 수 있게 되면 "하루의 끝"이라는
고정도 풀린다.

넣지 못하는 이유는 저장소가 다른 데서 온다:

| 얽힌 것 | 지금 | 흡수하려면 |
|---|---|---|
| 본문 | `userSettings.dailyComments[date]` | `meals` 로 이전 + 마이그레이션 |
| 미러 | `meals/dailyJournal_{date}` (파생) | 파생이 본체가 된다 |
| 체중·혈당 | **숫자 + 시각 + 최대 3건 + 추이 표기** | 메모에는 없는 기능 (§10) |
| 모먼트 공유 | `dailyJournal_{date}` entryId 규약 | 규약 유지 필요 |
| 관리자 | 모니터링 특례 · 백필 Callable | 재작성 |

그래서 v1 은 **목록에 자리만** 준다. 하루 소감을 `kind: 'journal'` 항목으로
개정판에 넣어 **순서만** 사용자가 정하게 하고(삭제 불가·이름 편집 가능),
데이터는 `dailyComments` 에 그대로 둔다. 피커·타임라인은 그 항목의 자리에
지금의 하루 소감 카드를 그린다.

이러면 사용자가 보기엔 "하루 소감도 항목 중 하나"가 되고, 우리는 저장소를
안 건드린다. 완전 흡수는 체중·혈당 숫자 필드가 생긴 뒤에 다시 꺼낸다.

  정적 빌드에 없는 클래스는 조용히 죽는다(2026-08-30 실측: z-index 가 `auto` 로).

## 9. 남은 위험

1. **구버전 클라이언트가 메모 정의를 지운다.** ★
   `sanitizeSlots` 는 모르는 `base` 를 버린다 — 구버전은 메모 항목을 통째로
   버린다. 구버전에서 **기록 항목 설정을 저장하면** 그날 개정판에 메모가 빠진
   채 쓰여, 그날부터 메모가 사라진다(기록과 이름은 §3 이 지킨다).
   웹은 main, APK 는 staging 을 받으므로 이 창은 실재한다.
   → **3단계 이후는 웹·APK 를 묶어서 내보낸다.** user-slot-plan §8-4 와 같은
   제약이고, 같은 이유다.
2. **`type` 3분기 누락.** `main ? A : B` 이분기가 남아 있으면 메모가 간식으로
   그려진다. 2단계에서 전수로 훑고, 새 값에 `default` 분기를 두지 않는다
   (조용히 통과하는 대신 눈에 띄게).
3. **아이콘 화이트리스트 우회.** 다른 기기·구버전이 임의 문자열을 쓸 수 있다.
   `sanitizeSlots` 가 화이트리스트 밖을 `sticky-note` 로 바꾼다 — 렌더 시점이
   아니라 **읽기 시점**에 정화한다.
4. **피커가 붐빈다.** 16개면 2열 8줄이라 스크롤이 생긴다. 실사용에서 메모를
   몇 개나 만드는지 보고 상한을 조정한다 — 지금 정하는 것은 16 까지다.
5. **`meals` 문서 수 증가.** 하루 4개 메모면 기록 수가 2배 가까이 된다.
   읽기 비용은 날짜 범위 로딩이라 그대로지만, 관리자 미러 부트스트랩
   (~1.2만 읽기)이 커진다. 미러는 증분이라 정기 비용은 안 오른다.

## 10. 안 하기로 한 것

- **숫자 필드·단위·추이 그래프.** 체중이 가장 원할 기능이지만, 넣는 순간
  "단위 정의 → 입력기 → 유효 범위 → 그래프 → 분석 반영"이 딸려 온다.
  v1 은 텍스트다. 하루 소감의 체중·혈당은 **그대로 둔다**(§7) — 그쪽을 먼저
  치우면 기능이 후퇴한다.
- **메모 사진의 모먼트 공유.** 공유는 식사 전제의 규약(entryId·슬롯 라벨·
  신고 경로)이 있다. 메모를 얹기 전에 그 규약을 다시 봐야 한다.
- **알림·반복.** "매일 아침 체중 남기기" 같은 것. 푸시 파이프라인이 따로 있고
  (push-notifications.md), 기록 항목과 엮으면 둘 다 복잡해진다.
- **메모 항목 복제.** 슬롯의 복제는 base 를 물려받기 위한 장치였다. 메모는
  base 가 없어 '새로 만들기'와 다를 게 없다.
