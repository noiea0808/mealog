# 사용자 메모 항목 설계 — 자리는 사용자가 아니라 **시간**이 정한다

작성: 2026-08-30 · **0~10단계 구현 완료** (staging, 같은 날)
구현: `js/utils/slot-plan.js`(순수) · `js/modals/memo-record.js`(기록 시트) ·
`js/modals/memo-settings.js`(메모 설정 팝업) · 테스트 `test/memo-items.test.mjs`
전제: [user-slot-plan.md](user-slot-plan.md) 0~4단계 완료 (사용자 슬롯·기록 항목 설정)
관련: [sync-outbox-design.md](sync-outbox-design.md), [admin-local-mirror.md](admin-local-mirror.md)

## 0. 문제

하루에 남기고 싶은 것이 밥만은 아니다. 체중·혈당·배변·운동·약·수면 —
사람마다 다르고, 우리가 목록을 정해 줄 수 없다.

지금 이 자리에 있는 것은 **하루 소감** 하나다. 거기에 체중·혈당이 하드코딩으로
박혀 있고(`js/modals/daily-journal.js` `METRIC_CONFIG`), 그 둘 말고는 어떤 것도
남길 자리가 없다. 셋째 항목을 원하는 사용자는 소감 본문에 "오늘 8천보"라고
적는 수밖에 없다.

게다가 하루 소감은 **하루의 끝**에 붙는다. 타임라인에서 늘 마지막이다. 아침
먹고 → 운동하고 → 점심 먹은 하루를 그 순서대로 남길 방법이 없다.

## 1. 대전제 — 메모에는 **자리를 묻지 않는다** ★

처음 초안은 메모를 기록 항목 목록에 끼워 **사용자가 끌어서** 위치를 정하게
했다. 이 안은 버린다. 사용자에게 답할 수 없는 질문을 하기 때문이다.

> 체중을 아침과 점심 사이에 둘까, 점심과 저녁 사이에 둘까?

체중은 아침에도 재고 자기 전에도 잰다. 위치를 하나 고르라고 하면 답이 없고,
피하려면 **아침체중 · 점심체중** 을 따로 만들게 된다 — 개념 하나가 시간대
수만큼 불어나고, 그 순서를 또 정해야 한다. 목록이 금세 못 읽을 만큼 길어진다.

시간은 이미 그 답을 안다. 메모를 남길 때 시각을 찍으므로(§4.4), **그 날 이미
적힌 기록들 사이 어디에 끼어야 하는지 계산할 수 있다.**

> **대전제.** 메모 **항목**은 개념 하나당 하나다(체중 하나, 혈당 하나).
> 메모 **기록**은 하루에 몇 건이든 남길 수 있고, 각 건의 자리는 그 건의
> **시각**이 정한다. 사용자는 자리를 고르지 않는다.

항목이 하나뿐이어도 손해가 없는 것은 기록이 여럿이기 때문이다. 아침 체중과
저녁 체중은 **같은 항목의 두 기록**이고, 타임라인에서는 각자 다른 자리에
놓인다(§3.2). '아침체중' 항목을 따로 만들 이유가 사라진다.

나중에 메모 설정에 **순서 끌기**를 넣었지만 이 대전제와 부딪히지 않는다 —
그건 **피커 격자에 보이는 순서**일 뿐이고, 타임라인의 자리는 여전히 시각이
정한다. 둘을 혼동하면 "체중을 아침과 점심 사이에 둘까"가 다시 생긴다.

이 한 줄이 아래 설계 전체를 끌고 간다.

| | 사용자 슬롯 | **메모 항목** |
|---|---|---|
| 무엇 | 끼니·간식 | 그 밖의 모든 것 |
| 이름 | 사용자 | 사용자 |
| 아이콘 | base 의 것(고정) | **사용자** |
| base(집계축) | 있다 — 정확히 하나 | **없다** |
| 늘리는 법 | 원본 복제 | 새로 만들기 |
| **목록에서의 순서** | 사용자가 끈다 | 사용자가 끈다 (**피커 격자 순서만**) |
| **타임라인에서의 자리** | 목록 순서 | **기록의 시각** |
| 하루 다건 | 한 그룹으로 **묶인다** | **낱건**으로 흩어진다 (§3.2) |
| 기록 서식 | 음식·평점·포만감·함께·장소… | 텍스트·사진·시간 |

### 불변식 갱신

user-slot-plan 의 불변식 2 를 고쳐 쓴다. 지금 문장은 이미 사실이 아니다 —
하루 소감 미러가 `slotId: 'daily_journal'` 로 `meals` 에 들어가 있다.

> **불변식 2′.** `meals.slotId` 는 `기준 슬롯 7개` ∪ `{'memo', 'daily_journal'}` 이다.
> 뒤의 둘은 **"이것은 식사가 아니다"** 라는 표식이며, 식사를 세는 모든 코드는
> 이 둘을 명시적으로 뺀다. 뺄 곳의 전수표는 §6 이다.

불변식 1(모든 사용자 슬롯은 정확히 하나의 base 에 속한다)은 **슬롯에만**
적용된다고 좁힌다. 메모에는 base 가 없다.

불변식 3(사용자 슬롯을 모르는 코드는 `slotId` 만 읽고도 정상 동작)과
불변식 4(어떤 설정으로도 기존 기록이 화면에서 사라지지 않는다)는 그대로다.

## 2. 데이터 모델

### 2.1 정의는 같은 배열에 살되, **항상 뒤쪽**에 모인다

```js
// userSettings.slotPlan.revisions['2026-09-01'].slots
[
  { key: '000000000morning', base: 'morning', label: '아침', enabled: true },
  { key: '000000000lunch',   base: 'lunch',   label: '점심', enabled: true },
  { key: '000000000dinner',  base: 'dinner',  label: '저녁', enabled: true },
  // ── 여기부터 메모 (sanitizeSlots 가 보장하는 경계) ──
  { key: '0mtek3x9', kind: 'memo', icon: 'scale',   label: '체중', enabled: true },
  { key: '0mtek4a1', kind: 'memo', icon: 'droplet', label: '혈당', enabled: true }
]
```

- `kind` 가 없으면 `'slot'` 이다 — 기존 데이터를 한 건도 안 고친다.
- 메모에는 `base` 가 없고, 슬롯에는 `icon`·`kind` 가 없다.
- **`sanitizeSlots` 가 슬롯을 앞, 메모를 뒤로 안정 정렬한다.** 이 한 줄이
  "배열 순서 = 표시 순서"(user-slot-plan §2.3)를 슬롯 구간에서 그대로
  지켜 주면서, "메모는 피커 아래쪽"(§4.1)을 **자료구조로** 보장한다.
  메모끼리의 순서는 만든 순이고, 사용자에게 노출되는 편집 수단이 없다.
- `key` 는 슬롯과 **같은 생성기**(`generateSlotKey`)를 쓰고 같은 이름공간을
  공유한다. 사용자 문서 안에서 영구 유일.
- 개정판(날짜 키 맵)·적용 시작일·뒤 개정판 통일·`retired` — user-slot-plan §2.1,
  §4.2.3~5 가 그대로 메모에도 적용된다. **새 기계장치가 하나도 없다.**

`memoPlan` 을 따로 두는 안은 버렸다. 결정적인 이유는 UI 가 아니라 **저장**이다.
두 목록이 같은 `revisions[날짜]` 를 각자 쓰면, 각 시트가 자기 몫만 담은 개정판을
써서 상대를 지운다 — 충돌 규칙이 "같은 날짜는 마지막 편집이 이긴다"
(user-slot-plan §5.3)이기 때문이다. 상대 것을 읽어 그대로 실어 주는 코드로
막을 수는 있지만, 그건 규칙이 하나라는 성질을 깨는 방향이다.
덤으로 이름 보존 장치(§2.3)와 다기기 병합(§5)을 두 벌 만들 필요가 없다.

### 2.2 기록은 `meals` 문서다 — `userSettings` 가 아니다 ★

하루 소감은 `userSettings.dailyComments[date]` 에 산다. 메모를 같은 자리에 두는
것이 언뜻 자연스러워 보이지만, **이 선택은 되돌릴 수 없고 한도가 있다.**

`userSettings` 는 **문서 하나**이고 Firestore 문서 한도는 1MB 다. 하루 소감
본문·사진 URL 이 이미 거기 있다(user-slot-plan §5.6 이 개정판 크기를 걱정한
바로 그 문서다). 메모를 넣으면:

| | 하루치 | 1년치 |
|---|---|---|
| 메모 4종 × 본문 40자 + 사진 URL 1개 | ~600B | **~220KB** |
| 여기에 하루 소감·개정판·프로필… | | 1MB 까지 3~4년 |

3년 뒤에 터지는 한도는 "나중에 고치면 된다"가 안 되는 종류다. 그때는 이미
사용자 데이터가 그 안에 있다.

`meals` 서브컬렉션은 반대다. 문서가 늘어날 뿐이고, 사진 업로드·아웃박스·
낙관적 UI·삭제 툼스톤·관리자 미러가 **전부 이미 거기에** 있다.

> **결정.** 메모 기록은 `artifacts/{appId}/users/{uid}/meals/{id}` 문서다.
> 대가는 "식사를 세는 코드가 메모를 빼야 한다" 하나이고, 그 목록은 유한하고
> 열거 가능하다(§6).

```js
// 메모 기록 = meals 문서
{
  id, date: '2026-09-01',
  slotId: 'memo',            // 불변식 2′ — "식사가 아니다"
  slotKey: '0mtek3x9',       // 어느 메모 항목인지 (§2.3)
  comment: '68.4kg',          // 본문 — 식사의 comment 를 그대로 쓴다
  photos: [...], photoAspectRatio: '1:1', photoMeta: [...],
  mealClock: '오전 7:20',      // 표시용 (기존 시계 휠 그대로)
  time: '07:20:00',           // 정렬용 — **자리를 정하는 값** (§3.3)
  recordedAt, updatedAt
}
```

식사 고유 필드(`mealType`·`rating`·`satiety`·`category`·`withWhom`·`place`…)는
**넣지 않는다.** 없는 필드는 없는 채로 둔다.

### 2.3 `memoKey` 를 새로 만들지 않는다 — `slotKey` 그대로

메모 기록이 어느 항목인지 가리키는 필드는 `slotKey` 다. 새 이름을 붙이고 싶은
충동이 있지만, 그러면 §3 의 해석기를 두 벌 만들어야 한다.

같은 필드를 쓰면 `resolveSlotView(record)` 가 **손대지 않고** 동작한다:
전 개정판에서 `slotKey` 를 찾고(1), 없으면 `retired`(2.5), 그래도 없으면
폴백(3). 메모는 base 가 없으니 2번(같은 base 의 원본 슬롯) 단계만 건너뛴다.

바뀌는 것은 폴백 한 줄이다. 어디서도 못 찾은 `slotId: 'memo'` 기록은
`{ label: '메모', icon: 'sticky-note' }` 로 떨어진다 — **폴백은 반드시
성공한다**는 §3 의 성질을 유지한다.

이름을 고치면 과거 기록에도 소급되고(§3.1), 항목을 지워도 그 기록의 이름은
`retired` 가 지킨다(§3.2). 메모 이름은 100% 사용자가 지은 것이라 이 보장이
슬롯보다 더 중요하고, 같은 배열에 살기 때문에 **한 줄도 안 짜고** 얻는다.

### 2.4 아이콘은 화이트리스트다

`icon` 은 Lucide 이름 문자열이고, **우리가 고른 30개 안**에서만 유효하다.
모르는 값은 읽는 시점에 `sticky-note` 로 정화된다(렌더 시점이 아니다).

- 자유 문자열을 그대로 `<i data-lucide="...">` 에 꽂지 않는다.
- 이모지를 쓰지 않는 이유: 기기마다 그림이 다르고, 앱의 나머지가 전부 Lucide
  단색 선화다. 목록에 이모지 하나가 끼면 그것만 튄다.

후보 30개(초안): `scale` `droplet` `activity` `heart-pulse` `pill` `syringe`
`dumbbell` `footprints` `bike` `waves` `moon` `bed` `alarm-clock` `smile`
`frown` `brain` `thermometer` `stethoscope` `toilet` `glass-water` `coffee`
`cigarette` `wine` `sun` `cloud-rain` `book-open` `pen-line` `camera`
`map-pin` `sticky-note`

### 2.5 상한과 이름 길이

| | 슬롯 | 메모 |
|---|---|---|
| 사용 중 개수 | 12 (그대로) | **+8** |
| 이름 | 12자 | **8자** |

메모 개수를 슬롯과 합산하지 않고 **따로 센다.** §1 대전제 덕분에 메모는 개념
하나당 하나뿐이라 8개면 넉넉하고, 무엇보다 피커에서 두 구역이 시각적으로
갈라져 있으므로(§4.1) 예산도 갈라져 있는 편이 설명하기 쉽다.

이름 8자는 3열 카드에서 온 제약이다. 375px 기기에서 열당 약 125px 이고,
8자 한글이 한 줄에 들어가는 한계다. (넘치면 2줄 클램프로 접힌다 — 깨지지는
않지만 격자가 들쭉날쭉해진다.)

기본 항목 둘(§2.6)도 이 8개 안에 든다 — 사용자가 만드는 것은 6개까지다.
따로 세지 않는 이유는 피커가 둘을 구분 없이 한 격자에 그리기 때문이다.
**화면에 안 드러나는 예산을 만들지 않는다.** 다 차면 안 쓰는 것을 지우거나
기본 항목을 해제하면 된다.

개정판 배열 총 길이는 24 → **32**.

### 2.6 기본 메모 항목 — 체중·혈당은 처음부터 있다 ★

빈 목록은 아무것도 가르쳐 주지 않는다. "메모를 만들 수 있다"는 사실보다
"체중을 여기 남기면 된다"가 훨씬 잘 전달된다. 그래서 **체중·혈당 두 개는
기본으로 깔려 있다.**

```js
defaultMemoItems() → [
  { key: '000000000memo-weight',     kind: 'memo', icon: 'scale',   label: '체중', unit: 'kg',    decimals: 1, enabled: true },
  { key: '000000000memo-bloodSugar', kind: 'memo', icon: 'droplet', label: '혈당', unit: 'mg/dL', decimals: 0, enabled: true }
]
```

- **key 는 결정적이다** — 기본 슬롯과 같은 수(§2.4, user-slot-plan). 이름을
  '몸무게'로 바꿔도 key 가 그대로라 §6.2 의 차트가 안 끊긴다. 이 성질이
  분석 연결의 토대다.
- **개정판에 그 key 가 하나도 없으면 `effectiveSlots` 가 덧붙인다.** 그래서
  기존 사용자(이미 개정판이 있는)도 마이그레이션 없이 얻는다.
- 덧붙임이 조용하려면 `withRevisionOn` 의 비교 기준(`current`)도 **같은
  보강을 타야 한다.** 안 그러면 설정을 열었다 저장만 해도 "기본 메모가
  늘었다"로 잡혀 개정판이 하나 생긴다(§5.6 성장 억제와 충돌).

> **기본 메모는 지울 수 없다 — 해제만 된다.** 지우면 다음 읽기에서 덧붙임이
> 되살려 놓으므로 삭제 버튼이 거짓말이 되고, 무엇보다 차트의 데이터 원천이
> 사라진다. 슬롯의 §4.2.1("원본은 해제, 확장은 삭제")과 **같은 규칙**이다 —
> 규칙 하나가 두 종류를 다 덮는다.

### 2.7 숫자 메모 — `unit` 이 있으면 숫자다

메모 정의에 단위가 붙으면 그 항목은 숫자를 받는다.

| 필드 | 뜻 |
|---|---|
| `unit` | `'kg'` · `'mg/dL'` — **있으면 숫자 메모**, 없으면 지금까지의 텍스트 메모 |
| `decimals` | 소수 자릿수 (0 또는 1). 없으면 0 |

기록 쪽에는 `value` 한 필드가 는다.

```js
{ slotId: 'memo', slotKey: '000000000memo-weight',
  value: 68.4,            // 숫자 메모만. 텍스트 메모에는 없다
  comment: '아침 공복',     // 선택 — 숫자 옆에 덧붙이는 말
  time: '07:20:00', photos: [...] }
```

- **숫자를 `comment` 에 문자열로 담지 않는다.** `"68.4kg"` 은 차트가 못 읽고,
  파싱하기 시작하면 `"68.4 정도?"` 같은 값에서 무너진다.
- `value` 는 0 이상 유한수만. 범위 상한은 두지 않는다 — 사람마다 다른 것을
  우리가 정하지 않는다는 §1 의 연장이다.
- **사용자도 숫자 메모를 만들 수 있다.** 만들기 팝업에 '숫자로 기록' 토글과
  단위 입력을 둔다(혈압·수면 시간·걸음 수…). 다만 **차트는 v1 에서 기본
  2종만**(§6.2) — 그 이유는 거기 적는다.

## 3. 읽기 경로

### 3.1 바뀌는 함수는 셋

**`resolveSlotView`** — §2.3. base 폴백을 건너뛰고 메모 기본값으로 떨어지는
가지 하나.

**`sanitizeSlots`** — 메모 항목을 살리고(지금은 모르는 `base` 라 버려진다),
아이콘을 정화하고, 슬롯 앞 / 메모 뒤로 안정 정렬한다.

**`groupMealsByUserSlotForDate`** — 지금은 `BASE_IDS.has(m.slotId)` 가 아닌
기록을 **버린다**(그래서 하루 소감 미러가 타임라인에 두 번 안 나온다).
여기에 메모 가지를 연다. 반환 단위는 `{ id:'memo', type:'memo', label, key, icon }`
에 **기록 한 건**이고, **자리는 §3.3 이 정한다.**

타임라인·사진 뷰어·일간 공유 캡처가 **같은 순회 함수 하나**를 쓰고 있으므로
(user-slot-plan §3), 이 한 곳을 고치면 세 화면이 함께 따라온다.

`type: 'memo'` 라는 세 번째 값이 생긴다. `slot.type === 'main' ? A : B` 로
갈라지는 호출부를 전수 확인해 3분기로 바꾼다 — 놓치면 메모가 간식 카드로
그려진다(깨지진 않지만 틀린 그림이다).

### 3.2 메모는 그룹을 이루지 않는다 — 기록 한 건이 한 자리다 ★

슬롯은 `slotKey` 로 묶어 **그룹**을 만든다. 점심 두 건은 한 덩어리로 붙어
나오고, 그 덩어리가 목록에서 한 자리를 갖는다.

메모는 묶지 않는다.

> 아침에 체중을 재고 저녁에 또 잰다. 두 건을 한 덩어리로 묶으면 **한 자리**밖에
> 못 갖는다 — 아침 체중과 저녁 체중이 하루의 한 지점에 뭉쳐 버린다. 시각이
> 자리를 정한다는 §1 대전제가 거기서 죽는다.

그래서 메모는 **기록 한 건이 곧 배치 단위**다. 같은 항목의 다건은 각자의 시각으로
각자의 자리에 놓인다. 슬롯의 묶음 규칙과 메모의 낱건 규칙이 다른 것은,
슬롯이 "그 시간대에 무엇을 먹었나"(한 덩어리)를 말하고 메모가 "그 순간에 이랬다"
(낱건)를 말하기 때문이다.

따라 오는 것 셋:

- **서수를 붙이지 않는다.** 식사는 같은 슬롯 다건에 '점심2'를 붙이지만
  (user-slot-plan §3), 메모는 카드마다 시각이 적혀 있어 이미 구분된다.
- 피커의 건수 배지는 그대로 **그 날 그 항목의 총 기록 수**다(체중 2건).
- 관리자 목록에서도 두 건은 **독립된 두 행**이다(§6.1).

### 3.3 자리 계산 — "그 앞의 마지막 그룹 뒤" ★

메모 기록 **한 건**의 자리를 정하는 규칙은 이것 하나다.

```
그 날의 슬롯 그룹들을 **목록 순서대로** 훑는다.
그룹의 대표 시각 = 그 그룹에서 **사용자가 적은** 가장 이른 시각(mealClock),
                  아무도 안 적었으면 그 슬롯이 뜻하는 시각(§3.3.1).
대표 시각 ≤ 메모의 시각인 그룹을 만날 때마다 앵커를 갱신한다.
→ 메모는 **마지막 앵커 그룹의 바로 뒤**에 놓인다.
앵커가 하나도 없으면(그 날 가장 이른 그룹보다 앞선 메모) 맨 앞.
```

#### 3.3.1 대표 시각은 `time` 이 아니다 ★

끼니 문서의 `time` 은 **정렬용 필드**다. 시각을 안 적으면 저장한 순간이 들어간다
(`entry-save-record.js`). 그걸 대표 시각으로 쓰면 이렇게 된다:

> 아침·점심을 시각 없이 오후 두 시에 몰아 적는다 → 두 그룹의 `time` 이 14시대가
> 된다 → 낮 한 시 반에 한 운동 메모가 **아침 앞**에 선다. 화면에는 끼니 시각이
> 안 보이니 왜 그런지도 알 수 없다.

그래서 대표 시각은 사용자가 실제로 고른 `mealClock` 만 본다. 아무도 안 적은
그룹은 **그 슬롯이 뜻하는 시각**으로 자리를 잡는다:

| base | 이름값 시각 |
|---|---|
| 아침 전 간식 | 06:30 |
| 아침 | 08:00 |
| 오전 간식 | 10:30 |
| 점심 | 12:30 |
| 오후 간식 | 15:30 |
| 저녁 | 18:30 |
| 저녁 후 간식 | 21:30 |

정확한 시각이 아니라 '점심은 낮'이라는 낯이다. 끼니 사이에 메모를 끼우는 데는
이 정도면 충분하고, **시각을 안 적는 사람에게도 아침·점심·저녁이라는 순서
정보는 이미 있다** — 그걸 쓰면 되지 시각 입력을 강요할 이유가 없다.

한 사람이라도 시각을 적었으면 그 시각이 이름값을 이긴다. 09:30 에 먹은 '점심'은
09:30 의 끼니다.

| 그 날 | 메모 | 결과 |
|---|---|---|
| 아침 07:00 · 점심 12:00 · 저녁 19:00 | 체중 07:30 | 아침 **뒤**, 점심 앞 |
| 아침 · 점심 (**둘 다 시각 미입력**) | 운동 13:30 | 점심 뒤 (이름값 08:00·12:30) |
| 〃 | 체중 07:00 | **맨 앞** (아침 08:00 보다 이르다) |
| 〃 | 체중 06:40 | **맨 앞** |
| 〃 | 운동 21:00 | 저녁 뒤 (맨 뒤) |
| 〃 | **체중 07:30 + 체중 21:00** | **아침 뒤에 하나, 저녁 뒤에 하나** (§3.2) |
| 점심 12:00 · 점심 13:30 (같은 그룹 2건) | 혈당 13:00 | 그 그룹 **전체의 뒤** |
| 기록 없음 | 체중 07:30 · 혈당 09:00 | 둘만 시간순 |

**메모는 그룹 사이에만 끼고, 그룹 안을 가르지 않는다.** 위 네 번째 줄이 그
경우다. 그룹은 카드가 이어 붙은 시각적 한 덩어리(`main-slot-card-group`)이고,
그 사이를 벌리려면 렌더를 훨씬 깊이 뜯어야 한다. 얻는 정확도보다 비용이 크다.

같은 앵커에 여러 메모가 걸리면 그들끼리 **시간순**이다.

사용자가 슬롯 순서를 시간과 어긋나게 정해 두면(야식을 아침 위로) 메모가
예상 밖에 낄 수 있다. 규칙은 여전히 결정적이고 한 문장으로 설명되므로 —
"화면에서 그 앞에 있는 마지막 그룹 뒤" — 그대로 둔다.

**하루 소감은 언제나 맨 뒤다**(현행 유지). 우연이 아니라 같은 규칙의 극단이다:
하루 소감 미러의 시각 기본값이 `23:59` 다(`recordedAtIsoToMealTime`).
언젠가 하루 소감을 메모로 흡수하면(§7) 이 자리는 규칙에서 저절로 나온다.

## 4. 화면

### 4.1 피커 — 슬롯 2열 아래에 메모 3열

```
기록 추가  8월 30일 (일)                        📝  ⚙
                                    메모 만들기 ─┘  └─ 기록 항목 설정
┌──────────────┐ ┌──────────────┐
│      아침     │ │     점심      │   ← 식사 항목: 2열, 색 있는 카드
│  ☁   1건      │ │  🍲  아직 없음 │
└──────────────┘ └──────────────┘
┌──────────────┐ ┌──────────────┐
│      저녁     │ │  저녁 후 간식  │
└──────────────┘ └──────────────┘

┌────────┐ ┌────────┐ ┌────────┐          ← 메모: 3열, 중성 색·점선
│   ⚖    │ │   💧   │ │   🚽   │
│  체중   │ │  혈당   │ │  배변   │
│  1건   │ │        │ │        │
└────────┘ └────────┘ └────────┘
        ── 하루 소감 (전체 폭) ──
```

- **줄당 개수와 색이 다르다.** 3열 · 중성(slate) · 점선 테두리. 식사 슬롯은
  base 색을 그대로 쓴다. 두 구역이 한눈에 갈라져야 "이건 밥, 이건 메모"라는
  분류를 설명 없이 전달한다.
- 메모 구역에는 **소제목을 붙이지 않는다.** 격자 모양이 이미 구분을 하고,
  '메모'라는 단어는 사용자가 지은 이름(체중·혈당)보다 정보가 적다.
- 건수 배지는 같은 규칙(`n건` / 없으면 비움 — 3열 카드에는 '아직 없음'이 길다).

### 4.2 기록 항목 설정 — **식사만** 다룬다

```
기록 항목 설정      사용 중 7 / 12          (?)
⠿  ☁  아침 ✎                        사용 중   ⧉
⠿  🍲  점심 ✎                        사용 중   ⧉
⠿  🌙  저녁 ✎                        사용 중   ⧉

적용 시작일  [ 2026-09-01 ▾ ]
9월 1일 기록부터 적용됩니다. …
                          [ 취소 ]  [ 저장 ]
```

**이 시트에 메모는 없다.** 두 판을 거쳐 여기 왔다.

1. 처음엔 '식사 항목 / 메모 항목' 두 구역으로 함께 뒀다.
2. 만들기만 기록 추가 시트로 옮겼더니 **"만들기는 여기, 빼기는 저기"** 가 됐다.
3. 그래서 메모를 통째로 옮긴다 — **기록 항목은 식사, 메모는 메모 설정**(§4.3).

개념이 다른 둘이 한 화면을 나눠 쓰면 어느 쪽을 고치는 화면인지 매번 읽어야
한다. 덤으로 위험 하나가 사라진다: 두 화면이 같은 날짜 개정판을 각자 쓰면
"같은 날짜는 마지막 편집이 이긴다"(user-slot-plan §5.3)로 서로를 덮는다.

> ⚠ **draft 에는 메모가 그대로 들어 있어야 한다.** 저장은 draft 를 통째로
> 개정판에 쓰므로, 안 그린다고 빼버리면 식사 항목을 고쳐 저장할 때마다 메모가
> 사라진다. `sanitizeSlots` 가 메모를 항상 뒤로 몰아 주므로(§2.1) 앞쪽만
> 그려도 인덱스가 그대로 맞는다.

행의 차이는 이미 있는 규칙을 따른다(user-slot-plan §4.2.1 — 한 자리에 하나만):

| 종류 | 손잡이 | 아이콘 | 오른쪽 끝 | 이름 |
|---|---|---|---|---|
| 원본 슬롯 | 있음 | base 고정 | 사용 중 / 사용 안 함 | 편집 |
| 복제 슬롯 | 있음 | base 고정 | 삭제 | 편집 |

메모 행도 같은 규칙을 따르되 그건 메모 설정 팝업에 있다(§4.3) — 기본
메모(체중·혈당)는 **사용 안 함**, 사용자가 만든 것은 **빼기**.

> **빼도 기록과 이름은 남는다**(§2.3 · `retired`). 이 점이 안 보이면 사용자가
> 빼기를 무서워한다 — 도움말에 한 줄 넣는다.

### 4.3 메모 항목 팝업 — 만들기와 빼기는 **같은 자리**여야 한다 ★

**기록 추가 시트 머리의 메모 아이콘**(톱니 왼쪽)에서 연다. 겹치는 팝업이고
도움말과 같은 층이다(`--z-slot-picker-help`).

처음 구현은 이 팝업이 **만들기 전용**이었다. 그러자 곧 지적이 나왔다 —
"넣어둔 걸 빼는 게 안 보인다". 삭제 버튼은 기록 항목 설정 시트에 **있었고
눌리기도 했지만**, 그게 문제가 아니었다:

> 만들기는 피커에 있는데 빼기는 설정 시트에 있다. 방금 만든 것을 무르려면
> 다른 화면으로 가야 한다는 뜻이고, 사용자는 그 화면이 있는 줄 모른다.

그래서 이 팝업을 **메모 항목 전체를 다루는 자리**로 넓힌다. 만들고·고치고·
빼는 일이 한 자리에 모인다.

```
메모 설정                                   ✕
 ⚖  [체중      ]  kg              사용 중      ← 이름은 인라인 입력
 💧  [혈당      ]  mg/dL        사용 안 함
 🏃  [운동      ]                     빼기
─────────────────────────────────
새 메모 항목
 🗒  [이름 (8자)   ]              만들기
 [체중][혈당][배변][운동][수면][약][물][기분]     ← 제안 칩
```

**목록과 새 항목을 한 화면에 둔다.** 한때 목록 뷰·편집 뷰 둘로 나눠 두었는데,
항목이 두어 개뿐인 화면에서 목록을 보고 다시 눌러 폼으로 들어가는 건 헛걸음이다.
만들고 바로 위에 서는 것을 보면 다음 하나를 이어 만들기도 쉽다.

- **목록 행이 곧 편집 행이다.** 이름은 인라인 입력칸이고(입력을 마칠 때 저장 —
  글자마다 저장하면 개정판이 쌓인다), 아이콘 버튼을 누르면 **그 행 바로 아래**에
  30개 격자가 펼쳐진다. 한 번에 하나만 펼친다 — 어느 행의 격자인지가 자리로
  드러나므로 "지금 무엇을 고르는 중인가"를 따로 적지 않는다.
- 꼬리 버튼은 §4.2 의 규칙과 같다 — 기본은 토글, 사용자 것은 빼기.
- **기록 항목 설정 시트에서는 메모를 아예 뺀다**(§4.2). 메모를 쓰는 화면은
  이제 하나다 — 두 화면이 같은 날짜 개정판을 각자 쓰던 위험도 같이 사라졌다.
- 저장은 **즉시**다. 이 팝업에는 저장 버튼이 없고, 적용 시작일은 부른 화면이
  보고 있던 날짜다(미래는 오늘로 자름 — user-slot-plan §5.5).
- 빼기에 확인 창을 띄우지 않는다. 되돌릴 수 없는 일이 아니기 때문이다 — 그
  항목으로 남긴 **기록은 그대로 있고 이름도 유지된다**(§2.3 `retired`).

애초에 이 자리로 옮긴 이유도 같다. 설정 시트에 있으면 "메모를 남기려면 먼저
설정에 들어가야 한다"가 되는데, 사용자가 하려던 일은 **기록**이지 설정이
아니다. 만들자마자 바로 아래 격자에 카드가 서고 누르면 기록으로 이어진다.

#### 새 항목 구역

**프리셋 칩은 이름칸 아래**에 둔다. 처음에는 칩이 맨 위, 이름칸이 그 아래였는데
둘이 형제로 읽혀 "이름 정하는 방법이 둘"처럼 보였다. 게다가 누른 칩에 아무
표시가 남지 않아 눌렸는지도 몰랐다.

칩은 **폼과 나란한 선택지가 아니라 폼을 채우는 도구**다. 그 위계를 배치로
드러낸다 — 앱에 이미 같은 관용구가 있다(`entry-suggest-row`, 기록 시트
'무엇을' 축의 제안 줄: 입력칸 **아래**에 붙고, 고른 칩은 상태가 남는다).

- 새 항목의 기본 아이콘은 **중성**(`sticky-note`)이다. 첫 아이콘(⚖)을 기본으로
  뒀더니 방금 만든 것과 무관하게 '체중'처럼 보였다.
- 만들면 입력칸·아이콘·칩이 모두 초기화된다 — 이어서 하나 더 만들 수 있게.
- 기본 메모(체중·혈당)는 이미 목록에 있으므로 프리셋에서 뺀다(§2.6) — 있는
  것을 또 만들라고 권하지 않는다.

### 4.4 메모 기록 시트

```
체중                                        ✕
  [ ① ↺ ✒ ↻ ] [ ② ... ]            ← 사진이 있으면 미리보기가 위로
 🖼 사진 2/5  [＋][＋]      [1:1][3:4][4:3]
─────────────────────────────────────────
 💬 내용
      [ 68.4kg                        ]
─────────────────────────────────────────
 🕐 시간  [현재 시각 ▾][오후 ▾][ 07:20 ]
                     [ 삭제 ]  [ 저장 ]
```

**끼니 시트와 같은 부품·같은 결이다.** 항목마다 구분선, 라벨은 색 아이콘 +
굵은 글씨, 시각은 출처 버튼이 달린 그 복합 입력칸. 두 시트가 조금씩 다르면
같은 일을 두 번 배우게 된다.

구현도 베끼지 않는다 — CSS 는 기록 시트의 디자인 시스템 선택자
`:is(#entryModal, #dailyJournalModal, #memoRecordModal)` 에 메모 시트를 **넣는**
방식으로 공유한다(하루 소감이 들어온 것과 같은 방식). 값을 복사해 두면 끼니
쪽을 고칠 때 메모만 옛 모양으로 남는다. 메모 전용으로 남는 것은 좁은
시트(22rem)에 맞춘 라벨 칸 폭과, 끼니가 `#entryMealTimeSectionMain` 같은 id 로
받던 시간 행 마감뿐이고 `css/style.css` 맨 끝에 모아 둔다 — 공유 규칙 **뒤에**
와야 이긴다.

라벨 칸은 끼니(7.25rem)보다 좁은 5rem 이다. 끼니에는 '어디서/무엇을/누구와'
처럼 긴 라벨이 있지만 메모 라벨은 두 글자뿐이고, 시트도 좁다. 그 폭을 그대로
쓰면 시각 복합칸이 밀려 시:분이 잘린다.

**칸 순서는 사진 > 값 > 내용 > 시간이다.** 메모를 남기는 손은 대개 사진에서
출발한다 — 체중계를 찍고, 운동 기록을 찍고 나서 말을 붙인다. 그리고 시각은
사진에서 끌어올 수 있으므로(아래 '시각 출처') 사진이 이미 들어와 있어야
마지막 칸에서 확인만 하고 끝난다. 시간이 맨 위에 있으면 아직 아무것도 안 넣은
상태에서 시각부터 정하게 되어, 사진을 넣은 뒤 다시 올라와 고치는 일이 생긴다.

식사 시트(2단계·9축)를 재사용하지 않는다. 메모는 축이 셋뿐이라 그 시트에
태우면 빈 칸이 대부분이다. 새 모달 하나(`memoRecordModal`)를 만들되 **부품은
전부 기존 것**을 쓴다 — 시계 휠(`meal-clock-wheel-picker`), 시각 출처 시트
(`time-source-picker`), 사진 고르기(`image-source-picker`), 사진 편집
(`render/photo-edit`), 사진 업로드(`entry-save-photos` 경로), 저장
(`dbOps.save`).

#### 사진 칸 — 끼니 슬롯의 부품 그대로

미리보기 한 칸에 순서 번호·빼기·앞뒤 이동·**편집**이 다 붙는다. 비율
(1:1·3:4·4:3)도 같은 자리에 둔다. 메모 사진만 기능이 얇으면 "여기서는 왜 못
고치지"가 되고, 고치려고 끼니로 옮겨 적는 일이 생긴다.

사진은 `appState.memoRecordPhotos` 에 산다. 모듈 지역 변수로 두면 사진 편집기가
못 집는다 — 편집기는 컨텍스트 이름으로 배열을 찾아가는 구조라
(`js/render/photo-edit.js` 의 `photoEditContext`), 그 규칙을 따르는 값만
편집·회전·되쓰기를 받는다. 그래서 컨텍스트에 `'memo'` 를 하나 더 낸다.

사진 시각 도장(타임스탬프)은 끼니 전용으로 남긴다 — 하루 소감도 그렇다.
그 도장은 남에게 보일 사진에 찍는 것이고, 메모 사진은 나중에 내가 다시 보는
근거다. 촬영시각은 이미 시각 칸이 받아 간다.

시각 기본값은 **지금**(과거 날짜면 정오). 사용자가 시간을 안 만져도 자리가
정해진다 — §3.3 이 성립하려면 시각이 늘 있어야 한다.

시각 칸은 **끼니 시트와 같은 껍데기**다 — 오전/오후 + 시:분 직접 입력 + 휠로
고르기. 같은 일을 두 가지 모양으로 배우게 하지 않는다. 입력 규칙도 그쪽 것을
그대로 쓴다(`meal-time-utils`) — 치는 동안에는 `1230` → `12:30` 으로 모양만
잡아 주고, 떠날 때 한 번 정리한다(`9` → `09:00`).

- 비우면 **직전 값으로 되돌린다.** 끼니는 시각을 비울 수 있지만(미입력),
  메모의 시각은 **자리를 정하는 값**이라(§3.3) 비울 수 없다.
- 입력칸을 고친 뒤 휠을 열면 **방금 친 값**에서 시작한다.
- blur 없이 저장을 누를 수 있으므로 저장 직전에 입력칸을 한 번 더 집는다.

#### 시각 출처 — 현재 시각 / 사진 시각 / 직접 입력

복합칸 왼쪽의 출처 버튼이 끼니 시트와 같은 출처 목록(`openTimeSourceSheet`)을
연다. 고른 뒤에는 그 버튼에 '현재 시각'·'사진 시각'·'직접 입력'이 그대로 남아,
지금 보이는 시각이 어디서 온 값인지 읽힌다. 사진을 먼저 넣는 순서로 바꾼 이상
'사진 시각'이 가장 잦은 답이 된다 — 아침에 찍어 둔 체중계 사진을 저녁에
넣어도 시각이 아침으로 잡힌다.

**'미입력'만 없다.** 끼니는 슬롯이 자리를 쥐고 있어 시각을 비워도 목록에서
사라지지 않지만, 메모에는 그 슬롯이 없다 — 시각이 곧 자리다(§3.3). 비우는
선택지를 주면 놓을 데가 없는 기록이 생긴다.

사진 시각을 읽으려면 **고를 때 EXIF 를 같이 읽어 둬야 한다.** 업로드하고 나면
Storage URL 만 남고 촬영시각은 사라진다. 그래서 사진 고르기가 끼니와 같은
전처리를 탄다 — `prepareIntakeImage`(다운스케일) + `createPhotoMetaFromFile`
(촬영시각), 결과는 `appState.memoRecordPhotoMeta` 에 사진과 같은 인덱스로.

**저장 경로를 새로 파지 않는다.** `dbOps.save` 안에 아웃박스 내구화·사진
업로드·낙관적 반영이 다 있다(sync-outbox-design §1). 메모용 두 번째 저장기를
만드는 순간 그 불변식이 두 벌이 된다. 다른 것은 토스트 문구와
`bumpUserMealCount` 뿐이고, 둘 다 `opts` 로 가른다.

같은 항목을 하루에 여러 번 남길 수 있다. 피커에서 다시 누르면 **늘 새 기록**이고,
타임라인 카드를 누르면 그 건의 수정이다 — 간식 슬롯과 같은 규칙.

피커의 메모 카드를 눌렀을 때 "오늘 것을 고칠까, 새로 쓸까"를 묻지 않는다.
아침에 잰 체중을 저녁에 또 재는 것이 기본 쓰임이므로(§3.2), 되묻는 화면은
매번 나오는 방해가 된다. 잘못 만든 건은 그 카드를 눌러 지운다.

#### 숫자 메모일 때 (§2.7)

```
체중                                    ✕
사진   0/5  [＋카메라] [＋앨범]        [1:1][3:4][4:3]
값     [ 68.4 ] kg          ← 숫자 메모에만. inputmode=decimal
내용   [ 아침 공복        ]   ← 선택 — 숫자 옆에 덧붙이는 말
시간   [오전 ▾][ 07:20 ][시계]
                     [ 삭제 ]  [ 저장 ]
```

- 값 칸이 **내용 위**에 온다. 숫자가 이 기록의 본체이기 때문이다.
  사진 아래인 것은 값을 사진에서 읽어 적는 일이 많아서다 — 체중계 눈금.
- 값이 비면 저장할 수 없다 — 숫자 메모의 빈 저장은 §4.6("있었다")과 달리
  아무 뜻이 없다. 텍스트 메모는 지금대로 빈 저장이 유효하다.
- 기본값은 **그 항목의 가장 최근 값**을 흐리게 채워 둔다(placeholder). 체중은
  어제와 비슷한 값을 넣는 일이 대부분이라 타이핑이 크게 준다. 자동 입력은
  하지 않는다 — 안 고치고 저장하면 거짓 기록이 된다.

### 4.5 타임라인 카드

간식 카드보다 한 단 낮은 밀도로 한 줄. 같은 항목의 다건은 **각자의 자리**에
따로 뜬다(§3.2) — 서수('체중2')는 붙이지 않는다. 시각이 이미 구분한다.

```
│ ⚖  체중             오전 7:20
│    68.4kg
   … 점심 …
│ ⚖  체중             오후 9:10
│    68.9kg                          [사진]
```

### 4.6 빈 메모는 '있었다'는 기록이다

배변·복약처럼 **유/무만** 남기고 싶은 항목이 있다. 여기에 체크박스를 새로
만들지 않는다.

> 본문도 사진도 없이 저장한 메모는 **유효한 기록**이다. 항목을 눌러 시간만
> 찍고 저장하면 그 자체가 "있었다"가 된다.

카드에는 아이콘·이름·시간만 남는다. 새 필드 없이 새 쓰임이 열리는 자리라
규칙으로 못 박아 둔다. (식사 기록은 반대로 빈 저장을 막는다 — 그쪽은 "뭘
먹었는지"가 본체이기 때문이다.)

## 5. 저장·동기화

기존 경로를 그대로 탄다. 새로 정할 것이 사실상 없다는 것이 §2.1·§2.2 결정의
값이다.

| 무엇 | 어디로 | 아웃박스 |
|---|---|---|
| 메모 **정의**(이름·아이콘·삭제) | `userSettings.slotPlan` | `settings` · `mergePayload` |
| 메모 **기록**(본문·사진·시간) | `meals/{id}` | `meal` · content 등급 |

- 충돌 규칙 하나 그대로: **같은 날짜 개정판은 마지막 편집이 이긴다**(§5.3).
- 정의와 기록의 도착 순서를 강제하지 않는다(§5.4). 기록이 먼저 오면 폴백
  이름('메모')이 잠깐 뜨고, 정의가 도착하면 교정된다.
- `slotPlan` 부분 손상 보호(§5.1)가 메모 이름까지 함께 지킨다.

넣는다 — 기능이 먼저 들어가면 통계가 조용히 틀어진다.

미러를 `count` 에 세고 있다 — 메모와 무관한 과다계수다. 여기서 함께 고치되
**과거 집계는 소급하지 않는다**(재집계는 별건이다). 고치는 순간 사용자의 '총
기록 수'가 하루 소감 수만큼 줄어 보이므로, 고칠지 말지는 실제 분포를 보고
정한다 — 이 문서는 "여기 있다"까지만 정한다.

### 6.1 관리자 모먼트 관리 — '사용자 메모'로 들어온다

빼는 게 아니라 **넣는다.** 사용자가 올린 사진·글이므로 모니터링 대상이다.
하루 소감이 이미 같은 방식으로 들어와 있고(`mealRowToFeedRow`), 그 자리에
가지를 하나 더 연다. 새 컬럼을 만들지 않고 **기존 컬럼에 싣는다.**

| 컬럼 | 메모 행이 싣는 값 |
|---|---|
| 유형 | **`사용자 메모`** |
| 식사구분 (`slotDisplayLabel`) | **기록 당시의 항목 이름** (`memoLabel`) |
| 날짜 · 시간 | `date` · `mealClock`/`time` (§3.3 의 그 값) |
| 코멘트 | `comment` (메모 본문) |
| 사진수 · 공유여부 · 금지여부 · 신고수 | 기존 로직 그대로 |
| 어떻게 · 어디서 · 무엇을 · 누구와 · 만족도 · 포만감 | **빈칸** (메모에 없는 축) |

- **이름은 기록 시점의 것이다** — meals 문서에 `memoLabel` 을 함께 적는다.
  설계 초안은 "행마다 그 userId 의 plan 으로 푼다"였는데, 구현하며 뒤집었다:
  미러의 `users` 스토어는 **분석이 쓰는 여섯 필드의 투영**이라 `slotPlan` 이
  없다(admin-local-mirror 2단계). 넣으려면 미러 스키마를 올리고 모니터링 행
  빌더가 두 스토어를 조인해야 하는데, 그 값이 필드 하나보다 크지 않다.
  덤으로 모니터링에는 **그때 뭐라고 불렀는지**가 오히려 맞는 정보다.
- 그래서 이름 해석 규칙이 둘이 된다: 앱 화면은 key 로 풀어 **소급**되고
  (§2.3), 관리자 열은 기록 당시 이름으로 **고정**된다. 화면 코드는
  `memoLabel` 을 읽지 않는다 — 읽는 순간 소급이 반쪽이 된다.
- 일괄 처리 체크박스는 하루 소감처럼 **비활성**이다. v1 에서 메모 사진은
  모먼트 공유 대상이 아니라 '공유 해제'로 할 일이 없다.
- 엑셀·CSV 내보내기는 같은 행 생성기를 지나므로 자동으로 따라온다.

### 6.2 분석 탭 — 폴백 사슬을 한 칸 늘린다 ★

> **구현 메모(2026-08-30).** 사슬은 세 칸이고 세 칸 전부 실측했다 —
> 메모만 70.2kg / 하루 소감만 66.6kg / 구세대 `dailyVitals` 만 55.5kg.
> 반대 방향(하루 소감의 값을 메모 카드로 보이기)는 §7.2 다 — 둘 다
> ‘옷기지 않고 읽는 자리에서 합친다’는 같은 수다.

숫자 메모의 값이 분석 탭의 **체중·혈당 추이 차트**로 간다
(`js/analytics/health-charts.js`, 864줄 · KPI 카드 + 차트 두 개).

지금 그 차트는 이렇게 읽는다:

```
getMetricRecordsForDate(settings, date, metric)
  1. dailyComments[date].weightRecords      ← 하루 소감의 숫자 (현행)
  2. ||= dailyVitals[date]                  ← 구세대 필드 (레거시 폴백)
```

여기에 **한 칸을 앞에 붙인다.**

```
  0. slotKey === defaultMemoKey('weight') 인 그 날짜 메모 기록의 value
  1. ||= dailyComments[date].weightRecords
  2. ||= dailyVitals[date]
```

- **마이그레이션이 없다.** 옛 데이터를 옮기지 않고 사슬만 늘린다 — 이미 이
  함수가 `dailyVitals` 에 쓰고 있는 수법 그대로다. 이 프로젝트의 관용구다.
- 항목 이름을 '몸무게'로 바꿔도 **key 로 찾으므로** 차트가 안 끊긴다(§2.6).
- 메모는 하루 다건이라(§3.2) 차트가 이미 기대하는 모양
  (`[{value, time}]`)과 그대로 맞는다.

**차트는 v1 에서 기본 2종만 만든다.** `health-charts.js` 는 두 지표 전용으로
짜였고 `index.html` 에 캔버스·KPI 카드가 하나씩 박혀 있다. 사용자가 만든
숫자 메모(혈압·수면…)까지 차트를 뽑으려면 그 파일을 N지표로 일반화해야 하는데,
**어떤 지표를 실제로 만드는지 보고 결정한다.** 지금 정하는 것은 "값은 다
모인다"까지다 — 데이터가 쌓여 있으면 차트는 나중에 붙일 수 있다.

식단분석(Gemini)에는 **넣지 않는다.** 지금 프롬프트에 체중·혈당이 아예 없고,
프롬프트는 `docs`·`functions`·`admin` 세 사본이 바이트 단위로 같아야 한다.
값이 없다는 뜻이 아니라 **별건**이라는 뜻이다.

## 7. 하루 소감 — 숫자 메모가 문을 연다

숫자 메모(§2.7)와 분석 연결(§6.2)이 들어가면 하루 소감을 막고 있던 것이
하나 줄어든다. 남는 것을 정리하면:

| 얽힌 것 | 지금 | 흡수하려면 | 상태 |
|---|---|---|---|
| 체중·혈당 | 숫자 + 시각 + 최대 3건 + 추이 | 메모에 숫자 필드 | **§2.7 로 해결** |
| 차트 | `dailyComments` 를 읽는다 | 메모도 읽어야 | **§6.2 로 해결** |
| 본문·사진 | `userSettings.dailyComments[date]` | `meals` 로 이전 | 남음 |
| 미러 | `meals/dailyJournal_{date}` (파생) | 파생이 본체가 된다 | 남음 |
| 모먼트 공유 | `dailyJournal_{date}` entryId 규약 | 규약 유지 필요 | 남음 |
| 관리자 | 모니터링 특례 · 백필 Callable | 재작성 | 남음 |

자리는 §3.3 이 이미 열어 뒀다. 시각 `23:59` 인 메모는 규칙상 하루의 맨 뒤이므로
하루 소감을 메모로 옮겨도 **자리가 지금과 같다.**

### 7.1 순서 — 지우기 전에 옮긴다

체중·혈당 입력구가 하루 소감과 메모 **두 곳**이 되는 기간이 생긴다. 그대로
두면 사용자가 어디에 적을지 헷갈리고, 차트도 두 소스를 합쳐야 한다.

그래서 이렇게 간다:

1. **숫자 메모 + 기본 항목**(§2.6·§2.7) — 체중·혈당이 메모에 생긴다. ✅
2. **읽는 자리에서 합친다** — 하루 소감에 쌓인 체중·혈당을 기본 메모 기록처럼
   타임라인·피커에 보여 준다. ✅ (§7.2)
3. **하루 소감의 체중·혈당 입력 UI 제거** — 새 입력은 메모로만 들어온다.
   옛 데이터는 계속 읽힌다. 제거하는 배포에 "체중은 이제 메모로" 한 줄 안내. ✅

   > ⚠ **저장 경로가 옛 값을 실어 내야 한다.** 입력기를 걷었으므로
   > `saveDailyJournal` 이 DOM 에서 지표를 모으면 빈 배열이 되고, 그대로
   > 저장하면 **소감을 한 번 고칠 때마다 옛 체중 기록이 지워진다.**
   > 이전 값(`prev`)을 그대로 넘겨 막았고, 저장 경로를 가로채 실측했다.

   > ⚠ **차트를 먼저 이어야 한다.** 입력기를 걷으면 새 값은 메모로만 들어오는데
   > 차트가 `dailyComments` 만 읽고 있으면 분석 탭이 새 값을 못 읽는다.
   > 그래서 §6.2 를 이 단계 **앞에** 넣었다.
4. (그 뒤) 하루 소감 자체를 메모로 흡수할지는 남은 넷을 보고 다시 판단.

3번까지 하면 하루 소감은 **텍스트 + 사진**만 남는다 — 그게 정확히 메모 하나의
모양이다. 4번은 그때 다시 꺼낸다.

### 7.2 마이그레이션은 **데이터를 옮기지 않는다** ★

"하루 소감의 체중·혈당을 메모로 옮긴다"를 실제 데이터 이동이 아니라 **읽기
시점의 합침**으로 구현했다(`journalMemoUnitsForDate`, `js/utils/slot-view.js`).

| | 실제 이관 | **읽으며 합치기** |
|---|---|---|
| meals 문서 | 사용자당 수백 개 새로 생김 | 0개 |
| 되돌리기 | 불가 | **코드만 되돌리면 원상복구** |
| 두 곳 입력 기간 | 중복을 따로 처리해야 | 저절로 한 화면에 합쳐짐 |
| 사용자가 보는 것 | 같다 | 같다 |

사용자에게는 결과가 같고, 우리는 되돌릴 수 있는 쪽을 고른다. 실제 이관이
필요해지는 순간은 하루 소감 입력 UI 를 걷을 때인데(3번), 그때도 이 합침이
계속 읽으므로 **이관 자체가 필요 없을 수 있다.**

- 이 기록은 **읽기 전용**이다. 누르면 하루 소감 시트가 열린다 — 정본이 거기다.
- 하루 소감 카드의 `#체중 68.4 > 68.9` 해시태그 미리보기는 **걷어냈다.** 같은
  값이 이제 제 시각 자리에 메모 카드로 뜨므로, 두면 한 화면에 같은 숫자가 두 번
  나온다.
- 사용자가 기본 메모를 '사용 안 함'으로 끄면 합침도 멈춘다 — "이 항목 안 볼래"의
  자연스러운 귀결이고, 값 자체는 하루 소감 시트에 그대로 있다.

### 7.3 하루 소감은 메모 목록의 **기본 항목**이다

흔수를 놓았던 4번은 이렇게 답했다: 저장소는 그대로 두고 **목록에서의 자리만**
메모 규칙을 따르게 한다.

| | 메모 규칙을 따른다 | 그대로다 |
|---|---|---|
| 피커의 자리 | 메모 격자의 한 칸 | |
| 사용 여부 | 기본 항목 토글 | |
| 순서 | 끌어 바꿈 | |
| 이름·아이콘 | 고칠 수 있음 | |
| 기록 저장소 | | `dailyComments` |
| 기록 시트 | | 하루 소감 시트 |
| 타임라인 카드 | | 하루의 끝 (23:59) |

저장소를 건드리지 않았으므로 **모먼트 공유 규약·관리자 특례·백필이 그대로
돌아간다.** §7 표에서 '남음'이던 네 중 세을 안 건드리고 사용자가 보는
모양만 바꿔놓은 셈이다 — 완전 흡수(저장소 이전)는 여전히 열려 있다.

피커에서 전체 폭 한 줄이던 하루 소감 행은 없어졌다. 메모 격자가 4열이므로
**식사 카드 2칸 = 메모 카드 4칸**이다 — 두 격자의 폭이 같고 gap 이 같으므로
저절로 떨어진다.

### 7.3 하루 소감은 메모 목록의 **기본 항목**이다 ★

흔수를 놓았던 4번을 이렇게 답했다: **저장소는 그대로 두고 목록에서의
자리만** 메모 규칙을 따르게 한다.

| 메모 규칙을 따른다 | 그대로다 |
|---|---|
| 피커에서 메모 격자의 한 칸 | 기록 저장소는 `dailyComments` |
| 사용 중 / 사용 안 함 토글(기본 항목) | 누르면 하루 소감 시트가 열린다 |
| 순서 끌기 | 타임라인 카드는 하루의 끝(23:59) |
| 이름·아이콘 고치기 | 모먼트 공유·관리자 특례·백필 규약 |

저장소를 안 건드렸으므로 §7 표에서 '남음'이던 네 중 세은 그대로 놓아둔
셀이다 — 사용자가 보는 모양만 메모로 맞추고, 완전 흡수(저장소 이전)는
여전히 열려 있다.

피커에서 전체 폭 한 줄이던 하루 소감 행은 없어졌다. 메모 격자를 4열로 두어
**식사 카드 2칸 = 메모 카드 4칸**이 된다 — 두 격자의 폭과 gap 이 같으므로
맞추는 숫자 없이 저절로 떨어진다.

## 9. 남은 위험

1. **구버전 클라이언트가 메모 정의를 지운다.** ★
   `sanitizeSlots` 는 모르는 `base` 를 버린다 — 구버전은 메모 항목을 통째로
   버린다. 구버전에서 **기록 항목 설정을 저장하면** 그날 개정판에 메모가 빠진
   채 쓰여, 그날부터 메모가 사라진다(기록과 이름은 §2.3 이 지킨다).
   웹은 main, APK 는 staging 을 받으므로 이 창은 실재한다.
   → **3단계 이후는 웹·APK 를 묶어서 내보낸다.** user-slot-plan §8-4 와 같은
   제약이고, 같은 이유다.
2. **`type` 3분기 누락.** `main ? A : B` 이분기가 남아 있으면 메모가 간식으로
   그려진다. 2단계에서 전수로 훑고, 새 값에 `default` 분기를 두지 않는다
   (조용히 통과하는 대신 눈에 띄게).
3. **자리가 튀어 보이는 경우.** 사용자가 슬롯 순서를 시간과 어긋나게 정하면
   §3.3 의 결과가 직관과 다를 수 있다. 규칙은 결정적이고 한 문장이지만,
   실사용에서 불평이 나오면 그때 데이터를 보고 조정한다 — **지금 예외를 만들지
   않는다.**
4. **아이콘 화이트리스트 우회.** 다른 기기·구버전이 임의 문자열을 쓸 수 있다.
   `sanitizeSlots` 가 **읽기 시점**에 정화한다.
5. **`meals` 문서 수 증가.** 하루 4건 메모면 기록 수가 2배 가까이 된다.
   날짜 범위 로딩이라 정기 읽기 비용은 그대로지만, 관리자 미러 부트스트랩
   (~1.2만 읽기)이 커진다. 미러는 증분이라 정기 비용은 안 오른다.
6. **관리자 목록이 메모로 붐빈다.** 모니터링은 사진·글 검토가 목적인데 사진
   없는 메모("68.4kg")가 다수 섞인다. 유형 필터에 '사용자 메모'를 넣어 접을 수
   있게 한다 — 5단계에서 함께.

## 10. 안 하기로 한 것

- **메모 항목의 순서 편집.** §1 대전제. 순서를 주는 순간 "아침체중/점심체중"
  문제가 돌아온다.
- **사용자 숫자 메모의 차트.** 값은 다 모으되(§2.7) 차트는 기본 2종만 그린다.
  `health-charts.js` 를 N지표로 일반화하는 일은 **어떤 지표를 실제로 만드는지**
  보고 정한다(§6.2). 데이터가 쌓여 있으면 차트는 나중에 붙일 수 있다.
- **식단분석(Gemini)에 체중·혈당 넣기.** 프롬프트 세 사본이 바이트 단위로
  같아야 하는 제약이 있어 별건으로 둔다(§6.2).
- **시간대 태그(오전/오후).** 이것이 곧 "아침체중/점심체중"이다. 시각이 이미
  그 정보를 담고 있고, 자리는 §3.3 이 계산한다.
- **메모 사진의 모먼트 공유.** 공유는 식사 전제의 규약(entryId·슬롯 라벨·신고
  경로)이 있다. 메모를 얹기 전에 그 규약을 다시 봐야 한다.
- **알림·반복.** "매일 아침 체중 남기기" 같은 것. 푸시 파이프라인이 따로 있고
  (push-notifications.md), 기록 항목과 엮으면 둘 다 복잡해진다.
- **메모 항목 복제.** 슬롯의 복제는 base 를 물려받기 위한 장치였다. 메모는
  base 가 없어 '새로 만들기'와 다를 게 없다.
