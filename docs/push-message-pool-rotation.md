# 푸시 메시지 풀 · 셔플 순환 발송 기획

작성일: 2026-08-25
대상: 관리자화면 > 푸시메시지

## 1. 문제

지금은 발송 1건마다 제목·내용을 직접 타이핑한다. 실제로는 비슷한 메시지가 반복되는데,
매번 새로 쓰는 비용이 그대로 든다. 과거에 썼던 메시지를 자산으로 쌓아두고, 정해진 요일·시각에
자동으로 하나씩 꺼내 보내고 싶다.

## 2. 요구사항

- 메시지들을 미리 저장해두는 **풀(pool)** 을 만든다.
- 반복되는 날짜·시각에 풀에서 **랜덤으로 하나씩** 보낸다.
- 한 바퀴(풀 전체)를 다 보내기 전에는 같은 메시지가 다시 나오지 않는다. **덱(deck) 셔플** 방식.
- 한 바퀴가 끝나면 다시 셔플해서 새 바퀴를 돈다.
- 운영 도중 메시지 추가가 가능하고, 추가한 메시지도 곧 순서에 낀다.

## 3. 설계 원칙 — 기존 엔진을 갈아엎지 않는다

현재 발송 엔진은 이미 안정적으로 돈다.

```
adminScheduledPushes (status: pending, scheduledAt)
        ↓  processScheduledAdminPushes (매분 크론)
   broadcastAdminPushToAllUsers → status: sent
```

순환 발송은 **"예약 문서를 대신 만들어주는 층"** 으로만 얹는다. 발송 경로·취소·기록·집계는
전부 기존 것을 그대로 쓴다. 새로 만드는 것은 (a) 메시지 풀, (b) 덱 상태, (c) 미리 배정하는 크론
세 가지뿐이다.

```
adminPushMessages (풀)            adminPushRotations (슬롯 + 덱 상태)
            \                        /
             └──> planAdminPushRotations (매일 1회 크론)
                              ↓
                  adminScheduledPushes 문서 생성
                  (scheduleSource: 'rotation')
                              ↓
                  기존 발송 엔진 그대로
```

## 4. 데이터 모델

### 4.1 메시지 풀 — `artifacts/{appId}/adminPushMessages/{messageId}`

| 필드 | 타입 | 설명 |
|---|---|---|
| `title` | string | 제목 (≤120자, 기존 `ADMIN_BROADCAST_TITLE_MAX`) |
| `body` | string | 내용 (≤240자, 기존 `ADMIN_BROADCAST_BODY_MAX`) |
| `landingTab` | string | `dashboard`\|`timeline`\|`gallery`\|`board`\|`settings` — **메시지별로 지정** |
| `active` | boolean | false면 순환에서 제외 (이력은 보존) |
| `useCount` | number | 누적 발송 횟수 |
| `lastUsedAt` | Timestamp\|null | 최근 발송 시각 |
| `lastCycleNo` | number\|null | 최근에 뽑힌 사이클 번호 |
| `createdByUid` / `createdAt` / `updatedAt` | | |

대상 환경(운영/스테이징)은 메시지 속성이 아니라 **발송 성격**이므로 순환 설정에 둔다.

### 4.2 순환 설정 + 덱 상태 — `artifacts/{appId}/adminPushRotations/{rotationId}`

단일 공용 풀이므로 문서는 `default` 하나로 시작한다. (구조상 여러 개도 가능하게 열어둔다.)

| 필드 | 타입 | 설명 |
|---|---|---|
| `name` | string | 표시용 이름 |
| `enabled` | boolean | 순환 사용 여부 (끄면 새 배정 중단) |
| `targetEnv` | string | `all`\|`production`\|`staging` |
| `slots` | array | `[{ weekday: 1~7, time: 'HH:mm' }]` — 월=1, 일=7 (기존 `weeklySchedule` 규칙 재사용) |
| `horizonDays` | number | 며칠치를 미리 배정해둘지. 기본 **14** |
| `cycleNo` | number | 현재 몇 바퀴째인지 (1부터) |
| `deckRemaining` | string[] | 이번 바퀴에서 **아직 배정되지 않은** 메시지 ID (셔플된 순서) |
| `deckServed` | string[] | 이번 바퀴에서 이미 배정된 메시지 ID |
| `lastAssignedMessageId` | string\|null | 바퀴 경계 중복 방지용 |
| `plannedUntilYmd` | string | 어디까지 배정했는지 (`YYYY-MM-DD`) |
| `newMessagePriority` | boolean | 새로 추가한 메시지를 앞쪽에 우선 배정할지. 기본 **true** |
| `priorityWindow` | number | 우선 배정 폭 — 앞쪽 몇 회 안에 끼울지. 기본 **10** |
| `updatedAt` / `updatedByUid` | | |

**무기한 운영**이므로 종료일은 없다. 대신 `horizonDays` 만큼만 앞서 배정하고, 크론이 매일 밀어준다.

### 4.3 순환에서 생성된 예약 문서 (기존 컬렉션에 필드만 추가)

`adminScheduledPushes/{docId}` — `scheduleType: 'once'` 그대로. 추가 필드:

| 필드 | 설명 |
|---|---|
| `scheduleSource` | `'rotation'` (기존 `'weeklyByDayExpanded'` 와 같은 자리) |
| `rotationId` | 출처 순환 |
| `messageId` | 풀 원본 ID |
| `cycleNo` / `deckIndex` | 몇 바퀴째 몇 번째인지 (`12/40` 표시용) |

`title`·`body`·`landingTab`은 **배정 시점에 복사(스냅샷)** 한다. 원본 메시지가 나중에 지워져도
발송은 정상 동작하고, 발송완료 기록도 그대로 남는다.

### 4.4 문서 ID를 결정론적으로 — 중복 발송 방지의 핵심

크론 재실행·중복 실행·수동 재배정이 겹쳐도 같은 슬롯에 두 건이 생기면 안 된다. 그래서
자동 ID 대신 슬롯에서 계산한 ID를 쓴다.

```
docId = `rot_${rotationId}_${YYYYMMDD}_${HHmm}`
```

`add()`가 아니라 "없을 때만 생성"(트랜잭션 내 존재 확인)으로 쓰면, 몇 번을 돌려도 슬롯당 1건이 보장된다.

## 5. 덱 알고리즘

### 5.1 뽑기

```
draw(rotation):
  if deckRemaining 이 비었으면:
      pool = active 메시지 ID 전부
      if pool 이 비었으면: 배정 중단 (경고)
      deckRemaining = shuffle(pool)                  # Fisher–Yates
      if deckRemaining[0] === lastAssignedMessageId and 길이 >= 2:
          swap(deckRemaining[0], deckRemaining[1])   # 바퀴 경계에서 연속 중복 방지
      cycleNo += 1
      deckServed = []
  id = deckRemaining.shift()
  deckServed.push(id)
  lastAssignedMessageId = id
  return id
```

풀이 40개면 40번 뽑는 동안 중복이 없고, 41번째에 새로 셔플된다. 요구사항 그대로다.

### 5.2 도중에 메시지를 추가하면

새 메시지는 **다음 바퀴까지 기다리지 않고 이번 바퀴 잔여 구간에 랜덤 위치로 끼워 넣는다.**

```
insertAt = newMessagePriority
             ? randomIndex(0 .. min(deckRemaining.length, priorityWindow))   # 앞쪽 N회 안에
             : randomIndex(0 .. deckRemaining.length)                        # 잔여 구간 전체
deckRemaining.splice(insertAt, 0, newId)
```

- 이미 배정이 끝난 미래 예약 문서는 건드리지 않는다 (관리자가 이미 목록에서 확인한 내용이므로).
- 잔여가 0이면 다음 셔플에 자연히 포함된다.
- 이 덕분에 "40개 등록 → 운영 중 5개 추가"가 매끄럽다. 그 바퀴는 45개짜리가 된다.
- **`newMessagePriority`(기본 켜짐, `priorityWindow` 기본 10)** — 풀이 커질수록 잔여 구간이 길어져
  방금 쓴 메시지가 몇 달 뒤에나 나가는 문제가 생긴다. 자세한 건 12장.

### 5.3 메시지를 비활성/삭제하면

- `deckRemaining`에서 제거한다.
- 이미 배정된 **미래 pending 예약** 중 그 메시지를 쓰는 건이 있으면 → 덱에서 새로 뽑아 자동 교체한다.
  (이미 발송된 건은 그대로 둔다.)

### 5.4 메시지를 수정하면

이미 배정된 미래 예약에 반영할지 묻는다. 기본은 **반영**(제목·내용·랜딩 덮어쓰기).
"이 예약만 손댄" 건(아래 6.3의 개별 수정)은 `rotationEdited: true` 로 표시해두고 덮어쓰지 않는다.

## 6. 배정 흐름

### 6.1 크론 — `planAdminPushRotations`

- `onSchedule('10 3 * * *', Asia/Seoul)` — 매일 새벽 3시 10분.
- `enabled === true` 인 순환마다:
  1. 오늘부터 `horizonDays` 뒤까지의 KST 날짜를 돌며 `slots`에 걸리는 시각을 모두 나열
     (기존 `enumerateWeeklyOccurrences` 로직 재사용, 종료일 대신 호라이즌 사용).
  2. 이미 문서가 있는 슬롯은 건너뛴다 (결정론적 ID 덕분에 조회 한 번이면 됨).
  3. 빈 슬롯마다 `draw()` → 예약 문서 생성.
  4. 덱 상태 + `plannedUntilYmd` 갱신.
- 슬롯 나열 → 문서 생성 → 덱 갱신은 **한 트랜잭션**으로 묶는다. 중간에 실패하면 덱이 앞서나가지 않는다.
- 1회 배정 상한을 둔다 (예: 200건). 슬롯 설정 실수로 폭주하는 걸 막는다.

### 6.2 발송 시 — 기존 크론에 후처리 한 줄

`processScheduledAdminPushes`가 발송에 성공한 뒤, 문서에 `messageId`가 있으면
해당 메시지의 `useCount` +1, `lastUsedAt`·`lastCycleNo` 갱신. 실패해도 발송에는 영향 없게 best-effort.

### 6.3 개별 예약 손보기

발송예정 목록에서 순환 예약 1건에 대해:

- **수정** — 기존 인라인 편집 그대로. 저장 시 `rotationEdited: true` 가 붙어 이후 원본 동기화에서 제외된다.
- **다른 메시지로 교체(재추첨)** — 덱에서 다시 뽑아 갈아끼운다. 원래 쓰던 메시지는 덱 잔여 앞쪽으로 되돌린다.
- **취소** — 기존 취소 그대로. 취소된 슬롯은 크론이 다시 채우지 않는다 (`rotationSkipped: true` 표시).

## 7. 화면 기획

기존 `푸시메시지 관리` 카드에 상단 탭을 2개 추가한다.

```
[ 발송예정 12 ] [ 발송완료 340 ] │ [ 메시지 풀 40 ] [ 순환 설정 ]
```

### 7.1 메시지 풀 탭

기존 발송예정 테이블과 같은 밀도의 표.

| 열 | 내용 |
|---|---|
| 선택 | 체크박스 — 선택 예약·선택 삭제용 (헤더 체크는 현재 페이지만) |
| 상태 | 활성/비활성 토글 |
| 랜딩 | 셀렉트 (밀당/밀로그/모먼트/라운지/설정) |
| 제목 | 인라인 편집 |
| 내용 | 인라인 편집 (textarea) |
| 사용 | `12회 · 3일 전` |
| 이번 바퀴 | `대기` / `배정됨` / `발송됨` — 지금 덱 어디에 있는지 |
| 작업 | 저장 / 삭제 |

- 하단 `+ 메시지 추가` — 기존 `createAdminPushNewNotification` 의 인라인 초안 패턴을 그대로 재사용.
- 풀이 커지는 걸 전제로 상단에 **검색 · 활성 필터 · 정렬(최근 사용순/사용 횟수순)** 을 둔다. (12장)
- **선택 예약** — 체크한 메시지들을 한 번에 발송예정 탭의 작성 행으로 옮긴다. 앞 행 기준으로
  하루씩 밀려 채워지므로, 날짜만 손보고 `저장 (N)` 한 번으로 전부 등록된다.
  한 건씩 담으려고 탭을 왕복하지 않아도 된다.
- **선택 삭제** — 체크한 메시지를 한 번에 풀에서 뺀다. 이미 등록된 예약에는 영향이 없다.

### 7.1.1 대량 등록 — 엑셀 파일 임포트는 만들지 않는다

두 경로면 충분하고, 둘 다 파일 업로드가 필요 없다.

**① 기록에서 선택해 가져오기 (주력)**

발송예정·발송완료 탭에서 행을 체크하고 `풀에 담기` 를 누르면 그대로 풀에 들어간다.

- 기존 목록은 이미 `title`·`body`·`landingTab`·`targetEnv` 를 전부 들고 있다 (`refreshAdminScheduledPushesCore`
  가 350건까지 로드). **파싱도 열 매핑도 서버 왕복도 없다.**
- 선택 상태(`adminPushSelectedIds`)와 일괄 작업 바(`buildAdminPushBulkBarHtml`)가 이미 있다.
  지금 일괄 취소에 쓰는 그 UI에 버튼 하나를 더하는 수준이다.
- 제목+내용 해시로 중복을 제거해 이미 풀에 있는 문구는 건너뛴다.
- **일회성 시드가 아니라 상시 기능이다.** "즉시 발송한 게 반응 좋네 → 풀에 담기" 로 계속 쓰인다.

**② 한 건씩 직접 입력**

풀 탭 하단의 `메시지 추가` 인라인 행으로 그때그때 한 건씩 넣는다.

**엑셀 파일 업로드도, 붙여넣기 대량 등록도 만들지 않는다** — 새 문구를 한 번에 수십 개
쏟아 넣을 일이 없다는 게 운영 판단이다. 기존 기록이 이미 자산이므로 ①이 대량 등록을 대신하고,
새 문구는 ②로 한 건씩 들어온다.

엑셀 파일 업로드는 그 위에 한글 CSV 인코딩(엑셀 기본 CP949 vs UTF-8 BOM) 문제, 열 매핑 UI,
파싱 라이브러리(SheetJS)로 인한 관리자 번들 증가까지 얹는데 얻는 게 ①과 같다.
나중에 정말 필요해지면 그때 붙인다.

### 7.2 순환 설정 탭

슬롯은 화면에서 **요일 × 시각의 곱**으로 다룬다. 실제 운영이 "월·수·금 09:00·20:00" 형태라
쌍을 하나씩 찍는 것보다 빠르고, 서버에는 펼쳐진 `[{weekday,time}]` 로 저장된다.

```
순환 발송           [ ●─ 켜짐 ]
대상 환경           ( 전체 / 운영 / 스테이징 )
발송 요일           월 화 수 목 금 토 일   ← 요일 칩
발송 시각           09:00  ✕     20:00  ✕     + 시각 추가
미리 배정 기간       [ 14 ] 일치
새 메시지 우선       [ ●─ 켜짐 ]  다음 [ 10 ] 회 안에 배정

── 현재 상태 ─────────────────────────────
2번째 바퀴 · 40개 중 27개 남음
다음 발송  8/26 (화) 09:00 — "오늘 첫 끼는 뭐였나요?"
배정 완료  9/8 (월) 까지

[ 지금 다시 채우기 ]   [ 남은 바퀴 다시 섞기 ]
```

- `남은 바퀴 다시 섞기`: `deckRemaining`만 재셔플하고, 이미 배정된 미래 pending도 다시 뽑아 채운다.
- 풀이 비어 있거나 슬롯이 없으면 저장 시 경고를 띄우고 크론은 조용히 건너뛴다.

### 7.3 발송예정 목록에서의 표시

순환에서 온 행은 제목 앞에 뱃지를 단다.

```
🔁 순환 13/40    오늘 첫 끼는 뭐였나요?
```

수동 예약과 섞여 보이지만 출처가 한눈에 구분되고, 취소·삭제·일괄선택은 기존 동작 그대로다.

## 8. 서버 API

### Callable (관리자 전용, `isAdminByUid` 확인)

| 이름 | 역할 |
|---|---|
| `upsertAdminPushMessage` | 풀 메시지 생성/수정 (+ 미래 예약 동기화 옵션) |
| `deleteAdminPushMessage` | 삭제 (+ 미래 예약 자동 교체) |
| `bulkCreateAdminPushMessages` | 붙여넣기 대량 등록 (TSV·빈줄 구분, 중복 제거) |
| `importAdminPushMessagesFromHistory` | 선택한 발송예정·발송완료 기록 → 풀에 담기 (jobId 배열, 중복 제거) |
| `saveAdminPushRotation` | 슬롯·환경·on/off·호라이즌 저장 |
| `planAdminPushRotationNow` | 수동 재배정 ("지금 다시 채우기") |
| `reshuffleAdminPushRotation` | 잔여 덱 재셔플 + 미래 pending 재배정 |
| `rerollAdminScheduledPush` | 예약 1건만 다른 메시지로 교체 |

### Scheduled

| 이름 | 주기 | 역할 |
|---|---|---|
| `planAdminPushRotations` | 매일 03:10 KST | 호라이즌 유지 |
| `processScheduledAdminPushes` | 기존 매분 | 발송 (+ `useCount` 후처리만 추가) |

### Firestore 규칙

```
match /artifacts/{appId}/adminPushMessages/{id}   { allow read: if isAdmin(); allow write: if false; }
match /artifacts/{appId}/adminPushRotations/{id}  { allow read: if isAdmin(); allow write: if false; }
```

실제 쓰기는 둘 다 Admin SDK로만 처리한다. 덱 상태는 "한 바퀴 안 중복 없음"을 담보하는
상태이므로 클라이언트가 직접 건드릴 수 있으면 그 보장이 무너진다. 메시지 쪽도 `useCount`
같은 집계 필드가 있어 같은 이유로 막았다.

## 9. 엣지 케이스

| 상황 | 처리 |
|---|---|
| 풀이 비어 있음 | 배정 스킵 + 순환 설정 탭에 경고 배너 |
| 활성 메시지가 1개뿐 | 매번 같은 메시지. 경고만 띄우고 막지는 않음 |
| 슬롯 수 > 풀 크기 | 정상. 바퀴가 빨리 돌 뿐 |
| 크론 중복 실행 | 결정론적 문서 ID로 무해 |
| 순환을 껐다 켬 | 껐을 때 이미 배정된 미래 pending을 취소할지 물음. 기본은 유지 |
| 배정 후 슬롯 시각을 바꿈 | 새 슬롯은 채우고, 없어진 슬롯의 미래 pending은 취소 여부를 물음 |
| 시간대 | 전부 KST. 기존 `kstMillisForYmdHm` / `kstWeekdayMon1Sun7FromYmd` 재사용 |
| 발송 실패 | 기존과 동일하게 `failed`. 덱은 되돌리지 않음(이미 소비 처리) |

## 10. 구현 단계

**Phase 1 — 풀 만들기 (단독으로도 가치 있음)** — 2026-08-25 구현 완료
`adminPushMessages` 컬렉션, 메시지 풀 탭, **기록에서 선택해 담기**, 검색·필터·정렬·페이지네이션,
풀 메시지로 예약 만들기(`messageId` 출처 기록 → 발송 시 `useCount` 집계).
여기까지만 해도 "예전 메시지 골라서 재사용"이 가능하다. 기록에서 담기가 이 단계의 핵심이다.

**Phase 2 — 순환 엔진** — 2026-08-25 구현 완료
`adminPushRotations`, 덱 알고리즘, `planAdminPushRotations` 크론(매일 03:10 KST), 순환 설정 탭,
발송예정 목록의 순환 뱃지, 개별 재추첨. 이 시점에 요구사항이 전부 충족된다.

구현하며 설계에서 달라진 것 셋:

- **덱 로직은 `functions/pushRotationDeck.js` 로 분리했다.** 조용히 깨지면 실사용자에게 같은
  푸시가 두 번 나가는 자리라, Firestore 를 참조하지 않는 순수 함수로 떼어내 단위 테스트로
  못박았다 (`test/push-rotation-deck.test.mjs`). 바퀴 경계 스왑을 빼면 테스트가 실제로 깨진다.
- **`rotationSkipped` 플래그는 두지 않았다.** 취소된 예약은 문서가 `cancelled` 상태로 남고,
  배정은 "문서가 없는 슬롯만 채운다"라서 취소된 슬롯이 자동으로 다시 채워지지 않는다.
  결정론적 문서 ID 하나가 중복 방지와 취소 존중을 동시에 해준다.
- **미래 배정을 되돌릴 때는 문서를 지운다.** 쓰였던 메시지를 덱 앞쪽으로 돌려놓고 문서를
  삭제하면, 그 슬롯은 다음 배정에서 자연히 다시 채워진다. 교체 로직을 따로 쓰지 않아도 된다.
  메시지 비활성·삭제, 슬롯 변경, 재셔플이 모두 이 한 경로를 쓴다.

**Phase 3 — 운영 편의**
개별 재추첨, 잔여 재셔플, 메시지 수정 시 미래 예약 동기화, 사용 통계(메시지별 수신자수·바퀴별 이력).

- 배정 도중 메시지 1개 추가 → 잔여 구간에 들어가고 이미 배정된 건은 그대로인지 확인.
- 크론 수동 2회 연속 실행 → 예약 건수가 늘지 않는지 확인 (멱등성).

## 11.1 조회 비용 — 페이지 단위로만 읽는다 (2026-08-25 적용)

초기 구현은 화면을 열 때마다 발송 기록 **350건 + 예정 120건**을 통째로 읽었다. 목록이 쌓일수록
그대로 과금되고, 전체를 한 번에 렌더해 화면도 무거웠다. 커서 페이지네이션으로 바꿨다.

| | 이전 | 지금 |
|---|---|---|
| 화면 열기 | 두 탭 합쳐 약 470 읽기 | 보고 있는 탭 25 + 건수 1 + 마지막 예약 1 ≈ **27** |
| 탭 전환 | 0 (캐시) | 27 |
| 페이지 이동 | — | 26 |
| 풀 메시지 1건 수정 | 풀 전량 재조회 | **0** (로컬 행만 갱신) |

- 두 탭을 미리 읽어두지 않는다. 보고 있는 탭만 읽고, 전환할 때 그 탭의 첫 페이지를 가져온다.
- 페이지 크기 25, 한 건 더 읽어 다음 페이지 유무를 판단한다.
- 탭 뱃지 숫자는 `getCountFromServer` — 1000건당 1회 읽기로 과금돼 목록 조회보다 훨씬 싸다.
- 새 작성 행의 기본 일시에 쓰던 "가장 늦은 예약"은 목록 전체를 훑는 대신 1건만 따로 읽는다.
- 풀 메시지 저장·삭제는 전량 재조회 대신 로컬 캐시를 고쳐 그린다. 300개짜리 풀에서
  10건을 편집하면 3000 읽기가 나가던 자리다.
- 선택(체크박스)의 범위는 **현재 페이지**다. 라벨도 "이 페이지 전체 선택"으로 적었다.

필요한 인덱스: `adminScheduledPushes (status ASC, scheduledAt DESC)` — 발송완료 최근 순과
"가장 늦은 예약" 조회가 쓴다. 기존 `(status ASC, scheduledAt ASC)` 는 발송예정용으로 그대로 쓴다.

## 12. 확장성 — 풀이 계속 커지는 것을 전제로

개수 상한은 두지 않는다. 다만 커질수록 성격이 달라지는 지점이 셋 있다.

### 12.1 저장 한계는 사실상 없다

덱 배열이 rotation 문서 필드에 들어가므로 Firestore 문서 1MB 제한을 받는다.
문서 ID 20자 기준 `deckRemaining` + `deckServed` 를 합쳐도 **수만 개까지 여유**가 있어
실질적으로는 걸리지 않는다. 5,000개를 넘어서면 덱을 별도 문서(`.../rotations/{id}/deck/{chunk}`)로
쪼개면 되지만, 그 전에 아래 12.2가 먼저 문제가 된다.

### 12.2 진짜 문제는 "한 바퀴가 길어진다"

| 풀 크기 | 하루 2회 발송 기준 한 바퀴 |
|---|---|
| 40개 | 20일 |
| 100개 | 50일 |
| 300개 | **150일** |

중복이 안 나는 건 의도대로지만, 부작용이 하나 생긴다. **오늘 새로 쓴 메시지가 잔여 구간에
균등 삽입되면 평균적으로 바퀴의 절반 뒤에 나간다.** 300개 풀이면 두 달 넘게 안 나갈 수 있다.
계절·이벤트에 맞춰 쓴 문구라면 시점을 놓친다.

그래서 5.2의 **`newMessagePriority`** 를 기본으로 켠다. 새 메시지는 잔여 구간 전체가 아니라
**앞쪽 `priorityWindow`(기본 10)회 안에** 랜덤 삽입된다. 하루 2회면 길어도 닷새 안에 나간다.
"순서대로 다 돌기"라는 원칙은 유지하면서 신규 문구의 지연만 없앤다.

끄면 기존대로 잔여 구간 전체에 균등 삽입된다.

### 12.3 UI가 먼저 무너진다

지금 발송예정 테이블은 전체를 한 번에 렌더한다. 풀이 100개를 넘으면 이 방식으로는 버겁다.
메시지 풀 탭은 처음부터 다음을 갖춘다.

- **검색** — 제목·내용 부분 일치 (클라이언트 필터)
- **필터** — 활성/비활성, 이번 바퀴 상태(대기/배정됨/발송됨)
- **정렬** — 최근 사용순 / 사용 횟수순 / 등록순
- **페이지네이션** — 50개씩. 전체 로드가 부담이 되는 시점(대략 500개~)에는
  `orderBy(createdAt).limit()` 커서 방식으로 전환한다.

덱 상태 표시("40개 중 27개 남음")는 rotation 문서 하나만 읽으면 되므로 풀 크기와 무관하다.

### 12.4 배정 크론의 비용

`planAdminPushRotations` 는 풀 전체를 읽는 게 아니라 **덱이 비었을 때만** 활성 메시지 ID를
훑는다(바퀴당 1회). 그 외에는 rotation 문서 1건 + 슬롯 수만큼의 존재 확인만 든다.
풀 크기가 커져도 일일 비용은 거의 늘지 않는다.
