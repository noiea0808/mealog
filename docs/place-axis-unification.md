# 어디서(place) 축 통합 — 표기 정규화

작성: 2026-08-13
관련: [entry-sheet-redesign.md](entry-sheet-redesign.md) (기록 시트 재설계 — 본 문서는 그 후속)

## 0. 문제

같은 장소가 여러 표기로 쪼개져 집계된다. 7~8월 실데이터:

- 끼니 어디서 최빈값 **'우리집' 651건** — 기본 서브태그가 '우리집'이라서
- 간식 어디서 최빈값 **'집' 204건** — snackPlaceMain 칩이 '집'이라서
- 그 밖에 '집에서', '자택', '샵'/'샵에서' 등 변형 다수

같은 곳인데 차트에서 두 줄로 나오고, 예측(entry-context-predict)에서는 표기가 갈리면
최빈값 점유율이 60% 문턱을 못 넘어 **예측이 침묵**한다 (우리집 40% + 집 30% = 각각 미달).

근본 원인은 입력 어휘가 모드별로 갈렸던 것: 간식은 칩(집·사무실·카페),
끼니는 자유 텍스트 + 서브태그 기본값('우리집').

## 1. 원칙

> ### 저장된 원문은 절대 바꾸지 않는다. 정규화는 읽을 때만 한다.

사용자가 쓴 표기는 사실이다(사실-유도 원칙의 연장). '우리집'이라 쓴 기록은 영원히
'우리집'으로 남고, 타임라인·상세보기·내보내기도 원문을 보여준다.
정규화가 적용되는 곳은 **집계(차트·랭킹)와 예측(투표)** 뿐이다.

## 2. 구현

새 모듈 `js/utils/place-normalize.js`:

- `normalizePlace(raw)` — 조사 '에서' 제거 + 변형 테이블(우리집·자택·홈·home→집,
  회사·오피스→사무실). **실관측 표기만, 의미가 확실한 것만** 담는다.
  '본가'(부모님 집)·'회사식당'(구내식당과 겹침) 같은 애매한 말은 정규화하지 않는다 —
  뭉개면 데이터 오염이다.
- `dominantPlaceGroup(values)` — 정규화 그룹으로 투표하고, 그 그룹에서 **가장 흔한
  원문 표기**를 대표로 돌려준다. 예측이 사용자의 습관 어휘를 보존하게
  ('우리집'파에게는 '우리집'을 제안).

적용 지점 3곳:

| 지점 | 파일 | 효과 |
|---|---|---|
| 어디서 상세 랭킹 | charts.js `getTop10RankingsFromMeals` | 우리집+집+집에서가 한 줄로 |
| 간식 어디서 도넛 | meal-analytics-tags.js `effectiveSnackPlaceForAnalytics` | 자유 텍스트 '우리집'이 '집' 칩과 합산 |
| 어디서 예측 투표 | entry-context-predict.js `qualifiedMode(…, groupPlaces)` | 표기 갈림에도 예측 발화, 제안은 원문 대표값 |

## 3. 하지 않은 것

- **저장 시 정규화** — 원칙 1 위반. 안 한다.
- **기본 서브태그 '우리집'→'집' 교체** — 읽기 정규화로 이미 합쳐지므로 불필요한 변경.
  '우리집'의 친근한 톤도 제품 자산이다.
- **간식 어디서 예측** — 예측 줄은 아직 끼니 전용. 간식 확장은 별도 판단
  (간식 place 입력률·반복성 데이터를 본 뒤).
- **mealType(집밥/외식/배달…)과의 통합** — mealType은 장소가 아니라 식사 형태다.
  '집밥' 차트와 '집' 랭킹은 다른 질문에 답한다. 합치지 않는다.

## 4. 사전 관리

변형 테이블에 새 표기를 추가할 때의 기준:

1. 실데이터에 반복 관측될 것 (일회성 표기는 추가하지 않는다)
2. 의미가 정규 라벨과 **완전히** 같을 것 (본가≠집, 학교 앞 카페≠카페 같은 경계는 제외)
3. 추가 후 어디서 상세 랭킹에서 병합 결과를 눈으로 확인할 것
