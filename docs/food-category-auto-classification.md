# 음식 카테고리 자동 분류 — 설계

작성: 2026-08-12

## 0. 배경 (왜 하는가)

7/1~8/12 모먼트 데이터 4,177건 분석 결과:

- '무엇을' 카테고리의 **61%가 '기타'** (2,532건, 88/112명이 사용)
- 자유 텍스트(무엇을_상세)는 73%가 입력 — "밥 100 + 닭다리살 100 + 김치" 식의 품목 나열
- '기타' 최다 사용자가 최상위 헤비유저들 — 카테고리를 가장 먼저 포기한 게 코어 유저

원인 두 겹:

1. **어긋난 분류 축**: 기본 카테고리(`한식/양식/일식/중식/분식/카페`)는 외식 요리 계열 축인데,
   실사용은 집밥·다이어트 품목 나열.
2. **조용한 '기타' 폴백**: `resolveEntrySaveFields`(entry-form-state.js)가 텍스트만 있고
   칩이 없으면 `categoryResolved = '기타'`를 자동 기입. 사용자는 분류한 적이 없는데
   데이터에는 '기타'로 남는다.

목표: **사용자가 카테고리를 "입력"하지 않아도 "확인"만 하면 되게** 만든다.
텍스트에서 카테고리를 추론하고, 사용자 수정은 학습으로 되먹임한다.

## 1. 대원칙

> ### 자동 분류는 저장 경로 밖에서 돈다. 분류가 실패해도 저장은 1ms도 늦어지지 않는다.

[sync-outbox-design.md](sync-outbox-design.md) 불변식의 연장이다. 분류는 두 층으로 나뉜다:

- **1층 (클라이언트, 동기)**: 로컬 키워드 사전 매칭. 네트워크 0, 입력 중 실시간 제안.
  저장 시점엔 이미 계산돼 있는 값을 필드에 얹을 뿐이다.
- **2층 (서버, 비동기 best-effort)**: 1층이 못 잡은 기록을 Cloud Function이 나중에
  Gemini로 배치 분류해 별도 필드에 backfill. 실패하면 다음 배치에서 재시도. 아무것도 막지 않는다.

AI 호출을 기록 시트 안에 넣는 설계(입력 중 Gemini 호출 등)는 **금지**. 지연·오프라인·비용
세 가지 모두에서 진다.

## 2. 데이터 모델

moment 문서에 필드 추가 (기존 필드는 불변):

```js
{
  category: '한식',            // 기존. 이제 "사용자가 확정한 값"만 담는다
  categoryAuto: '단백질식',     // 신규. 자동 분류 결과 (1층 또는 2층이 기록)
  categorySource: 'user',      // 신규. 'user' | 'local' | 'ai' | null
}
```

- **읽기 규칙 (통계·리포트·UI 공통)**: `category(user) ?? categoryAuto ?? '미분류'`.
  헬퍼 `resolveCategory(moment)` 하나로 통일하고 각 소비처가 직접 coalesce하지 않는다.
- **'기타' 조용한 폴백 제거**: `resolveEntrySaveFields`에서 칩 미선택 시 '기타' 기입을
  중단하고 빈 값으로 저장한다. 빈 값 = "아직 분류 안 됨" = 2층 backfill 대상.
  (엑셀 내보내기 등 표시 계층에서는 빈 값을 '미분류'로 표기.)
- `categorySource` 판정: 사용자가 칩을 직접 탭했으면 `user`, 로컬 제안이 그대로
  저장됐으면 `local`, 서버 backfill이면 `ai`.

## 3. 1층 — 로컬 사전 분류기

새 모듈 `js/utils/food-classifier.js`. 의존성 없음, 순수 함수.

### 3.1 토크나이저

무엇을_상세의 실제 패턴("밥 100 + 닭다리살 100 + 김치", "소금빵,모카번,쿠키", "잠봉1/4라떼1/2")에 맞춘다:

1. 구분자 분리: `+`, `,`, `，`, 공백, 줄바꿈
2. 수량·단위 제거: `100`, `1개`, `2알`, `1/2`, `130그람`, `한봉`, `g`, `kg`, `숟` 등
   정규식 한 벌 (`/[\d./]+(?:개|알|봉|장|조각|숟|그람|g|kg|ml|cc)?$/` 계열)
3. 남은 토큰을 소문자·trim

### 3.2 사전 구조와 매칭

```js
// 전역 사전 — 정적 데이터, 코드와 분리된 모듈로
export const FOOD_KEYWORDS = {
  '단백질식': ['계란', '달걀', '닭가슴살', '닭찌', '쉐이크', '프로틴', '두부', '반숙란', ...],
  '밥/한상':  ['밥', '잡곡밥', '김치', '찌개', '국', '나물', '반찬', '제육', ...],
  '면':       ['라면', '국수', '파스타', '우동', '칼국수', '냉면', ...],
  '빵/샌드위치': ['빵', '토스트', '샌드위치', '베이글', '소금빵', '와플', ...],
  '샐러드':   ['샐러드', '채소', '야채', '방토', '방울토마토', '오이', '양배추', ...],
  '과일':     ['사과', '수박', '복숭아', '바나나', '과일', '견과', ...],
  '커피/음료': ['커피', '아메리카노', '라떼', '착즙', '우유', '요거트', ...],
  '간식/디저트': ['쿠키', '케이크', '아이스크림', '과자', '초코', '모찌', ...],
};
```

- 매칭: 토큰이 키워드를 **포함**하면 해당 카테고리에 1표 (부분일치 — "닭다리살"이 "닭" 아닌
  "닭다리살"/"닭가슴살" 수준의 구체 키워드에 걸리도록 키워드는 2글자 이상 구체어 위주로).
- 집계: 최다 득표 카테고리 채택. **2위가 1위의 절반 이상 득표하면 복수 제안**
  (예: "소금빵+아메리카노" → 빵/샌드위치 + 커피/음료).
- 0표면 제안 없음 → 저장 시 categoryAuto 비움 → 2층 대상.

개인 사전이 전역 사전보다 **우선** 매칭된다 (§5).

### 3.3 카테고리 축 개편과의 관계

위 사전의 키는 새 축(식사 형태 기반)이다. 축 개편 자체는 별도 제품 결정이지만,
**분류기는 처음부터 새 축으로 만든다.** 기존 축(한식/양식/...)으로 만들면 어차피 다시 만든다.
기존 `category` 값과의 호환은 읽기 계층에서 매핑 테이블 하나로 흡수한다
(`한식→밥/한상`, `카페→커피/음료`, ...).

## 4. 1층 — UX

기록 시트(entry-and-core.js)의 whatInput에 debounce 300ms 리스너:

1. 입력 텍스트 → `classify()` → 제안 카테고리 0~2개
2. 제안된 칩을 **자동 제안 상태**로 표시 — 선택(active)과 구별되는 스타일
   (점선 테두리 + ✨ 아이콘 등). 라벨: "자동 분류".
3. 사용자 행동:
   - **무시하고 저장** → 제안값이 `categoryAuto`로 저장, `categorySource='local'`
   - **제안 칩 탭** → 확정. `category`에 저장, `categorySource='user'`
   - **다른 칩 탭** → 교정. 그 값이 `category`, `categorySource='user'` + 개인 사전 학습(§5)
   - **제안 ✕ 탭** → 거부. 아무 카테고리 없이 저장(2층도 건너뛰도록 플래그)
4. 제안 계산은 순수 동기 함수라 저장 버튼과 아무 상호작용 없음. 분류기 에러는
   try/catch로 삼키고 제안만 생략 (저장에 영향 주는 throw 금지).

## 5. 개인 사전 학습

교정이 일어날 때(제안 A → 사용자가 B 선택) 이번 입력의 토큰들을 사용자 설정에 기록:

```js
// userSettings에 추가 — favoriteSubTags와 같은 디바운스 저장 경로 재사용
personalFoodKeywords: {
  '단백질식': ['닭찌', '방토'],   // 이 사용자가 B로 교정했을 때의 토큰
}
```

- 분류 시 개인 사전 먼저, 전역 사전 나중. 같은 토큰이 양쪽에 있으면 개인이 이긴다.
- 저장은 기존 `entry-save-subtags.js`의 설정 디바운스 저장에 편승 — 새 저장 경로를 만들지 않는다.
- 상한: 카테고리당 30개, 초과 시 오래된 것부터 제거 (최근성 갱신은 rememberCommaSeparatedSubTags 패턴 재사용).

## 6. 2층 — 서버 backfill (Cloud Function)

새 스케줄 함수 `classifyUncategorizedMoments` (예: 6시간마다):

1. 쿼리: `categorySource == null && category in (null, '', '기타') && 무엇을_상세 있음`,
   최근 7일, 최대 100건.
2. 배치 프롬프트 1회: 텍스트 목록 → JSON 배열 응답.
   `responseSchema`로 카테고리 enum 강제 (자유 생성 금지 — 파싱 실패 원천 차단).
3. 결과를 `categoryAuto` + `categorySource='ai'`로 개별 update.
   **`category`(사용자 필드)는 절대 건드리지 않는다.**
4. 신뢰성 (reliability-principles.md 대전제 준수):
   - Gemini 호출은 AbortController 30초 타임아웃으로 감싼다. SDK/fetch 내부 대기를 믿지 않는다.
   - 실패한 건은 그냥 둔다 — 다음 배치가 다시 집는다. 재시도 카운터·데드레터 없음
     (분류는 없어도 되는 데이터라 그 복잡도가 정당화 안 됨).
   - 함수 전체 실패해도 사용자 영향 0.
5. 비용: gemini-2.5-flash, 100건 배치 1회 ≈ 수천 토큰. 하루 4회 무시 가능한 수준.
   기존 `callGemini`의 per-user 레이트리밋과 무관한 서버 자체 호출.

### 6.1 과거 데이터 마이그레이션

같은 함수를 1회성 파라미터로 돌려 기존 '기타' 2,532건 backfill.
완료 후 인사이트/리포트에서 즉시 분포가 살아난다 — 사용자 행동 변화 없이 얻는 첫 성과.

## 6.2 간식 '무엇을' — 별도 축은 없다

> ### 끼니와 간식은 **기록 슬롯**이 가른다. '무엇을' 축은 형태 축 하나다.

간식 전용 사전도, 간식 전용 분류 함수도, 형태 → 간식 축 번역표도 없다. 간식에 방울토마토를
적으면 끼니와 똑같이 `채소·샐러드`가 나온다.

이렇게 오기까지 두 번 걸렸다. 처음엔 간식만 옛 축 7개(커피·베이커리…)로 번역했는데, 그
번역표가 **관문으로 동작해** 대응 이름이 없는 형태(채소·샐러드·고기·생선·밥류…)의 분류
결과를 통째로 버렸다 — "식사엔 방울토마토가 있는데 간식엔 없다". 번역표를 폴백으로 낮춰
한 번 고쳤고, 결국 축 자체를 하나로 합쳐 표를 없앴다. 축을 둘로 두는 한 같은 종류의 누락이
계속 생긴다.

- 저장은 끼니와 같은 필드 쌍(`categoryAuto`/`categorySource`)을 공유하고, 사용자 확정값은
  기존 필드(`category` / `snackType`)에 그대로 들어간다. **필드는 그대로, 축만 하나다** —
  필드 통합은 마이그레이션이 따르는 별도 문제이고, 축을 합치는 데 필요하지도 않다.
- 과거 기록의 `snackType` 원문(`베이커리` 등)은 **고치지 않는다.** 읽을 때
  `normalizeFoodForm`이 형태 축으로 맞춘다. 7개 중 6개는 이름이 이미 같고, 표기가 갈리는
  것은 `베이커리 → 베이커리/떡` 하나뿐이다(빵류인지 떡인지 값만으론 모르므로 포괄적인 쪽).
- **`snackType`에도 '기타' 조용한 폴백은 없다** (§2와 동일 규칙). 폴백이 남아 있으면
  `buildEntrySaveRecord`의 사용자 확정 판정(`userPicked`)이 항상 참이 되어 자동 분류는
  물론 사용자가 탭한 제안 확정까지 '기타'에 먹힌다 — 간식 자동 분류가 통째로 죽는다.
- 서버 backfill(`classifyMoments.js`)도 **같은 enum**을 쓴다. 여기만 옛 축을 남겨두면
  클라이언트가 잡으면 새 축, 서버가 집으면 옛 축이 들어가 한 필드에 두 축이 섞인다.
- 기본 태그도 `tags.category` · `tags.snackType` **둘 다 형태 축**이고, 관리자 화면의
  '무엇을' 편집란도 하나로 합쳤다(저장 시 두 필드에 같은 값을 쓴다). 필드를 하나로 합치는
  것은 과거 기록 마이그레이션이 따르는 별도 문제이고, 축을 통일하는 데 필요하지도 않다.
- 다만 운영 사용자는 관리자 태그 문서가 이 기본값을 덮어쓰므로, 상수만 바꿔서는 아무 변화가
  없다 — 실제 반영은 관리자가 '형태 축 불러오기' 후 저장하는 시점이다. 자동 치환을 넣지
  않은 이유는, 그 문서를 고치는 순간 전 사용자의 칩이 바뀌기 때문이다.

### 6.2.1 축 교체가 서브태그를 죽이지 않게 하는 장치

서브태그(`subTags.menu` 등)의 `parent`는 **저장 시점의 메인 칩 텍스트**다. 그래서 메인 축을
갈아끼우면(한식·양식… → 밥류·면류…) 옛 `parent`를 가진 항목이 어떤 칩과도 매칭되지 않아
사용자가 쌓아온 서브칩이 화면에서 통째로 증발한다. 데이터는 멀쩡한데 안 보이는 것이라,
**축 교체의 실질 비용이 전부 여기 몰려 있었다.**

`renderSecondary`(js/render/entry-chips.js)가 이를 흡수한다: `parent`가 **현재 메인 칩 목록에
없으면** 고아로 보고 어느 칩에서든 보여준다. 마이그레이션 없이 축을 바꿀 수 있게 하는
장치이고, 사용자가 그 칩을 다시 고르면 새 `parent`로 갱신되면서 자연히 정리된다.

## 6.3 분석 화이트리스트 (필수)

끼니 자동 분류 축(밥/한상·단백질식…)은 **사용자 태그 목록에 없는 값**이다.
`charts.js`의 `aggregateProportionData`와 `analysis-top-icons.js`의 `getAllowedTags`는
허용 목록 밖 값을 '미입력'으로 접기 때문에, 두 곳 모두에서 **사용자 태그 ∪ AUTO_CATEGORIES**
합집합을 만들어야 한다. 이 처리가 빠지면 자동 분류가 차트에서 통째로 사라진다.

간식도 **같은 합집합이 필요하다.** §6.2대로 간식은 형태 축 값으로 저장되는데 관리자 태그
문서는 아직 옛 축 7개를 담고 있으므로, `snackType` 허용 목록도
`사용자 태그 ∪ AUTO_CATEGORIES`여야 한다. 빠지면 방울토마토·삶은계란 간식이 차트에서
'미입력'으로 접힌다. (옛 값은 `normalizeFoodForm`이 새 축으로 맞춰 통과시킨다.)

| 지표 | 정의 | 목표 |
|---|---|---|
| 제안 적중률 | 제안 노출 대비 (무시 저장 + 제안 탭) 비율 | 80%+ |
| 교정률 | 제안 노출 대비 다른 칩 선택 비율 | 15% 미만 |
| 미분류율 | 주간 신규 기록 중 category+categoryAuto 모두 빈 비율 | 10% 미만 (현 '기타' 61% 대비) |

교정률이 높은 카테고리는 전역 사전 보강 대상 — 2층 로그에서 (텍스트, 교정 전/후) 쌍을 추출해
사전을 주기적으로 갱신한다.

## 8. 단계별 적용

| 단계 | 내용 | 범위 | 리스크 |
|---|---|---|---|
| 1 | `food-classifier.js` + 제안 UI + `categoryAuto/Source` 필드 + '기타' 폴백 제거 | 클라이언트만 | 낮음 — 저장 경로는 필드 추가뿐 |
| 2 | `classifyUncategorizedMoments` + 과거 데이터 backfill | Functions | 낮음 — 격리된 best-effort |
| 3 | 개인 사전 학습 | 클라이언트 | 낮음 |
| 4 | 카테고리 축 개편 — 끼니·간식 '무엇을'을 형태 축 하나로 (§6.2) | 코드 완료, **미배포** | 중간 — 반영 시점은 관리자 태그 갱신 |

1단계만으로도 "타이핑하면 칩이 알아서 켜져 있는" 경험이 완성된다. 2단계는 1단계가 못 잡는
꼬리를 청소하고, 과거 데이터를 살린다.

4단계는 "제품 결정 필요"로 미뤄져 있었는데, 실제로 막고 있던 것은 결정이 아니라 §6.2.1의
서브태그 문제였다. 그 장치가 생기면서 마이그레이션 없이 축을 바꿀 수 있게 됐다.
코드는 끝났고 남은 것은 반영뿐이다:

1. `functions/` 배포 (classifyMoments 축 통일, mealStats 의 `categoryAuto` 집계)
2. 관리자 화면 → 태그 → '무엇을' → **형태 축 불러오기** → 저장
   (이 순간부터 전 사용자 칩이 바뀐다 — 그 전까지는 아무 변화가 없다)

그 사이를 메우려고 **형태 축 파일럿**(계정 단위 스위치)을 두었다. 등록된 uid만 새 축으로
칩·분석이 돌고 나머지 사용자는 전혀 영향받지 않는다. 켜는 법과 전환 순서, 전환 후 지울
임시 코드 목록은 [food-axis-rollout.md](food-axis-rollout.md) 에 있다.

## 9. 하지 않는 것

- 입력 중 실시간 AI 호출 (지연·오프라인·비용 — §1)
- 저장 경로에서의 분류 실패 전파 (분류는 언제나 optional)
- 사용자 확정값(`category`) 자동 덮어쓰기 — `user`가 최종, 어떤 자동화도 못 이긴다
- 영양소·칼로리 추정 — 별개 문제, 이 설계의 범위 밖
