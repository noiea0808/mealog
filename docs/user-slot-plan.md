# 사용자 슬롯 설계 — 화면의 슬롯과 집계의 슬롯을 가른다

작성: 2026-08-29 · **0~4단계 구현 완료** (staging, 같은 날)
구현: `js/utils/slot-plan.js`(순수 계층) · `js/utils/slot-view.js`(브라우저 어댑터) ·
`js/modals/slot-plan-settings.js`(설정 시트) · 테스트 `test/slot-plan.test.mjs`
관련: [entry-axes-and-tags-direction.md](entry-axes-and-tags-direction.md),
[admin-local-mirror.md](admin-local-mirror.md), [sync-outbox-design.md](sync-outbox-design.md)

## 0. 문제

사람마다 하루의 리듬이 다르다. 지금 슬롯은 일곱 개 고정이다
(`js/constants.js` `SLOTS`). 2교대 근무자에게 '아침/점심/저녁'은 거짓말이고,
간식을 안 먹는 사람에겐 네 칸이 늘 비어 있다. 반대로 술자리 2차·야식을
따로 남기고 싶은 사람에겐 칸이 모자란다.

그런데 `slotId` 는 코드 376곳에서 쓰인다. Functions 의 식단분석
(`functions/index.js` `DIET_SLOT_ORDER`), 관리자 통계(`functions/mealStats.js`),
분석 탭 차트(`js/analytics/charts.js`), 관리자 미러 집계까지 전부 이 일곱 개를
축으로 센다. **사용자가 슬롯을 늘리면 이 축이 무너진다.**

## 1. 대전제 — 두 층으로 가른다

| 층 | 이름 | 누가 정하나 | 값 | 어디에 쓰나 |
|---|---|---|---|---|
| 집계축 | **기준 슬롯** (base) | 우리 | 현행 7개 고정 | Functions·통계·관리자·분석 |
| 표시축 | **사용자 슬롯** (user slot) | 사용자 | 최대 12개, 이름 자유 | 피커·타임라인 제목·공유카드 |

**불변식 1.** 모든 사용자 슬롯은 정확히 하나의 기준 슬롯에 속한다.
**불변식 2.** `meals.slotId` 는 지금과 똑같이 기준 슬롯 7개 중 하나다. 영원히.
**불변식 3.** 사용자 슬롯을 모르는 코드는 `slotId` 만 읽고도 정상 동작한다.
서버·Functions·관리자는 사용자 슬롯 필드를 **읽지 않는다**.

이 셋이 "화면에 반영되는 것과 서버에 반영되는 건 따로 논다"의 구현이다.
사용자 슬롯은 순수한 표시 계층이며, 지우면 앱은 현행으로 되돌아간다.

## 2. 데이터 모델

### 2.1 `userSettings.slotPlan` — 날짜 키 맵

```js
slotPlan: {
    schema: 1,
    revisions: {
        // 키 = effectiveFrom (YYYY-MM-DD). 배열이 아니라 맵인 이유는 §5.2
        '2026-09-01': {
            createdAt: 1756...,
            slots: [
                { key: 's1a2', base: 'morning', label: '아침', enabled: true },
                { key: 's1a3', base: 'lunch',   label: '점심', enabled: true },
                { key: 's1a4', base: 'dinner',  label: '저녁', enabled: true },
                { key: 's1a5', base: 'night',   label: '야식', enabled: true },
                { key: 's1a6', base: 'night',   label: '2차',  enabled: true }
            ]
        }
    }
}
```

- **어떤 날짜의 유효 개정판** = `effectiveFrom <= date` 인 것 중 가장 늦은 것.
  하나도 없으면 내장 기본값(현행 7슬롯).
- `key` 는 사용자 문서 안에서 **영구 유일**하다. 재사용 금지 — 이름을 바꿔도,
  슬롯을 지웠다 다시 만들어도 옛 key 는 다시 쓰지 않는다. §3 의 이름 보존이
  여기에 기댄다.
- **한 개정판 안의 슬롯 상한 12개.** 두 열 × 6줄이면 스크롤 없이 한 화면에
  들어간다. 개정판 **수**의 상한과는 다른 이야기다 — 그건 §5.6.
- 개정판은 지우지 않는다. 대신 **안 쌓이게 막는다** (§5.6).

설정을 바꾸면 기존 개정판을 고치는 게 아니라 **그 날짜 키를 새로 넣는다.**
이것이 "정해지면 그 날짜 이후로 적용"이다.

### 2.2 `meals.slotKey` — 새 필드 하나

- `slotId`: 기존 그대로. 필수. = 사용자 슬롯의 `base`
- `slotKey`: 신규. 선택. 기록 당시 고른 사용자 슬롯의 `key`

같은 base 를 쓰는 사용자 슬롯이 둘 이상일 때(야식·2차) 어느 쪽인지 가르는
유일한 값이다. 없으면 base 의 첫 슬롯으로 접힌다 — 옛 기록과 옛 클라이언트가
그대로 도는 이유.

### 2.3 순서는 사용자가 정한다 — base 는 집계 축만 맡는다

**표시 순서 = `slots` 배열의 순서.** 사용자가 설정 시트에서 끌어 바꾼다.

처음엔 "순서는 base 의 시간축이 정하고 같은 base 안에서만 사용자가 정한다"로
잡았다가 뒤집었다. 반례가 명확하다:

> 야식을 **끼니로 여기는 사람.** 저녁 19시 → 밤 간식 21시 → 야식 23시.
> 집계로는 야식이 `dinner` 가 맞고, 순서로는 `night` 간식 뒤가 맞다.

`base` 가 두 가지 일을 겸하고 있었다 — **집계 축**이면서 동시에 **시간 순서**.
같은 base 끼리 붙어 있어야 한다는 제약이 위 배치를 불가능하게 만든다.
둘을 가르면 제약이 사라진다. `base` 는 집계 축 하나만 맡는다.

자유 정렬을 막았던 원래 근거("피커와 타임라인이 어긋난다")는 성립하지 않는다.
지금 타임라인은 `SLOTS.forEach` 로 돌아 **배열 순서가 곧 표시 순서**다
(`js/render/timeline.js:1620`). 타임라인도 같은 개정판을 순회하게 만들면
두 화면이 같은 목록을 읽으므로 어긋날 수가 없다. 1단계의 작업 범위가
"라벨 해석"에서 "라벨 + 순서"로 넓어진다.

'야식'을 '아침' 위에 올리는 모순 구성도 가능해지지만 막지 않는다. 사용자가
만든 자기 목록이고, 두 화면이 똑같이 그 순서를 따르므로 앱은 일관된다.

## 3. 읽기 경로 — 이름은 절대 잃지 않는다

```
resolveSlotView(record) →
  1. record.slotKey 를 **모든 개정판에서** 찾는다   ← 날짜로 좁히지 않는다
  2. ||= 그 날짜 유효 개정판에서 base === record.slotId 인 슬롯 중
        **key 가 가장 오래된 것**                    ← 표시 순서 기준이 아니다 (아래)
  3. ||= SLOTS 의 기본 정의                          ← 폴백은 반드시 성공한다
  → { label, base, icon, tint }
```

**2번이 "첫 번째"가 아니라 "가장 오래된 key"인 이유** — 순서를 사용자가 끌 수
있게 되면서(§2.3) 생긴 구멍이다. 폴백을 표시 순서 기준으로 잡으면, base 가 같은
'야식'·'2차'의 순서를 바꾸는 순간 **`slotKey` 없는 옛 기록들의 이름이 눈앞에서
'야식'→'2차'로 갈아탄다.** key 는 시간 기반이라 가장 오래된 key = 그 base 의
원본 슬롯이고, 순서를 아무리 끌어도 귀속이 흔들리지 않는다. 피커의 건수 배지도
같은 규칙으로 센다 — `slotKey` 없는 기록은 원본 슬롯의 건수다.

**정렬 위치도 같은 폴백을 쓴다.** 타임라인은 그 날짜 유효 개정판의 배열 순서로
슬롯을 늘어놓는데, 기록의 slotKey 가 그 개정판에 없으면(나중에 만든 슬롯의 과거
기록 등) base 가 같은 원본 슬롯의 자리에 끼운다. 라벨과 위치가 항상 같은 슬롯을
가리키게 — 해석기 하나가 둘 다 답한다.

**1번이 날짜로 좁히지 않는 것이 핵심이다.** 좁히면 이런 일이 난다: 오늘 아침
'2차'로 저장한 기록이 있는데 오늘 오후에 '2차' 슬롯을 지우면, 새 개정판의
`effectiveFrom` 이 오늘이라 그 기록이 눈앞에서 '저녁 후 간식'으로 바뀐다.
key 는 영구 유일하므로 전체에서 찾으면 **한 번 붙은 이름은 영원히 유지된다.**

날짜별 개정판은 **"피커에 무엇을 띄울지"만** 정한다. 이름 해석은 key 가 한다.
이 분리 덕에 "지운 슬롯의 과거 기록을 어떻게 보여줄까"는 결정할 필요가 없어진다.

**불변식 4. 어떤 설정으로도 기존 기록이 화면에서 사라지지 않는다.**
`enabled: false` 는 **피커에서만** 숨기는 플래그다. 이걸 렌더 필터로 쓰는 순간
사용자는 자기 기록을 잃는다.

서수 규칙: 지금 `getEntrySlotTitleLabel` 은 같은 슬롯 다건에 '점심2'를 붙인다
(`js/modals/entry-modal-header.js`). `slotKey` 가 있어 이름이 이미 갈린 경우엔
서수를 붙이지 않고, 없을 때만 현행대로 붙인다.

### 3.1 이름 수정은 소급, 구성 변경은 비소급

| 편집 | key | 처리 | 과거 기록의 이름 |
|---|---|---|---|
| 이름만 고침 | 그대로 | 모든 개정판의 그 key 라벨을 일괄 갱신 | **바뀐다** |
| 슬롯 추가·삭제·사용토글 | 새 key / 제거 | 오늘 날짜 개정판 추가 | 그대로 |

판단 기준은 key 다 — key 가 유지되면 "같은 슬롯의 다른 이름", 새로 생기면
"다른 슬롯". 오타를 고쳤는데 과거가 영원히 오타를 달고 있는 일이 없고,
UI 도 단순해진다(이름 편집에는 "오늘부터 적용" 안내를 띄우지 않는다).

## 4. 화면

### 4.1 슬롯 피커 — 한 열에서 두 열로

지금 행은 `아이콘 → 라벨 → 건수 → 꺾쇠`가 가로로 늘어서 있어서, 두 열로 쪼개면
가로 공간이 안 나온다. **행을 카드로 바꾼다.**

```
┌──────────────┐ ┌──────────────┐
│ ◉            │ │ ◉            │
│ 아침          │ │ 오전 간식     │
│ 1건 · 추가    │ │ 아직 없음     │
└──────────────┘ └──────────────┘
        ── 하루 소감 (전체 폭) ──
```

- `.entry-slot-picker__group` 을 `grid-template-columns: repeat(2, minmax(0,1fr))`,
  `gap: 0.5rem`. 아이템의 `margin-bottom` 은 gap 이 대신한다.
- 꺾쇠 제거 — 카드 격자에서는 중복이다.
- **하루 소감은 `grid-column: 1 / -1`** 로 전체 폭. 슬롯이 아니라는 읽힘을 유지한다.
- 라벨의 `white-space: nowrap` 을 풀고 2줄 클램프. 사용자가 12자 이름을 붙일 수
  있으므로 필수다.
- 패널 폭은 건드리지 않는다. `--shell-float-width`(최대 28rem)의 `!important` 가
  `max-w-[22rem]` 을 이미 덮고 있어(`css/style.css:16369`) 실폭 408px,
  열당 200px 이 나온다. 375px 기기에서도 열당 147px.
- 목록은 **피커가 열린 날짜**의 유효 개정판에서 `enabled` 인 것만.
- 헤더 우측(`기록 추가 · 8월 29일` 줄 끝)에 톱니 → 슬롯 설정 시트.

### 4.2 슬롯 설정 시트 (신규)

```
[ 아침        ] 아침         ●사용
[ 점심        ] 점심         ●사용
[ 저녁        ] 저녁         ●사용
[ 저녁 후     ] 야식         ●사용
[ 저녁 후     ] 2차          ○사용 안 함
                              + 슬롯 추가   (5/12)

사용 여부 변경은 8월 29일 기록부터 적용됩니다.
지난 기록은 그대로 남습니다.                  [기본값으로]
```

- 이름: 인라인 편집, 12자 이내. 저장 즉시 소급 반영(§3.1).
- 사용 토글 / 삭제 / **순서 끌기** → 오늘 날짜 개정판 추가.
- 꺼진 슬롯은 목록 제자리에 회색으로 남긴다. 아래 "사용 안 함" 구역으로 모으지
  않는다 — 시간 순서가 곧 목록의 뼈대이므로 자리를 옮기면 읽는 감각이 깨진다.

**슬롯을 더하는 길은 둘, 복제가 먼저다.**

| 길 | 동작 | base |
|---|---|---|
| **복제** (기본) | 기존 슬롯의 ⋯ → "복제" → 이름만 새로 | 원본에서 상속 |
| 새로 만들기 | "언제쯤인가요?" 7택 → 이름 | 고른 시간대 |

복제가 기본인 이유: "저녁 슬롯을 복사해서 야식이라고 이름 붙인다"가 사용자가
실제로 하는 생각이고, 이 경로에서는 **집계 축 얘기를 한 번도 안 해도 된다.**
"새로 만들기"는 원본이 없을 때만 쓰는 뒷길이며, 이때도 base 를 시간대 질문
(아침 전 / 아침 / 오전 / 점심 / 오후 / 저녁 / 저녁 후)으로 포장한다.

### 4.3 두 번째 진입점

설정 모달에도 같은 시트를 여는 행을 둔다. 피커 톱니만으로는 발견되지 않는다.

## 5. 저장·동기화

### 5.1 slotPlan 은 부분 손상이 치명적이다

`saveSettings` 는 기존 문서 읽기에 실패하면 새 값으로 그냥 진행한다
(`js/db/ops.js:487` 주석). slotPlan 이 그렇게 리셋되면 **사용자가 붙인 모든
이름과 개정 이력이 한 번에 날아간다.**

- slotPlan 은 전용 저장 함수로 분리하고, **읽기에 실패하면 저장을 중단**한다.
  기본값으로 덮지 않는다 (`stripGateRegressions` 와 같은 성격의 보호).
- 기본값 병합에서 slotPlan 은 "없으면 만들지 않는다". 빈 맵과 기본값을 구분한다.

### 5.2 왜 배열이 아니라 맵인가 ★

설정도 아웃박스를 탄다(`js/db/ops.js:444`, `CLASS_CONTENT`, `mergePayload: true`).
그런데 병합 방식이 문제다:

- 아웃박스의 `deepMergePlain`(`js/utils/outbox-store.js:139`) — 맵은 재귀 병합,
  **배열은 통째로 교체**
- Firestore `setDoc(..., { merge: true })` — 똑같이 **배열은 통째로 교체**

`revisions` 가 배열이면, 두 기기가 각자 개정판을 추가했을 때 나중에 도착한
쪽이 앞의 것을 통째로 지운다. 날짜 키 맵이면 두 필드가 각각 병합돼 **둘 다
살아남는다.** 나중에 고치기 비싼 구조 결정이라 여기서 정한다.

### 5.3 충돌 규칙은 하나

> **같은 날짜는 마지막 편집이 이긴다.**

맵 키가 날짜라 저절로 그렇게 된다. 설명 가능한 규칙 하나면 충분하다.

### 5.4 도착 순서는 강제하지 않는다

기록(meals)과 설정(settings)은 별개 아웃박스 항목이라 도착 순서가 정해지지
않는다. 기록이 먼저 오면 그 `slotKey` 를 모르는 상태이므로 §3 의 폴백으로 기준
슬롯 이름이 뜨고, 설정이 도착하면 저절로 교정된다.

**폴백이 절대 실패하지 않으므로 순서 보장 장치가 필요 없다.** 순서를 맞추는
기계장치를 새로 넣지 않는다 — 그게 아웃박스가 13번 수정된 패턴이다.

### 5.5 시계 방어

`effectiveFrom` 은 기기 로컬 날짜다. 시계가 틀어진 기기가 2030년 개정판을
쓰면 그 뒤로 영원히 그것이 유효 개정판이 된다.

- 쓸 때: 로컬 오늘로 고정. 다른 값을 받지 않는다.
- 읽을 때: `오늘 + 1일` 보다 미래인 개정판은 무시한다.

### 5.6 개정판은 지우지 않고, 안 쌓이게 막는다

개정판 **수**에는 상한을 두지 않는다. 삭제는 `deleteField` 센티널이 필요해
경합에 약하고(§5.3의 "마지막 편집이 이긴다"와 충돌한다), 무엇보다 사용자가
붙인 이름의 이력이다.

대신 성장 자체를 막는다:

- **직전 개정판과 슬롯 목록이 완전히 같으면 새 개정판을 쓰지 않는다.**
  토글을 껐다 켜서 원상복구하면 아무 일도 일어나지 않는다. 실제 성장의
  대부분이 여기서 죽는다.
- 맵 키가 날짜라 **하루 최대 한 개**다(§5.3).

그래도 감시는 필요하다. `userSettings` 는 `dailyComments`(하루 소감 본문·사진
메타)와 **같은 문서**를 쓰므로 1MB 한도가 남 얘기가 아니다. 개정판 12슬롯 한
개가 약 340B 이니:

| 개정판 수 | 크기 | 판단 |
|---|---|---|
| 24 | ~8KB | 평범한 사용자의 현실적 상한 |
| 200 | ~70KB | 진단 로그(`diag`) 한 줄 남긴다 |
| 3,000 | ~1MB | 매일 구성을 바꿔야 10년 — 실제로 오면 그때 데이터를 보고 결정 |

지금 정하는 건 **200에서 로그를 남긴다**까지다. 가지치기 정책을 미리 만들지
않는다 — 실측 없이 만든 삭제 코드가 이 서브시스템에서 제일 위험하다.

## 6. 서버·통계에 미치는 영향

없다. `slotId` 축이 그대로이므로 Functions·미러·관리자 코드는 한 줄도 안 바뀐다.

한 가지만 남는다: 사용자가 '점심'을 꺼도 통계에서는 "점심 기록 0건"으로 보이고,
**안 쓰는 것과 안 먹은 것이 구분되지 않는다.** 지금도 같은 한계이고 이번 범위
밖이다. 필요해지면 관리자 미러가 이미 읽는 `config/settings` 에 slotPlan 이
들어 있으므로 "활성 슬롯 수"를 분모로 쓰는 길이 열려 있다.

## 8. 남은 위험

1. **`enabled: false` 를 렌더 필터로 쓰는 실수.** 불변식 4를 깨는 유일한 경로다.
   1단계에서 `resolveSlotView` 에 "필터링용 아님" 주석을 박고, 타임라인 렌더가
   plan 을 아예 안 보게 만든다.
2. **`key` 재사용.** 슬롯을 지웠다 같은 이름으로 다시 만들 때 옛 key 를 재사용하면
   과거 기록이 새 슬롯에 딸려온다. 생성기는 시간 기반 + 랜덤으로 만들고,
   재사용 경로를 아예 두지 않는다.
3. **slotPlan 저장이 `saveSettings` 전체를 태운다.** 슬롯 이름 하나 고치는데
   닉네임 클레임 트랜잭션까지 도는 경로다. 0단계에서 실제 호출 비용을 재고,
   필요하면 slotPlan 전용 경량 경로를 검토한다.
4. **클라이언트 혼재 기간.** 웹은 main, APK 는 staging 을 받는다 — 이 기능이
   staging 에만 있는 동안 웹에서 저장한 기록은 `slotKey` 가 없다. 폴백 덕에
   깨지진 않지만, 같은 base 다중 슬롯 사용자가 웹에서 저장하면 전부 원본
   슬롯으로 귀속된다. 4단계는 **웹(main) 배포와 묶어서** 내보낸다.
5. **퀵입력의 하드코딩 잔재.** ~~2단계에서 교체~~ → 전수 확인 결과
   `resolveQuickEntrySlotId`·`getTimeBasedMainSlotId` 는 **사용처가 없는 죽은
   코드**였다(정의만 존재). 나머지 하드코딩 전수표:

   | 위치 | 하드코딩 | 판정 |
   |---|---|---|
   | `js/admin/*`, `functions/*` | MEAL/SNACK_SLOTS 등 | 그대로 — base 집계축 (§1) |
   | `js/analytics/*` (charts·insight·kpi·tags) | main/snack id 집합 | 그대로 — base 축 분석, 5단계에서 선택 |
   | `js/utils/diet-record-score.js` | MAIN_SLOT_IDS | 그대로 — 점수 계약은 base |
   | `js/utils/meal-delete-optimistic.js:9` | main 집합 | 그대로 — type 판정 = base |
   | `entry-modal-header.js` TINTED_SLOTS | morning/lunch/dinner | 그대로 — 헤더 테마 = base (야식도 저녁 테마가 맞다) |
   | `entry-quick-open.js` | QUICK_MAIN_SLOT_IDS | 죽은 코드 — 필요 시 삭제 |

한편 확인해서 **문제없음으로 닫은 것**: meals 쓰기 규칙(firestore.rules:64)에
`hasOnly` 필드 제한이 없고, `saveArtifactUserMeal` Callable 도 필드 화이트리스트
없이 통과시킨다 — `slotKey` 는 규칙·프록시 양쪽 다 수정 없이 저장된다. 기록
시트의 서식(본식/간식 폼)은 base 의 type 을 따르므로, 저녁을 복제한 '야식'은
자연히 본식 폼을 받는다 — 야식을 끼니로 여기는 사용자의 기대와 일치한다.
