# 사용자 슬롯 설계 — 화면의 슬롯과 집계의 슬롯을 가른다

작성: 2026-08-29 · **0~4단계 구현 완료** (staging, 같은 날)
구현: `js/utils/slot-plan.js`(순수 계층) · `js/utils/slot-view.js`(브라우저 어댑터) ·
`js/modals/slot-plan-settings.js`(설정 시트) · 테스트 `test/slot-plan.test.mjs`
관련: [entry-axes-and-tags-direction.md](entry-axes-and-tags-direction.md),
[admin-local-mirror.md](admin-local-mirror.md), [sync-outbox-design.md](sync-outbox-design.md)

## 0. 문제

사람마다 하루의 리듬이 다르다. 지금 슬롯은 일곱 개 고정이다
(`js/constants.js` `SLOTS`). 2교대 근무자에게 '아침/점심/저녁'은 거짓말이고,
간식을 안 먹는 사람에겐 네 칸이 늘 비어 있다. 반대로 술자리 2차·야식을
따로 남기고 싶은 사람에겐 칸이 모자란다.

그런데 `slotId` 는 코드 376곳에서 쓰인다. Functions 의 식단분석
(`functions/index.js` `DIET_SLOT_ORDER`), 관리자 통계(`functions/mealStats.js`),
분석 탭 차트(`js/analytics/charts.js`), 관리자 미러 집계까지 전부 이 일곱 개를
축으로 센다. **사용자가 슬롯을 늘리면 이 축이 무너진다.**

## 1. 대전제 — 두 층으로 가른다

| 층 | 이름 | 누가 정하나 | 값 | 어디에 쓰나 |
|---|---|---|---|---|
| 집계축 | **기준 슬롯** (base) | 우리 | 현행 7개 고정 | Functions·통계·관리자·분석 |
| 표시축 | **사용자 슬롯** (user slot) | 사용자 | 사용 중 최대 12개, 이름 자유 | 피커·타임라인 제목·공유카드 |

**불변식 1.** 모든 사용자 슬롯은 정확히 하나의 기준 슬롯에 속한다.
**불변식 2.** `meals.slotId` 는 지금과 똑같이 기준 슬롯 7개 중 하나다. 영원히.
**불변식 3.** 사용자 슬롯을 모르는 코드는 `slotId` 만 읽고도 정상 동작한다.
서버·Functions·관리자는 사용자 슬롯 필드를 **읽지 않는다**.

이 셋이 "화면에 반영되는 것과 서버에 반영되는 건 따로 논다"의 구현이다.
사용자 슬롯은 순수한 표시 계층이며, 지우면 앱은 현행으로 되돌아간다.

## 2. 데이터 모델

### 2.1 `userSettings.slotPlan` — 날짜 키 맵

```js
slotPlan: {
    schema: 1,
    revisions: {
        // 키 = effectiveFrom (YYYY-MM-DD). 배열이 아니라 맵인 이유는 §5.2
        '2026-09-01': {
            createdAt: 1756...,
            slots: [
                { key: 's1a2', base: 'morning', label: '아침', enabled: true },
                { key: 's1a3', base: 'lunch',   label: '점심', enabled: true },
                { key: 's1a4', base: 'dinner',  label: '저녁', enabled: true },
                { key: 's1a5', base: 'night',   label: '야식', enabled: true },
                { key: 's1a6', base: 'night',   label: '2차',  enabled: true }
            ]
        }
    },
    // 개정판 어디에도 안 남은 슬롯의 이름 (§3.2). 없으면 필드 자체가 없다
    retired: { 's1a9': { base: 'dinner', label: '한잔' } }
}
```

- **어떤 날짜의 유효 개정판** = `effectiveFrom <= date` 인 것 중 가장 늦은 것.
  하나도 없으면 내장 기본값(현행 7슬롯).
- `key` 는 사용자 문서 안에서 **영구 유일**하다. 재사용 금지 — 이름을 바꿔도
  key 는 그대로고, 복제는 언제나 새 key 를 받는다. §3 의 이름
  보존이 여기에 기댄다. 기본 7슬롯의 key 는 §2.4 참고.
- **상한은 둘이고 세는 대상이 다르다.** `MAX_ENABLED_SLOTS = 12` 는 **사용 중인**
  슬롯 수(두 열 × 6줄 = 한 화면), `MAX_SLOTS_PER_REVISION = 24` 는 해제분까지
  담는 저장 배열 총 길이. 해제한 원본이 목록에 남는데(§4.2.1) 그게 피커
  상한을 먹으면 안 된다. 개정판 **수**의 상한은 또 다른
  이야기 — 그건 §5.6.
- 개정판은 지우지 않는다. 대신 **안 쌓이게 막는다** (§5.6).

설정을 바꾸면 기존 개정판을 고치는 게 아니라 **그 날짜 키를 새로 넣는다.**
이것이 "정해지면 그 날짜 이후로 적용"이다.

### 2.4 기본 7슬롯의 key 는 결정적이다

`defaultSlotKey(base)` = `'000000000' + base` → `'000000000morning'`.

처음엔 `key: null` 을 "아직 저장 안 된 기본 슬롯" 표식으로 썼다. 그 하나가
**규칙 셋**을 낳았다:

| 낳은 규칙 | 왜 필요했나 |
|---|---|
| key 구체화를 **시트 여는 시점**에 | 저장 때 하면 복제본 key 가 원본보다 오래돼(복제 시각 < 저장 시각) 원본 판정이 뒤집힌다 |
| `slotsEqual` **비대칭 비교** | 구체화만으로 개정판이 생기면 안 되니, 저장된 쪽 null key 를 와일드카드로 |
| `adoptExistingKeys` | 과거 날짜 편집 시 같은 '아침'이 날짜마다 다른 슬롯이 되는 것 방지 |

셋 다 **자초한 것**이었다. 기본 key 를 base 에서 결정적으로 만들면 `null` 이
아예 없어지고 셋이 함께 사라진다. **어느 날짜에서 읽어도 '아침'은 늘 같은
슬롯**이라는 사실이 코드가 아니라 값의 성질이 된다.

접두사가 0 아홉 개인 이유: 생성 key 의 타임스탬프(base36)는 2059년까지 8자라
한 자리만 0 으로 채워지고(`'0mtek…'`), 그 뒤로는 9자가 되며 `'1'` 이상으로
시작한다. 어느 쪽이든 문자열 비교에서 기본 슬롯이 먼저 온다 —
**"가장 오래된 key = 원본"(§3)이 영원히 성립한다.**

기본 key 끼리의 정렬 순서(base 이름 알파벳순)는 상관없다. base 마다 하나뿐이라
원본 판정이 흔들릴 여지가 없다.

> 남은 것 하나: `adoptLegacyKeys` 는 **결정적 key 이전에 저장된 plan** 을 위한
> 마이그레이션 심지로 `effectiveSlots` 안에 남아 있다. 호출부가 기억할 규칙이
> 아니며, 그런 plan 이 없다고 확신되면 함수째 지워도 된다.

### 2.2 `meals.slotKey` — 새 필드 하나

- `slotId`: 기존 그대로. 필수. = 사용자 슬롯의 `base`
- `slotKey`: 신규. 선택. 기록 당시 고른 사용자 슬롯의 `key`

같은 base 를 쓰는 사용자 슬롯이 둘 이상일 때(야식·2차) 어느 쪽인지 가르는
유일한 값이다. 없으면 base 의 첫 슬롯으로 접힌다 — 옛 기록과 옛 클라이언트가
그대로 도는 이유.

### 2.3 순서는 사용자가 정한다 — base 는 집계 축만 맡는다

**표시 순서 = `slots` 배열의 순서.** 사용자가 설정 시트에서 끌어 바꾼다.

처음엔 "순서는 base 의 시간축이 정하고 같은 base 안에서만 사용자가 정한다"로
잡았다가 뒤집었다. 반례가 명확하다:

> 야식을 **끼니로 여기는 사람.** 저녁 19시 → 밤 간식 21시 → 야식 23시.
> 집계로는 야식이 `dinner` 가 맞고, 순서로는 `night` 간식 뒤가 맞다.

`base` 가 두 가지 일을 겸하고 있었다 — **집계 축**이면서 동시에 **시간 순서**.
같은 base 끼리 붙어 있어야 한다는 제약이 위 배치를 불가능하게 만든다.
둘을 가르면 제약이 사라진다. `base` 는 집계 축 하나만 맡는다.

자유 정렬을 막았던 원래 근거("피커와 타임라인이 어긋난다")는 성립하지 않는다.
지금 타임라인은 `SLOTS.forEach` 로 돌아 **배열 순서가 곧 표시 순서**다
(`js/render/timeline.js:1620`). 타임라인도 같은 개정판을 순회하게 만들면
두 화면이 같은 목록을 읽으므로 어긋날 수가 없다. 1단계의 작업 범위가
"라벨 해석"에서 "라벨 + 순서"로 넓어진다.

'야식'을 '아침' 위에 올리는 모순 구성도 가능해지지만 막지 않는다. 사용자가
만든 자기 목록이고, 두 화면이 똑같이 그 순서를 따르므로 앱은 일관된다.

## 3. 읽기 경로 — 이름은 절대 잃지 않는다

```
resolveSlotView(record) →
  1. record.slotKey 를 **모든 개정판에서** 찾는다   ← 날짜로 좁히지 않는다
  2. ||= 그 날짜 유효 개정판에서 base === record.slotId 인 슬롯 중
        **key 가 가장 오래된 것**                    ← 표시 순서 기준이 아니다 (아래)
  2.5 ||= slotPlan.retired[slotKey] — 폐기된 슬롯의 이름 (§3.2)
  3. ||= SLOTS 의 기본 정의                          ← 폴백은 반드시 성공한다
  → { label, base, icon, tint }
```

**2번이 "첫 번째"가 아니라 "가장 오래된 key"인 이유** — 순서를 사용자가 끌 수
있게 되면서(§2.3) 생긴 구멍이다. 폴백을 표시 순서 기준으로 잡으면, base 가 같은
'야식'·'2차'의 순서를 바꾸는 순간 **`slotKey` 없는 옛 기록들의 이름이 눈앞에서
'야식'→'2차'로 갈아탄다.** key 는 시간 기반이라 가장 오래된 key = 그 base 의
원본 슬롯이고, 순서를 아무리 끌어도 귀속이 흔들리지 않는다. 피커의 건수 배지도
같은 규칙으로 센다 — `slotKey` 없는 기록은 원본 슬롯의 건수다.

**정렬 위치도 같은 폴백을 쓴다.** 타임라인은 그 날짜 유효 개정판의 배열 순서로
슬롯을 늘어놓는데, 기록의 slotKey 가 그 개정판에 없으면(나중에 만든 슬롯의 과거
기록 등) base 가 같은 원본 슬롯의 자리에 끼운다. 라벨과 위치가 항상 같은 슬롯을
가리키게 — 해석기 하나가 둘 다 답한다.

**1번이 날짜로 좁히지 않는 것이 핵심이다.** 피커는 **그 날짜**로 열리므로
과거 날짜에도 기록을 추가할 수 있다. 오늘 '야식' 슬롯을 만들고 어제 날짜로
야식을 적으면, 어제 개정판에는 그 key 가 없다 — 날짜로 좁히면 방금 적은 기록이
'저녁'으로 뜬다. key 는 영구 유일하므로 전 개정판에서 찾으면
**한 번 붙은 이름은 영원히 유지된다.**

날짜별 개정판은 **"피커에 무엇을 띄울지"만** 정한다. 이름 해석은 key 가 한다.
이 분리 덕에 해제한 슬롯·나중에 만든 슬롯의 기록을 어떻게 보여줄지는 결정할
필요가 없어진다 — 저절로 옳다.

**불변식 4. 어떤 설정으로도 기존 기록이 화면에서 사라지지 않는다.**
`enabled: false` 는 **피커에서만** 숨기는 플래그다. 이걸 렌더 필터로 쓰는 순간
사용자는 자기 기록을 잃는다.

설정 시트는 `userSettings.slotPlan` 만 쓴다 — `meals` 컬렉션도 `mealHistory` 도
건드리지 않는다. 슬롯을 해제하든 삭제하든 **기록을 지우는 경로 자체가 없다.**
실측(2026-08-30, 데모 계정):

| 한 일 | 기록 | 타임라인 이름 |
|---|---|---|
| 기록 있는 '아침' 해제 | 그대로 | '아침' 유지 (피커에서만 빠짐) |
| 다른 날 만든 '야식' 삭제 | 그대로 | '야식' 유지 (앞 개정판에 key 생존) |
| 같은 날 만들고 같은 날 삭제한 '2차' | 그대로 | '2차' 유지 (§3.2 `retired`) |

서수 규칙: 지금 `getEntrySlotTitleLabel` 은 같은 슬롯 다건에 '점심2'를 붙인다
(`js/modals/entry-modal-header.js`). `slotKey` 가 있어 이름이 이미 갈린 경우엔
서수를 붙이지 않고, 없을 때만 현행대로 붙인다.

### 3.2 폐기 이름 — 개정판에서 사라진 key 의 마지막 보루

§3 의 1번(전 개정판에서 key 찾기)에는 구멍이 하나 있었다. **같은 날짜 키의
개정판을 덮어쓰면** 그 사이에만 존재하던 key 가 통째로 증발한다:

1. 8/30 에 '2차'를 만들고 저장 → 8/30 개정판에 `k-cha`
2. 8/30 에 '2차'로 기록 한 건 → `meal.slotKey = k-cha`
3. 8/30 로 다시 열어 '2차' 삭제 → **8/30 개정판이 교체**되며 `k-cha` 소멸
4. 그 기록이 '저녁'으로 보인다 — "한 번 붙은 이름은 영원히 유지된다"가 깨진다

기록 자체는 무사하지만(불변식 4는 지켜진다) 약속은 약속이다. `withRevisionOn`
이 저장할 때마다 **어느 개정판에도 안 남게 되는 key** 를 이름과 함께
`slotPlan.retired` 에 옮긴다. `findSlotByKey` 는 개정판을 다 뒤진 뒤 여기를 본다.

- 다른 개정판에 살아 있으면 폐기하지 않는다 — 흔한 경우(며칠 뒤 삭제)는
  `retired` 가 아예 안 생긴다.
- 쌓이기만 하고 지우지 않는다. 슬롯 하나당 약 60B 다.
- `retired` 도 맵이라 아웃박스·Firestore 병합에서 필드별로 합쳐진다(§5.2).

### 3.1 이름 수정은 소급, 구성 변경은 비소급

| 편집 | key | 처리 | 과거 기록의 이름 |
|---|---|---|---|
| 이름만 고침 | 그대로 | 모든 개정판의 그 key 라벨을 일괄 갱신 | **바뀐다** |
| 복제·삭제·사용토글·순서 | 새 key / 제거 | 오늘 날짜 개정판 추가 | 그대로 |

판단 기준은 key 다 — key 가 유지되면 "같은 슬롯의 다른 이름", 새로 생기면
"다른 슬롯". 오타를 고쳤는데 과거가 영원히 오타를 달고 있는 일이 없고,
UI 도 단순해진다(이름 편집에는 "오늘부터 적용" 안내를 띄우지 않는다).

## 4. 화면

### 4.1 슬롯 피커 — 한 열에서 두 열로

지금 행은 `아이콘 → 라벨 → 건수 → 꺾쇠`가 가로로 늘어서 있어서, 두 열로 쪼개면
가로 공간이 안 나온다. **행을 카드로 바꾼다.**

```
┌──────────────┐ ┌──────────────┐
│      아침     │ │      저녁 후  │
│  ◉           │ │  ◉   간식     │
│      1건      │ │      아직 없음│
└──────────────┘ └──────────────┘
        ── 하루 소감 (전체 폭) ──
```

**아이콘 | (이름 / 건수)** — 아이콘은 이름과 같은 행이 아니라 **카드 높이의
중앙**에 선다. 이름이 두 줄로 접히면 아이콘이 첫 줄에 매달려 위로 쏠려 보인다.
건수에 '· 추가 가능'을 붙였다가 뺐다 — 카드를 누르면 추가된다는 건 자명하다.

**한 줄 배치(아이콘·이름·건수)는 포기했다.** 실측: 카드 안쪽 폭이 데스크톱
173px / 375px 기기 117px 인데, 한 줄에 필요한 폭은 176px 다(아이콘 36 +
'저녁 후 간식' 77 + '아직 없음' 47 + 간격 16). 데스크톱조차 3px 모자란다.
게다가 **이름은 사용자가 12자까지 짓는다** — 약 154px 이라 화면이 아무리
넓어도 한 줄을 보장할 수 없다. 두 줄은 어떤 이름·어떤 기기에서도 안 깨진다.

줄바꿈은 `word-break: keep-all` 로 **어절 단위**다. `overflow-wrap: anywhere`
만 두면 '저녁 후 간식'이 '저녁 후 간 / 식'으로 잘린다(375px 실측). anywhere 는
공백 없는 긴 이름의 넘침을 막는 뒷받침으로만 남긴다.

- `.entry-slot-picker__group` 을 `grid-template-columns: repeat(2, minmax(0,1fr))`,
  `gap: 0.5rem`. 아이템의 `margin-bottom` 은 gap 이 대신한다.
- 꺾쇠 제거 — 카드 격자에서는 중복이다.
- **하루 소감은 `grid-column: 1 / -1`** 로 전체 폭. 슬롯이 아니라는 읽힘을 유지한다.
- 라벨의 `white-space: nowrap` 을 풀고 2줄 클램프. 사용자가 12자 이름을 붙일 수
  있으므로 필수다.
- 패널 폭은 건드리지 않는다. `--shell-float-width`(최대 28rem)의 `!important` 가
  `max-w-[22rem]` 을 이미 덮고 있어(`css/style.css:16369`) 실폭 408px,
  열당 200px 이 나온다. 375px 기기에서도 열당 147px.
- 목록은 **피커가 열린 날짜**의 유효 개정판에서 `enabled` 인 것만.
- 헤더 우측(`기록 추가 · 8월 29일` 줄 끝)에 톱니 → 기록 항목 설정 시트.

### 4.2 기록 항목 설정 시트 (신규)

**화면에서는 '슬롯'이라고 부르지 않는다.** 사용자에게 슬롯은 뜻이 안 잡히는
말이라는 지적을 받았다 — 화면 이름은 **기록 항목**, 코드·데이터·이 문서의 내부
용어는 그대로 `slot`/슬롯이다. 둘을 섞어 개명하면 `slotKey`·`slotPlan` 까지
번지므로 경계는 화면 문구에서 끊는다.

```
기록 항목 설정      사용 중 7 / 12          (?)
⠿  ◉  아침 ✎                  사용 중   ⧉   ← 원본
⠿  ◉  점심 ✎                사용 안 함  ⧉   ← 원본(꺼짐)
⠿  ◉  저녁 ✎                  사용 중   ⧉   ← 원본
⠿  ◉  야식 ✎                    삭제   ⧉   ← 저녁을 복제한 확장

적용 시작일  [ 2026-08-27 ▾ ]

8월 27일부터 8월 28일까지의 기록에 적용됩니다.
8월 29일부터는 그날 저장한 구성이 따로 있어요.
                              [ 취소 ]  [ 저장 ]
```

⠿ 끌기 · ✎ 이름 편집 · ⧉ 복제. 이름 아래에 '아침 전 시간대' 같은 설명을
달았다가 뺐다 — 아이콘이 이미 시간대를 말하고, 두 줄이 되면 목록이 무거워진다.

- 이름: 인라인 편집 + **옆에 연필 아이콘**. 12자 이내, 저장 즉시 소급 반영(§3.1).
  (연필 없이 입력칸만 두니 고칠 수 있다는 걸 아무도 몰랐다 — 실사용 피드백.)
- 손잡이(⠿)와 연필은 **진하게** 그린다. 회색 #cbd5e1 로 두니 "너무 흐려서 안
  보인다"는 지적을 받았다 — 이 둘이 '만질 수 있다'는 유일한 신호다.
- 사용 토글 / 삭제 / **순서 끌기** → 오늘 날짜 개정판 추가.
- 토글 라벨은 **상태**를 적는다: `사용 중` / `사용 안 함`. `사용` 한 단어는
  "지금 켜져 있다"인지 "누르면 켜진다"인지 갈렸다 — 실사용 피드백. 두 라벨의
  글자 폭이 달라 행이 들썩이므로 최소 폭을 잡아 삭제 버튼과 같은 열에 세운다.
- 우상단 **물음표** → 도움말 팝업(§4.2.6).
- 꺼진 슬롯은 목록 제자리에 회색으로 남긴다. 아래 "사용 안 함" 구역으로 모으지
  않는다 — 시간 순서가 곧 목록의 뼈대이므로 자리를 옮기면 읽는 감각이 깨진다.

### 4.2.1 원본은 해제, 확장은 삭제

처음엔 삭제와 사용 해제를 **모든** 슬롯에 나란히 뒀다가, 둘의 차이가 이것뿐이라
걷어냈다:

| | 피커에서 | 설정 목록에서 | 과거 기록 |
|---|---|---|---|
| 사용 해제 | 사라짐 | 회색으로 남음 | 그대로 |
| 삭제 | 사라짐 | 사라짐 | **그대로** (§3 덕에) |

그런데 삭제를 통째로 없애니 **복제로 잘못 만든 슬롯을 치울 방법**이 사라졌다.
답은 슬롯의 성격을 나누는 것이었다:

| 슬롯 | 판정 | 그 자리의 버튼 |
|---|---|---|
| **원본** — base 마다 하나, key 가 가장 오래된 것 | `originalSlotSet` | 사용 중 / 사용 안 함 |
| **확장** — 복제로 늘린 것 | 나머지 전부 | 삭제 |

**한 자리에 하나만** 둔다. 나란히 두면 "뭐가 다르냐"는 질문이 다시 생긴다.

원본을 못 지우는 데는 이유가 둘 있다.

1. **복제가 유일한 추가 경로**다(§4.2.2). 원본이 사라지면 그 시간대로 슬롯을
   만들 길이 없어진다.
2. `slotKey` 없는 옛 기록의 **폴백 귀속처**가 원본이다(§3). 사라지면 라벨이 흔들린다.

확장은 지워도 안전하다 — 그 슬롯으로 남긴 기록의 이름은 §3 이 지킨다. 그래서
삭제에 확인 창을 띄우지 않는다. 되돌릴 수 없는 일이 아니다.

전부 해제하는 것은 저장 시 막는다 — 되돌릴 수는 있지만 피커가 빈 채로 열린다.

**key 구체화 시점이 이 판정을 좌우한다.** 설정 시트는 **열 때** null key 를
채운다(`materializeSlotKeys`). 저장 때 채우면 그 사이 만든 복제본의 key 가
원본보다 오래돼(복제 시각 < 저장 시각) 원본 판정이 뒤집힌다. 구체화만으로
개정판이 생기지 않도록 `withTodayRevision` 의 비교는 **저장된 쪽의 null key 를
어떤 key 와도 같다고** 본다(§5.6).

### 4.2.2 '슬롯 추가' 버튼은 없앴다

행마다 복제 버튼이 있고 원본 7개는 절대 사라지지 않으므로, **어떤 시간대든
복제로 도달할 수 있다.** "언제쯤인가요?" 7택은 같은 일을 하는 두 번째 길이라
지웠다 — 덕분에 사용자가 집계 축(base)을 고르는 화면 자체가 사라졌다.

슬롯을 더하는 길은 이제 복제 하나다. 행 오른쪽 복제 아이콘 → 이름만 새로 짓는다.
base 는 원본에서 상속된다. "저녁 슬롯을 복사해서 야식이라고 이름 붙인다"가
사용자가 실제로 하는 생각이고, 이 경로에서는 **집계 축 얘기를 한 번도 안 해도
된다.**

### 4.2.3 적용 시작일은 사용자가 고른다

처음엔 저장이 무조건 **오늘** 날짜 개정판을 만들었다. 어제 일을 오늘 정리하는
사람에게는 하루가 어긋난다. 시트 상단에 날짜 입력을 두고, 그 날짜 개정판으로
저장한다.

| 저장한 날짜 | 적용 범위 |
|---|---|
| 27일 | 27·28일 (다음 개정판 앞까지) |
| 29일 | 29일부터 계속 |

개정판이 **날짜 키 맵**이라(§2.1) 과거 날짜를 나중에 끼워 넣어도 뒤 개정판을
지우지 않는다. 이 동작을 얻는 데 데이터 모델은 한 줄도 안 바꿨다 — 날짜를 고를
수 있게 연 것뿐이다.

- **편집 대상은 그 날짜에 유효하던 구성**이다. 27일을 고르면 27일에 보이던
  목록이 뜬다.
- 안내문이 **끝나는 날까지** 말한다. 뒤에 개정판이 있으면 거기서 끊긴다.
- 날짜를 바꾸면 draft 를 다시 읽는다. 편집분이 있었으면 토스트로 알린다 —
  소리 없이 버리지 않는다.
- **미래는 못 고른다**(input max = 오늘). 읽기 쪽 시계 방어(§5.5)가 오늘+1일
  뒤를 무시하므로, 미래 개정판은 저장해도 한동안 안 보인다. 그런 유령을
  만들지 않는다.
- 기본값은 **피커가 보고 있던 날짜**다. 8월 27일 타임라인에서 톱니를 누르면
  27일이 채워져 있다.

### 4.2.4 뒤 개정판 통일 — 앞 날짜를 나중에 고칠 때

날짜를 고를 수 있게 열자 순서가 뒤엉킬 수 있게 됐다. **28일을 편집한 뒤 26일을
편집하면** 26일 편집이 26~27일짜리 **섬**이 된다:

| 날짜 | 28일 편집(야식) → 26일 편집(2차) 결과 |
|---|---|
| 26·27일 | + 2차 |
| **28일부터** | + 야식 — **2차가 사라진다** |

개정판이 완전한 스냅샷이라 그렇다. 26일 편집의 출발점은 "26일에 유효하던
구성"이고 거기엔 28일에 넣은 야식이 없다. 논리는 일관되지만 **의도와 어긋난다** —
앞 날짜를 고치는 이유는 대개 "사실 26일부터였어"이기 때문이다.

데이터 사고는 아니다(기록·이름 모두 안전). 의미론의 문제라 **묻는다.** 뒤에
개정판이 **있을 때만** 체크박스가 뜬다:

```
☐ 8월 28일 이후 구성도 이걸로 통일하기 — 그날 저장해 둔 구성은 덮어써집니다.
```

- **기본 꺼짐.** 켜면 되돌릴 수 없다. 28일을 일부러 다르게 둔 경우도 있다.
- 켜면 그 날짜보다 **뒤의 개정판을 같은 내용으로 덮어쓴다.** 지우지 않는다 —
  삭제는 `deleteField` 센티널이 필요해 아웃박스 payload 를 못 타고(§5.2)
  §5.6 과도 부딪힌다. 맵 갱신만으로 같은 결과를 얻는다.
- 앞 날짜 개정판은 건드리지 않는다.
- 통일하며 밀려난 슬롯의 이름은 `retired` 가 받는다(§3.2). 그 슬롯으로 남긴
  기록은 이름을 잃지 않는다.
- 델타 전파(바뀐 것만 뒤로 반영)는 **하지 않는다.** 추가·삭제·이름·토글·순서마다
  병합 규칙이 다르고, 순서 전파는 특히 모호하다. 통째로 덮어쓰거나 안 하거나 둘뿐이다.

### 4.2.5 내용이 같은 개정판은 "끝나는 날"로 안 센다

개정판은 **내용이 같아도 자국이 남는다.** 두 경로가 있다:

1. **고쳤다가 되돌리기.** 29일에서 고쳐 저장하면 개정판 29 가 생기고, 되돌려
   저장하면 "개정판 29 vs 되돌린 값"이 다르므로 개정판 29 를 다시 쓴다.
   결과: 28일과 **내용이 똑같은** 개정판 29 가 남는다. 비교 대상이 앞 개정판이
   아니라 **그 날짜의 개정판 자신**이라서 그렇다.
2. **뒤 개정판 통일**(§4.2.4). 설계상 같은 내용을 뒤 날짜에 써넣는다.

이 자국을 "다음 개정판"으로 세면 안내가 거짓말을 한다 — 29일 내용이 같아서
실제로는 계속 적용되는데도 *"8월 28일부터 8월 28일까지 적용됩니다"* 라고.
통일 체크박스도 이미 같은 걸 통일하겠다고 나선다.

그래서 안내와 체크박스는 **다음으로 내용이 달라지는** 개정판을 찾는다
(`nextDifferentRevisionAfter`). 같은 내용은 건너뛴다.

자국 자체는 지우지 않는다. 지우려면 `deleteField` 센티널이 필요한데 아웃박스
payload 를 못 타고(§5.2) §5.6 과도 부딪힌다. 해석에는 아무 영향이 없고
(내용이 같으니) 크기도 무시할 만하다 — **보이는 쪽만 정직하면 된다.**

한 가지 함정이 있었다. 29일 개정판만 있는 상태에서 27일을 편집하면
`effectiveSlots(27)` 이 기본값(key:null)을 준다. 그대로 새 key 를 매기면 같은
'아침'이 날짜마다 다른 슬롯이 돼, 이름 소급(§3.1)이 한쪽만 고친다.
`adoptExistingKeys` 가 **가장 이른 개정판의 같은 base 원본 key 를 물려줘서**
정체성을 하나로 유지한다.

### 4.2.6 도움말 — 버튼 설명이 아니라 "하고 싶은 일"로 묶는다

우상단 물음표를 누르면 설정 시트 **위에 겹치는 팝업**이 뜬다
(`slotPlanHelpModal`, `--z-slot-picker-help: 296`).

처음엔 시트 안에서 접었다 펴는 안내로 만들었다가 두 가지 이유로 걷어냈다.

1. 짧은 화면에서 펼친 안내가 목록을 밀어냈다. 설명을 읽는 동안 정작 그 설명이
   가리키는 대상이 안 보인다.
2. 항목마다 **버튼의 뜻**을 적고 있었다("복제 — 같은 시간대 항목을 하나 더").
   사용자는 버튼 이름이 아니라 *하고 싶은 일*을 들고 온다.

그래서 다섯 물음으로 다시 묶었다: 새로 만들고 싶다 / 안 쓰는 걸 숨기고 싶다 /
순서를 바꾸고 싶다 / 이름을 바꾸고 싶다 / 언제부터 적용되나. 각 답 안에서
"오른쪽 끝 복제 버튼", "왼쪽 손잡이"처럼 **위치로** 가리키고, 본문에 그 아이콘을
그대로 한 번 더 그려 준다. 말투도 안내문이 아니라 옆에서 알려 주는 말투다.

- 닫기는 X · '알겠어요' · 바깥 · ESC 넷 다. ESC 는 z 정렬 덕에 도움말만 닫고
  설정 시트는 남긴다(`escape-close-modals`).
- 딤은 옅게(20%) 깐다. 시트가 이미 딤을 깔고 있어 같은 농도를 또 얹으면 두 겹이
  된다.
- 몸통 스크롤 잠금은 시트가 이미 쥐고 있다 — 여기서 또 잡지 않는다.

### 4.3 두 번째 진입점

설정 모달에도 같은 시트를 여는 행을 둔다. 피커 톱니만으로는 발견되지 않는다.

## 5. 저장·동기화

### 5.1 slotPlan 은 부분 손상이 치명적이다

`saveSettings` 는 기존 문서 읽기에 실패하면 새 값으로 그냥 진행한다
(`js/db/ops.js:487` 주석). slotPlan 이 그렇게 리셋되면 **사용자가 붙인 모든
이름과 개정 이력이 한 번에 날아간다.**

- slotPlan 은 전용 저장 함수로 분리하고, **읽기에 실패하면 저장을 중단**한다.
  기본값으로 덮지 않는다 (`stripGateRegressions` 와 같은 성격의 보호).
- 기본값 병합에서 slotPlan 은 "없으면 만들지 않는다". 빈 맵과 기본값을 구분한다.

### 5.2 왜 배열이 아니라 맵인가 ★

설정도 아웃박스를 탄다(`js/db/ops.js:444`, `CLASS_CONTENT`, `mergePayload: true`).
그런데 병합 방식이 문제다:

- 아웃박스의 `deepMergePlain`(`js/utils/outbox-store.js:139`) — 맵은 재귀 병합,
  **배열은 통째로 교체**
- Firestore `setDoc(..., { merge: true })` — 똑같이 **배열은 통째로 교체**

`revisions` 가 배열이면, 두 기기가 각자 개정판을 추가했을 때 나중에 도착한
쪽이 앞의 것을 통째로 지운다. 날짜 키 맵이면 두 필드가 각각 병합돼 **둘 다
살아남는다.** 나중에 고치기 비싼 구조 결정이라 여기서 정한다.

### 5.3 충돌 규칙은 하나

> **같은 날짜는 마지막 편집이 이긴다.**

맵 키가 날짜라 저절로 그렇게 된다. 설명 가능한 규칙 하나면 충분하다.

### 5.4 도착 순서는 강제하지 않는다

기록(meals)과 설정(settings)은 별개 아웃박스 항목이라 도착 순서가 정해지지
않는다. 기록이 먼저 오면 그 `slotKey` 를 모르는 상태이므로 §3 의 폴백으로 기준
슬롯 이름이 뜨고, 설정이 도착하면 저절로 교정된다.

**폴백이 절대 실패하지 않으므로 순서 보장 장치가 필요 없다.** 순서를 맞추는
기계장치를 새로 넣지 않는다 — 그게 아웃박스가 13번 수정된 패턴이다.

### 5.5 시계 방어

`effectiveFrom` 은 기기 로컬 날짜다. 시계가 틀어진 기기가 2030년 개정판을
쓰면 그 뒤로 영원히 그것이 유효 개정판이 된다.

- 쓸 때: 사용자가 고르되(§4.2.3) **오늘을 넘지 못한다**(input max = 오늘,
  저장 직전에도 한 번 더 자른다).
- 읽을 때: `오늘 + 1일` 보다 미래인 개정판은 무시한다.

### 5.6 개정판은 지우지 않고, 안 쌓이게 막는다

개정판 **수**에는 상한을 두지 않는다. 삭제는 `deleteField` 센티널이 필요해
경합에 약하고(§5.3의 "마지막 편집이 이긴다"와 충돌한다), 무엇보다 사용자가
붙인 이름의 이력이다.

대신 성장 자체를 막는다:

- **직전 개정판과 슬롯 목록이 완전히 같으면 새 개정판을 쓰지 않는다.**
  토글을 껐다 켜서 원상복구하면 아무 일도 일어나지 않는다. 실제 성장의
  대부분이 여기서 죽는다.
- 맵 키가 날짜라 **하루 최대 한 개**다(§5.3).

그래도 감시는 필요하다. `userSettings` 는 `dailyComments`(하루 소감 본문·사진
메타)와 **같은 문서**를 쓰므로 1MB 한도가 남 얘기가 아니다. 개정판 12슬롯 한
개가 약 340B 이니:

| 개정판 수 | 크기 | 판단 |
|---|---|---|
| 24 | ~8KB | 평범한 사용자의 현실적 상한 (슬롯 12개 기준) |
| 200 | ~70KB | 진단 로그(`diag`) 한 줄 남긴다 |
| 3,000 | ~1MB | 매일 구성을 바꿔야 10년 — 실제로 오면 그때 데이터를 보고 결정 |

지금 정하는 건 **200에서 로그를 남긴다**까지다. 가지치기 정책을 미리 만들지
않는다 — 실측 없이 만든 삭제 코드가 이 서브시스템에서 제일 위험하다.

## 6. 서버·통계에 미치는 영향

없다. `slotId` 축이 그대로이므로 Functions·미러·관리자 코드는 한 줄도 안 바뀐다.

한 가지만 남는다: 사용자가 '점심'을 꺼도 통계에서는 "점심 기록 0건"으로 보이고,
**안 쓰는 것과 안 먹은 것이 구분되지 않는다.** 지금도 같은 한계이고 이번 범위
밖이다. 필요해지면 관리자 미러가 이미 읽는 `config/settings` 에 slotPlan 이
들어 있으므로 "활성 슬롯 수"를 분모로 쓰는 길이 열려 있다.

## 8. 남은 위험

1. **`enabled: false` 를 렌더 필터로 쓰는 실수.** 불변식 4를 깨는 유일한 경로다.
   1단계에서 `resolveSlotView` 에 "필터링용 아님" 주석을 박고, 타임라인 렌더가
   plan 을 아예 안 보게 만든다.
2. **`key` 재사용.** 해제한 슬롯을 되살려 이름만 바꿔 쓰는 경로가 있으므로
   (§4.2.1) 그 슬롯의 **과거 기록도 새 이름을 따라온다** — key 가 같으니 당연하고,
   §3.1 의 "이름 수정은 소급"과 같은 규칙이다. 다만 옛 key 를 **다른 슬롯에**
   재사용하면 과거 기록이 엉뚱한 데 딸려온다. 생성기는 시간 기반 + 랜덤으로 만들고,
   재사용 경로를 아예 두지 않는다.
3. **slotPlan 저장이 `saveSettings` 전체를 태운다.** 슬롯 이름 하나 고치는데
   닉네임 클레임 트랜잭션까지 도는 경로다. 0단계에서 실제 호출 비용을 재고,
   필요하면 slotPlan 전용 경량 경로를 검토한다.
4. **클라이언트 혼재 기간.** 웹은 main, APK 는 staging 을 받는다 — 이 기능이
   staging 에만 있는 동안 웹에서 저장한 기록은 `slotKey` 가 없다. 폴백 덕에
   깨지진 않지만, 같은 base 다중 슬롯 사용자가 웹에서 저장하면 전부 원본
   슬롯으로 귀속된다. 4단계는 **웹(main) 배포와 묶어서** 내보낸다.
5. **퀵입력의 하드코딩 잔재.** ~~2단계에서 교체~~ → 전수 확인 결과
   `resolveQuickEntrySlotId`·`getTimeBasedMainSlotId` 는 **사용처가 없는 죽은
   코드**였다(정의만 존재). 나머지 하드코딩 전수표:

   | 위치 | 하드코딩 | 판정 |
   |---|---|---|
   | `js/admin/*`, `functions/*` | MEAL/SNACK_SLOTS 등 | 그대로 — base 집계축 (§1) |
   | `js/analytics/*` (charts·insight·kpi·tags) | main/snack id 집합 | 그대로 — base 축 분석, 5단계에서 선택 |
   | `js/utils/diet-record-score.js` | MAIN_SLOT_IDS | 그대로 — 점수 계약은 base |
   | `js/utils/meal-delete-optimistic.js:9` | main 집합 | 그대로 — type 판정 = base |
   | `entry-modal-header.js` TINTED_SLOTS | morning/lunch/dinner | 그대로 — 헤더 테마 = base (야식도 저녁 테마가 맞다) |
   | `entry-quick-open.js` | QUICK_MAIN_SLOT_IDS | 죽은 코드 — 필요 시 삭제 |

한편 확인해서 **문제없음으로 닫은 것**: meals 쓰기 규칙(firestore.rules:64)에
`hasOnly` 필드 제한이 없고, `saveArtifactUserMeal` Callable 도 필드 화이트리스트
없이 통과시킨다 — `slotKey` 는 규칙·프록시 양쪽 다 수정 없이 저장된다. 기록
시트의 서식(본식/간식 폼)은 base 의 type 을 따르므로, 저녁을 복제한 '야식'은
자연히 본식 폼을 받는다 — 야식을 끼니로 여기는 사용자의 기대와 일치한다.
