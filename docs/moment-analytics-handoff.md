### 2.1 축별 누적 막대 — 이 화면의 본체

처음에는 「항목별 입력률」(채워졌나)만 있었습니다. 그 표로는 답할 수 없는 질문이 셋 있고,
셋 다 **한자리에서** 답해져야 하는 것들이었습니다:

| 질문 | 그림에서 읽는 자리 |
|---|---|
| 「태그 관리」의 구분이 실제로 유의미했나 | 범례의 **흐린 항목**(건수 0) = 기간 안에 아무도 안 고른 칩 |
| 「기타」가 여전히 많이 쓰이나 | 같은 막대의 다른 칸과 길이로 비교된다 |
| 시트 개편의 자동 항목이 입력을 늘렸나 | 축 머리의 **직접 / 자동** 두 숫자 |

처음엔 이걸 표로 만들었는데, **숫자만 늘어놓으니 「멀게」 읽힌다**는 지적을 받았습니다.
구성비와 건수가 둘 다 중요하므로 둘을 한 그림에 담습니다 — **길이가 몫이고, 칸 나눔이
구성**입니다. 표는 걷어냈습니다: 범례가 같은 값을 더 짧게 말하고, 정확한 전량이 필요하면
「엑셀 내보내기」의 `선택지 분포` 시트가 그대로 들고 있습니다.

**막대 전체 길이는 언제나 분석 대상 기록 100%입니다.** 축마다 제 입력분만큼만 칠해지고
나머지는 미입력 트랙으로 남습니다. 그래서 축들을 위아래로 세우면 「어떻게는 58% 채워지고
누구와는 47%」 같은 것이 **길이 차이로 바로** 보입니다. 각 축을 100%로 늘려 그리면 구성비는
보이지만 그 비교가 통째로 사라집니다.

**축은 다섯입니다** — 어떻게 · 어디서 · **무엇을 · 형태** · **무엇을 · 종류** · 누구와.
「무엇을」이 둘인 것은 같은 끼니의 **다른 절단면**이기 때문입니다: 형태(밥류·면류…)는
사용자가 고르거나 분류기가 채우고, 종류(한식·중식…)는 **묻지 않고** 분류기가 붙입니다.
「면을 얼마나 먹나」와 「중식을 얼마나 먹나」는 다른 질문이라 한 축에 담기지 않습니다
(docs/food-category-auto-classification.md §6.2).

종류 축은 **관리자 태그 목록에 없습니다** — 편집란이 없는 축이라 사전
(`CUISINE_CATEGORIES` + `혼합`)이 목록을 대신합니다. 값을 고르는 규칙은 앱의 읽기 계층
(`effectiveCuisineForAnalytics`)을 **그대로** 씁니다.

**범례가 모든 칸에 이름을 붙입니다.** 칸 안의 직접 라벨은 넓은 칸에만 들어가므로(좁은 칸에
넣으면 글자가 잘립니다) 좁은 칸은 색만 남는데, 색만으로는 무엇인지 알 수 없습니다 — 게다가
이 팔레트의 세 색은 흰 바탕 대비가 3:1 아래라 색을 단독 식별 수단으로 쓰면 안 됩니다.
범례 아래 잔줄이 한 색으로 묶인 것들의 정체를 마저 밝힙니다(「그 외」·「목록 밖」·「미입력 내역」).

지켜야 할 것 셋 — 어기면 그림이 그럴듯하게 그려지면서 거짓말을 합니다:

| 규칙 | 왜 |
|---|---|
| **색은 여덟 슬롯까지** (`AXIS_CHART_SLOTS`) | 아홉 번째 색을 만들어 쓰면 색맹 조건에서 기존 색과 구별되지 않습니다. 넘치는 만큼은 「그 외 n종」으로 접고, 접힌 이름은 잔줄에 답니다 |
| **칸도 범례도 많은 순**, 색은 그 순위를 따른다 | 처음엔 관리자 목록 순서로 색을 고정했습니다 — 기간을 바꿔도 색이 옮겨 다니지 않게. 그 대가로 목록 뒤쪽의 큰 값(「커피」)이 회색 「그 외」에 묻혔고, 크기 순으로 읽는 그림에서 그건 손해가 더 컸습니다. **색이 순위를 따를 때의 위험은 「기간을 바꾸면 색이 바뀐다」인데, 막대 바로 아래 범례가 모든 칸의 이름을 대고 있어 색을 맞춰 볼 일이 없습니다** — 그래서 순위 쪽을 골랐습니다. 식별은 언제나 범례의 이름으로 |
| **칸 사이 2px 틈은 칸 안쪽에서** (`border-right` + `border-box`) | 바깥 여백으로 내면 칸 수만큼 폭이 밀려(열 칸이면 20px, 좁은 화면에서 5% 넘게) 「길이가 곧 비율」이라는 전제가 깨집니다 |

**라벨은 그릴 때 넣지 않고 붙인 뒤에 잽니다**(`fitAxisBarLabels`). 비율로 어림하면 틀립니다 —
9%는 넓은 화면에서 100px 이지만 좁은 패널에서는 33px 이고, 「배달/포장 9%」는 66px 이 필요합니다.
같은 글꼴의 자를 세워 실제 글자 폭을 재고, 칸보다 좁을 때만 넣습니다. 잘린 글자는 없는 것만
못하기 때문입니다. 폭이 바뀌면 `ResizeObserver` 가 다시 재웁니다 — 넓어지면 라벨이 돌아옵니다.

### 읽을 때 조심할 곳 (막대)

- **비율의 분모는 축마다 전체 기록 수**입니다(입력된 건수가 아니라). 그래야 「미입력」까지
  같은 자로 잽니다. 축 머리의 자동 옆 괄호만 분모가 입력 건수입니다.
- **「목록 밖」이 무엇인가는 축마다 뜻이 다릅니다.**
  - 「무엇을」의 목록 밖은 대부분 **축을 갈아끼우기 전에 저장된 옛 어휘**입니다 —
    옛 *요리 종류* 축(한식·양식·일식·중식·분식·카페)과 「기타」. 이것들은 형태 축에 1:1
    대응이 없어 **일부러 매핑하지 않습니다**: 「한식」은 밥류일 수도 국물요리일 수도 있어서,
    어느 칩에 넣든 없는 정보를 지어내는 셈이 됩니다.
  - 반면 **표기만 달랐던 옛 형태 축 값**(`밥/한상`·`베이커리`…)은 읽을 때 맞춰
    제 칩으로 갑니다(`normalizeFoodForm`). 앱의 읽기 계층과 **같은 함수**입니다 — 여기만
    다르면 관리자가 보는 분포와 사용자가 보는 분포가 갈립니다.
  - 「어디서」는 끼니가 가게 이름을 자유 입력하므로 목록 밖이 큰 것이 **정상**입니다.
- **「종류」의 미입력을 실패로 읽지 마세요.** 과일·커피·채소·샐러드처럼 **축이 애초에
  해당되지 않는 형태**(`CUISINE_EXEMPT_FORMS`)가 여기 섞여 있습니다 — 「사과가 한식인가
  양식인가」는 질문이 성립하지 않아 빈 값으로 둡니다.
- **「종류」는 직접/자동을 가르지 않습니다.** 사용자가 고르는 칸이 애초에 없어서입니다.
  옛 기록 일부는 사용자가 「무엇을」에 직접 고른 종류 값이지만, 그걸 가르려면 옛 어휘
  집합을 관리자 쪽에 한 벌 더 두어야 해서(두 곳에 두면 갈립니다) 나누지 않았습니다.
- **「자동」은 나중에 커질 수 있습니다** — 「무엇을」은 서버 AI 배치가 나중에 돌아 채웁니다.
  최근 며칠은 「서버 분류 대기」가 부풀어 보입니다.
- **거부는 「무엇을」에만 기록됩니다.** 사용자가 형태 제안을 ✕ 하면 `categorySource='dismissed'`
  가 남지만, **어떻게·어디서·누구와의 추측을 지운 것은 저장되지 않습니다**(세션 상태
  `userCleared` 로만 삽니다). 그래서 그 세 축의 「미입력」에는 「거부했다」와 「애초에 제안이
  없었다」가 섞여 있고, 그림은 그 둘을 가르지 못합니다.
- **「직접 / 자동」을 가르는 근거는 저장 경로가 남긴 자국뿐입니다:**

  | 축 | 자동의 근거 | 남기는 곳 |
  |---|---|---|
  | 어떻게·누구와 | 맥락 예측이 자동 적용 | `autoContext: ['mealType'\|'withWhom']` |
  | 어디서 | 예측이 적용은 하되 입력란은 안 건드린 경우 | `autoContext: ['place']` |
  | 무엇을 | 로컬·서버 분류기가 채운 값 | `categoryAuto` + `categorySource` |

  값만 보면 자동과 직접은 **구별되지 않습니다** — 「집밥」은 사람이 골라도 「집밥」이고
  예측이 넣어도 「집밥」입니다. 그래서 이 두 숫자가 없으면 입력률이 올라도 그게 사람이 더
  채운 것인지 기계가 메운 것인지 영영 알 수 없습니다. 추이 표의 **자동적용** 열도 같은
  값(축 하나라도 자동으로 채워진 기록의 비율)을 기간 축으로 편 것입니다.

## 3. 「무엇을」 경로 분해 — 왜 필요했나

시트 개편 뒤 이 축의 입력률이 뚝 떨어져 보이는데, 한 줄로는 **"사용자가 덜 고르게 됐다"와
"분류 자체가 안 된다"를 가를 수 없었습니다.** 손댈 곳이 전혀 다른 두 사실입니다.

이 축만 값이 들어오는 길이 넷입니다(`js/modals/entry-save-record.js`,
`functions/classifyMoments.js`):

| 경로 | 저장 형태 |
|---|---|
| 사용자 확정 | `category` / `snackType`, `categorySource='user'` |
| 로컬 분류기 | `categoryAuto`, `source='local'` |
| 서버 Gemini 배치 | `categoryAuto`, `source='ai'` |
| 제안 ✕ 거부 | 값 없음, `source='dismissed'` — **backfill도 건너뜀(영구 미분류)** |
| 아무도 안 집음 | 값·source 없음 — 서버 배치 대기(단 `menuDetail` 이 있어야 집힘) |

**자동 분류는 `category`·`snackType` 을 절대 건드리지 않습니다.** 그래서 「무엇을」 행은
처음부터 사용자 확정만 세고 있었습니다 — 값은 맞았지만 혼자서는 오해를 부릅니다.
지금은 「무엇을」 막대(§2.1)가 그 자리를 대신합니다 — 축 머리의 **직접 / 자동**이
사용자가 고른 몫과 분류기가 채운 몫을 가르고, 범례 아래 「미입력 내역」 잔줄이
거부·대기·상세없음을 갈라 보여 줍니다. 추이의 `무엇을(최종)` 열도 그대로 있습니다.
(배타적 8경로 자체는 `FOOD_PATH_SPECS` 로 남아 엑셀 「무엇을 경로」 시트에 나갑니다.)

### 읽을 때 조심할 곳

- **서버 AI는 배치로 나중에 돕니다.** 최근 며칠은 아직 안 돌았을 수 있어 「대기」가 부풀고
  「AI가 채움」이 낮게 나옵니다. **추이 맨 오른쪽 구간은 그만큼 감해서 보세요.**
- **「기타」는 직접 선택과 갈라 두었습니다** — 서버가 미분류로 보고 다시 집는 값입니다
  (`classificationKind`: `userValue !== '기타'`).
- **만족도·포만감**은 설정에서 끌 수 있어 미입력에 「꺼 둔 사용자」가 섞입니다. 걸러내려면
  사용자별 `config/settings` 를 읽어야 해서(읽기가 사용자 수만큼 늘어남) 각주로만 밝혔습니다.
- 분모에서 **하루기록 미러·캡처 공유를 뺐습니다** — 이 항목들을 애초에 갖지 않아, 넣으면
  입력률이 통째로 내려앉아 아무것도 못 읽는 숫자가 됩니다.

## 4. 읽기 비용

**모먼트 관리와 나눠 쓸 수 없습니다** — 저쪽은 페이지당 20건, 이쪽은 기간 전체를 읽습니다.
그래서:

- 탭 진입만으로는 조회하지 않음. 「분석 실행」에서만 읽습니다.
- 같은 기간은 **10분 캐시**(결과 위에 「n분 전 결과 · 읽기 없음」과 「새로 읽기」가 뜹니다).
- 상한 **2만 건**. 넘으면 최근 날짜부터 그만큼만 집계하고 그 사실을 알립니다.
- 읽은 문서 수를 요약 카드에 찍어 비용이 보이게 했습니다.

2. **「무엇을」 하락의 해석을 끝낼 것.** 봐야 할 두 값:
   - **최종 분류 도달률**이 유지되는가 → 유지되면 입력 경로만 옮겨간 것
   - **「무엇을 상세」 입력률**이 그만큼 올랐는가 → 칩 대신 텍스트로 갔다면 받쳐줘야 함

   형태 칩을 접은 개편이라면 직접 선택 하락은 설계상 예상된 방향입니다
   ([project 메모: 음식 텍스트 재사용률 14% 근거](food-axis-rollout.md) 계열 참조).
3. **읽기량 실측 후 판단** — 부담되면 대시보드 증분 집계
   (`js/admin/dashboard-incremental.js`) 방식으로 서버에 미리 세어두는 쪽으로 옮깁니다.
   지금은 매 실행이 기간만큼 읽습니다.
4. **어떻게·어디서·누구와의 「거부」를 저장할지 결정.** 지금은 사용자가 추측을 지운 것이
   세션 상태(`userCleared`)로만 살다 사라져, 그 세 축의 미입력에서 「거부했다」와 「제안이
   없었다」가 안 갈립니다. 「무엇을」만 `categorySource='dismissed'` 로 남습니다.
   필드를 하나 더 남기는 저장 경로 변경이라 값이 있는지부터 판단할 일입니다.
5. **[entry-sheet-rollout-metrics.md](entry-sheet-rollout-metrics.md) §2 표와 이어붙이기** —
   교정률(`categorySource` 기반)·선택 입력 채움률은 이 화면이 이미 세고 있습니다.
   스크립트(`functions/scripts/entry-sheet-effect.js`)와 숫자가 맞는지 한 번 대조하면
   둘 중 하나를 접을 수 있습니다.
