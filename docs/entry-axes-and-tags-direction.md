# 기록 축 통일과 태그 시스템의 방향 — 제안

작성: 2026-08-13 (제안 단계, 미착수)
관련: [entry-sheet-redesign.md](entry-sheet-redesign.md),
[place-axis-unification.md](place-axis-unification.md),
[food-category-auto-classification.md](food-category-auto-classification.md)

## 0. 문제 두 개

**A. 끼니와 간식은 같은 행위인데 기록 구조가 다르다.**
끼니 1축(`mealType`)은 형태(집밥/외식/배달·포장)·장소(구내식당)·상황(회식/술자리)이
혼재된 축인데 라벨은 '어디서'다. 간식 1축(`snackPlaceMain`)은 진짜 장소(집/사무실/카페)다.
같은 "먹기"를 기록하는데 모드에 따라 다른 질문을 받는다 — 초기 세팅의 유산.

**B. 사용자 태그가 축 정의 권한까지 갖고 있다.**
태그는 빠른 입력 수단으로 만들었지만, 실제로는 "이 필드에 어떤 값이 유효한가"까지
사용자가 정한다. 그 대가: 분석 화이트리스트 2곳 수동 관리(태그 밖 값은 '미입력'으로
접힘), 자동 분류 제안이 사용자 태그 밖이면 필터, 사용자별 어휘 파편화로 전체 통계의
축이 흔들림.

## 1. 목표: 질문 4개짜리 공통 스키마

끼니·간식 모두 같은 구조. 끼니/간식 구분은 슬롯(시간대)이 이미 담당한다.

| 질문 | 축 | 값 예 | 입력 성격 |
|---|---|---|---|
| 무엇을 | foodCategory (새 축) | 밥/한상, 단백질식, 면, … | 사실-유도 (텍스트 추론 ✨) |
| 어디서 | place (장소) | 집, 사무실, 카페, 식당, 구내식당, 편의점 | 습관-추측 (예측 한 줄) |
| 어떻게 | method (현 `mealType`) | 집밥, 외식, 배달·포장 | 습관-추측 |
| 누구와 | withWhom | 혼자, 가족, 직장동료, … | 습관-추측 (예측 한 줄) |

- **'어디서'와 '어떻게'는 독립 정보다.** 장소가 '집'이어도 집밥/배달이 갈리고,
  '어디서'를 알면 '어떻게'가 상당 부분 유도되지만(구내식당→외식류) 전부는 아니다.
- **간식의 '어떻게'는 도입하지 않는다** (기본 접힘/생략). 간식에서 조달 형태의
  정보 가치는 낮다 — 필요해지면 데이터를 보고 결정.

## 2. 왜 이 방향인가 — 이미 절반 와 있다

재설계 이후의 코드가 사실상 이 방향을 선취했다:

- **예측 한 줄은 이미 장소를 예측한다.** `entry-context-predict`가 확정하는 필드는
  `place`·`withWhom` — 간식의 장소축과 같은 시맨틱이다. mealType이 아니다.
- **3층 어휘 구조의 부품이 전부 있다.** 저장은 원문(사용자 어휘) → 읽을 때 정규화
  (`place-normalize`) → 표준 축으로 집계. 개인 사전 훅(`personalKeywords`)과
  favorite 시스템도 이 구조의 부품이다.
- **새 foodCategory 축은 snackType과 이미 겹친다** (커피/음료·간식/디저트·과일).
  '무엇을' 축 통합이 자연스럽게 예고되어 있다.

남은 것은 이 사실을 **라벨과 시트 구조가 인정**하게 만드는 일이다.

## 3. 단계별 적용

| 단계 | 내용 | 데이터 영향 |
|---|---|---|
| 0 | **라벨 정정**: 끼니 펼침 칩의 mealType 그룹에 '어떻게' 라벨, 장소 입력에 '어디서' 라벨. 예측 한 줄·분석 화면 제목도 정합 | 없음 (표기만) |
| 1 | **분리 노출**: 끼니 '고칠래요' 펼침을 두 그룹으로 — 어떻게(mealType 칩) + 어디서(최근 장소 칩 + 자유입력). 저장 필드는 현행 유지 | 없음 (신규 입력의 place 입력률 상승 기대) |
| 2 | **혼재 값 읽기 정리**: '구내식당'은 장소 집계에도 계상, '회식/술자리'는 상황값으로 유지하되 형태 집계에서 '외식' 그룹에 접기 — 전부 읽기 계층 매핑, 원문 불변 | 없음 (집계만 변화) |
| 3 | **'무엇을' 축 통합**: categoryAuto 실데이터로 새 축이 검증되면(인수인계 §4-4의 판단 시점) snackType을 foodCategory로 흡수. 이 시점에 끼니·간식 기록 구조가 완전히 같아진다 | 새 기록부터 단일 축. 과거는 읽기 호환 |

각 단계가 독립적으로 가치가 있고, 어느 단계에서 멈춰도 이전 단계가 낭비되지 않는다.

## 4. 태그 시스템 — 역할을 셋으로 쪼개서 답한다

"태그를 유지해야 하나"는 하나의 질문이 아니다. 태그는 지금 세 역할을 겸직한다:

| 역할 | 현재 | 제안 |
|---|---|---|
| ① 축 정의 (유효값 결정) | 사용자 편집 가능 | **시스템으로 회수** — 표준 축은 코드·관리자만 정의. 통계·자동분류·예측의 공통 어휘 |
| ② 입력 가속 (칩 한 번 탭) | 사용자가 목록 관리 | **자동화** — 칩을 사용자 최근·최빈값에서 자동 생성. 예측 한 줄의 일반화이므로 수동 관리가 필요 없어진다 |
| ③ 개인화 (내 어휘) | 태그 편집으로 흡수 | **원문 + 정규화** — 자유 입력은 계속 허용, 저장은 원문, 집계는 정규화·개인 사전이 표준 축으로 모은다 |

근거는 [entry-sheet-redesign.md](entry-sheet-redesign.md) §4 실사용 검증에 이미 있다:

- 태그가 작동하는 곳(어디서 재사용률 79%, 누구와 90%, 고유값 3~5개)은 정확히
  **예측이 상위 호환인 곳**이다. 매번 같은 3개 중 하나를 고르는 일은 예측이 대신한다.
- 태그가 작동하지 않는 곳(무엇을 재사용률 14%)의 답은 칩이 아니라 텍스트 추론이다.
- 즉 어느 쪽이든 "사용자가 태그 목록을 편집한다"는 기능 자체의 존재 이유가 소멸했다.

**"통계를 위해 유지"는 방향이 반대다.** 데이터 집중은 사용자 태그가 아니라
표준 축 + 읽기 정규화가 담당한다. 사용자마다 다르게 편집된 태그는 축을 갈라놓아
오히려 집중을 방해한다 — 화이트리스트 2곳 수동 관리가 그 증상이다.

### 선행 계측 (제거 판단의 분모)

**태그 편집률** — 기본 태그에서 실제로 목록을 수정(추가/삭제/개명)한 사용자 비율.
userSettings.tags를 기본값과 대조하는 일회성 분석 스크립트면 된다
(`functions/scripts/analyze-meal-field-usage.js` 패턴 재사용).
편집률이 한 자릿수면 편집 UI 제거는 무부담이고, 높으면 그 사용자들의 커스텀 값을
개인 정규화 별칭으로 이전하는 마이그레이션을 먼저 설계한다.

## 5. 입력 흐름 설계 (2026-08-13 구현분)

### 어떻게는 어디서의 라우터다

'어떻게(조달)'를 먼저 고르면 '어디서(장소)'의 입력 방식이 결정된다:

| 어떻게 | 어디서 입력 | 구현 |
|---|---|---|
| 집밥 · 배달/포장 | '우리집' 기본값 채움 (수정 가능) | entry-and-core.js selectTag `HOW_PLACE_DEFAULTS` |
| 구내식당 | '구내식당' 기본값 채움 | 〃 |
| 외식 · 회식/술자리 | 카카오 검색이 주 경로 (기본값 없음) | 기존 검색 버튼 |

시트 DOM도 이 순서를 따른다 — 끼니 어디서 섹션: **어떻게 라벨(utensils) → mealType 칩 →
어디서 보조 라벨(map-pin) → 장소 입력**. 간식은 칩도 장소이므로 '어디서' 라벨 하나
(`applyEntryModeLabels`가 모드별 전환). index.html 구조 변경이라 SW 캐시 v8.

### 카카오 픽 = placeType 자동 분류

검색 결과 선택 시 `place`=상호명 원문, `placeType`=식당/카페/편의점/술집
(js/utils/place-type.js, 저장은 entry-save-record.js). 사용자가 고른 장소의 객관 속성이라
**사실-유도** — categoryAuto처럼 확인 없이 자동 저장한다. 어디서 통계의 집계 축이
상호명 파편 대신 이 카테고리가 되는 것이 목적. 검색 필터는 FD6 고정을 풀고
식음 관련(FD6·CE7·CS2 + 이름 판정)으로 확장 — **서버 함수(searchKakaoPlaces) 재배포 필요**.

### 맥락 한 줄 — 1페이지, 세그먼트 + 인라인 피커

**위치**: 1페이지(사진·무엇을와 같은 화면) '무엇을' 바로 아래. 2페이지 섹션은 저장 필드의
소유자로 그대로 두고, 이 줄은 **값을 미리 채우는 지름길**이다.

**구조**: 축 하나 = 세그먼트 하나 (어떻게 · 어디서 · 누구와, 순서 = 라우팅 순서).
세그먼트를 탭하면 그 축의 칩만 **줄 바로 아래에서 인라인으로** 열린다 — 오버레이·드롭다운을
쓰지 않는 이유는 시트 높이 재측정이 키보드 중에 막히는 알려진 지뢰를 피하기 위해서다
(entry-sheet-tabs.js). 드롭다운의 의미론(접힘·축별 교정)에 칩의 렌더링(1탭·어휘 노출)을 얹은 형태.

**상태 표기**: 점선 = 추측(자동), 프라이머리 채움 = 사용자가 직접 고름, 흐림 = 토글 OFF로
저장에 쓰이지 않는 추측. 값이 없으면 `+ 어디서` 트리거.
콜드 스타트에서도 줄은 남아 1페이지에서 바로 입력을 열 수 있다 — 조르지 않되 입구는 준다.

**적용 모델 — 자동 적용 + 되돌릴 수 있는 토글** (2026-08-13 변경. 재설계 원칙 2의
"추측 무확인 저장 금지"를 맥락 필드에 한해 대체한다):

- 확인 질문('맞아요/아니에요')을 묻지 않는다 — 입력에 답을 요구하는 형태가 어색하고,
  한 번 거부하면 되돌릴 수 없었다. 대신 헤더 우측에 **상태 스위치**를 둔다:
  `사용 안함`(**기본 OFF**) ↔ `이대로 사용`(ON).
- 이 축들은 "쓴다/안 쓴다"가 먼저다. 추천값은 **쓰기로 했을 때 채워질 값**으로 세그먼트에
  미리 들어가 있고, OFF에서는 흐리게 표시될 뿐 저장되지 않는다. 기본 OFF라
  원칙 2("추측은 확인 없이 데이터가 되지 않는다")도 그대로 지켜진다.
- 어느 쪽이든 스위치는 사라지지 않고 언제든 되돌아온다.
- 토글이 지배하는 것은 **추측뿐**이다. 세그먼트 피커에서 직접 고른 값은 토글 상태와
  무관하게 항상 저장된다. 같은 값을 다시 탭하면 해제된다.
- 데이터 정직성은 categoryAuto 패턴으로 지킨다: 자동 적용된 축 이름이
  `record.autoContext` 에 남고, **예측 표본에서 자동 적용값을 제외**해 추측이 추측을
  강화하는 루프를 차단한다. `context_predict_auto_saved` 로 교정률을 측정한다.

예측 문턱은 종전과 동일(표본 3+·점유 60%), '기타'·'건너뜀'은 습관이 아니므로 표본에서 제외.

**어디서 피커**는 내 최근·최빈 장소 칩(정규화 그룹의 대표 원문 표기)에 더해
`장소 검색 · 직접 입력`으로 카카오 검색을 연다 — 카테고리로 안 잡히는 장소의 탈출구.

**상위 축이 하위 선택지를 좁힌다.** 집밥을 골랐는데 식당 이름이 뜨거나 외식을 골랐는데
'우리집'이 먼저 뜨는 걸 막는다. 좁히는 기준은 하드코딩된 분류표가 아니라 **그 조달 방식으로
기록한 사용자 자신의 이력**이고, 이력이 없을 때만 시드가 나선다 (어휘 보존 원칙).

| 어떻게 | 어디서 (이력 우선 → 시드) | 누구와 |
|---|---|---|
| 집밥 | 그 방식의 내 장소 → 우리집·본가·처가·친구집 | 가족·혼자 우선 |
| 배달/포장 | 〃 → 우리집·본가·사무실 | 혼자·가족 우선 |
| 구내식당 | 〃 → 구내식당 | 직장동료·혼자 우선 |
| 외식 · 회식/술자리 | 내가 갔던 상호명 (시드 없음) + 카카오 검색 | 외식: 가족·친구·연인 / 회식: 직장동료·친구 |

**어디서는 거르고, 누구와는 정렬만 한다** — '혼자 외식'·'가족 회식'처럼 드물지만 정당한
조합을 막으면 안 되기 때문이다. 누구와는 관련 값을 앞으로 보낼 뿐 목록에서 빼지 않는다.

### '무엇을' 축 재설계 — 형태 × 요리 종류

옛 축(밥/한상·단백질식·면·빵/샌드위치·샐러드·과일·커피/음료·간식/디저트)은 **기준 셋이
섞여** 있었다: 형태(밥/한상·면·빵) · 식단 컨셉(단백질식·샐러드) · 식품군(과일·음료).
그래서 "탕수육은 밥/한상인가 단백질식인가" 같은 답 없는 질문이 생겼고, 실측에서 흔한 음식
59개 중 **22%가 미분류**(치킨·돈까스·초밥·회…), 같은 돼지고기인데 삼겹살=밥/한상 ·
보쌈=단백질식으로 갈렸다.

이제 사전은 `음식 → { form, cuisine }` 한 항목이고 매칭은 **최장 일치**다
('탕수육'이 '수육'보다 길어 먼저 잡힌다 — 부분문자열 오탐이 구조적으로 사라졌다).

| 축 | 입력 | 값 |
|---|---|---|
| **형태** (주 축) | 사용자 선택 + ✨제안 | 밥류 · 국물요리 · 면류 · 빵류 · 고기·생선 · 채소·샐러드 · 과일 · 음료 · 간식·디저트 |
| **요리 종류** | **자동 저장, 묻지 않음** (`cuisineAuto`) | 한식 · 중식 · 일식 · 양식 · 분식 · 패스트푸드 · 기타 (+집계값 `혼합`) |

두 가지 설계 판단을 기록해 둔다:

- **국물요리를 분리한 이유**: 부대찌개·곰탕·미역국이 전부 '밥류'에 있어 어색했다. 국물
  요리를 통째로 빼서 밥류를 밥 요리로 순수하게 남긴다. 나트륨 관점의 통계 축이기도 하다.
  단 **국밥·죽은 밥류에 남긴다** — 이름과 먹는 방식이 밥 요리다.
- **반찬을 분리하지 않는 이유**: 김치·나물·계란말이를 별도 축으로 빼면
  "잡곡밥 + 김치 + 나물 + 계란말이"가 반찬 3표로 몰려 밥상이 '반찬'으로 분류된다.
  반찬이 밥류에 있어야 한식 밥상이 밥류로 투표된다 — 의도적인 배치다.

**어떻게 추측의 두 원천** (합성 우선순위: 사실-유도 추론 > 습관 예측):

| 원천 | 신호 | 추측 | 개인/공통 |
|---|---|---|---|
| 사실-유도 (이 기록의 입력) | 카카오 픽 placeType=식당/술집/카페 | 외식 | 공통 규칙 |
| 〃 | **무엇을 원문의 조달 키워드** (배민·배달·구내식당·회식…) | 해당 값 | 공통 사전 |
| 〃 | 장소 표기 '구내식당' | 구내식당 | 공통 규칙 |
| 〃 | 장소=집 그룹 + 무엇을 형태=밥류·국물요리 | 집밥 | 공통 규칙 |
| 〃 | **요리 종류** (장소가 비었을 때) | 개인 통계 → 시드(중식·일식=외식) | **개인** + 공통 시드 |
| 습관 예측 (이력 통계) | (슬롯×평일/주말) 최빈값, 표본 3+·점유 60%+ | 최빈값 | **개인** |

**어떻게 → 어디서 연쇄**: 어떻게가 추천됐는데 어디서가 비어 있으면 거기서 이어 받는다
(집밥·배달/포장 → 우리집, 구내식당 → 구내식당). 값은 **개인 통계 우선** — "내가 집밥일 때
어디서였나"가 시드보다 정확하다. 외식·회식은 상호명이라 추론하지 않는다.
두 가지 안전장치가 있다: ① **빈칸일 때만** 개입한다 — 슬롯 기반 습관 예측이 이미 장소를
내놨으면 덮지 않는다(추측 위에 추측을 얹어 오차가 곱해지는 걸 막는다). ② 어떻게가 바뀌면
**그 어떻게 때문에 넣었던 어디서는 함께 무효화**된다("배민 치킨"→우리집 에서 "탕수육"으로
고치면 우리집이 남으면 안 된다).

**간식도 같은 예측을 탄다** (2026-08-13). 축은 어디서·누구와 둘뿐이라 어떻게 관련 계산만
건너뛴다. 표본은 **같은 종류(간식 슬롯)로 좁혀** 뽑는다 — 슬롯 표본이 모자랄 때 전체 이력으로
폴백하면 끼니 장소('구내식당')가 간식 추측으로 새기 때문이다.

**요리 종류 → 어떻게**: "탕수육"을 적었는데 그 슬롯 최빈값이 집밥이라는 이유로 집밥이
뜨는 걸 막는다. 개인 통계가 먼저다 — *내가* 중식을 먹을 때 배달이었는지 외식이었는지가
전역 시드보다 정확하다(표본 3+·점유 60%+ 같은 문턱). 이력이 모자랄 때만 시드가 나서고,
시드는 **집에서 해 먹는 일이 드문 종류만**(중식·일식·패스트푸드) 담는다 — 한식·양식·분식은
집에서도 흔히 만들므로 습관 예측에 맡긴다.

**'패스트푸드'를 요리 종류로 둔 이유**: 엄밀히는 요리 종류가 아니라 형식이지만, 배달앱
분류와 실사용 어휘가 이미 별도 범주로 쓴다(햄버거를 '양식'이라 부르지 않는다). 같은 이유로
'분식'이 이미 들어와 있다. 추론 쪽에서도 **양식 안에 파스타(집에서 만듦)와 햄버거(사 먹음)가
섞여 있어 시드를 달 수 없던 문제**를 갈라준다. 샌드위치·토스트는 집에서도 흔히 만들므로
양식에 남긴다. 다만 이걸로 다 풀리지는 않는다 — 족발·보쌈(한식)·스테이크(양식)처럼
"사 먹지만 요리 종류는 그대로"인 음식은 여전히 개인 통계에 의존한다. 과거 기록에는 `cuisineAuto` 가 없으므로 상세 텍스트에서
파생해 쓴다(마이그레이션 불필요, 시트 세션 동안 캐시).

**카테고리가 아니라 원문을 본다.** 음식 카테고리(밥/한상·면…)는 조달 방식을 거의 알려주지
않는다 — 면은 집에서도 끓이고 배달로도 오고 식당에서도 먹는다. 반면 사용자가 적은 원문에는
조달어가 직접 들어 있다("배민 치킨"). 그래서 조달 힌트 사전
([procurement-hint.js](../js/utils/procurement-hint.js))은 **원문 문자열**을 스캔하며,
장소가 비어 있어도 발화하는 유일한 규칙이다. 정밀도 우선이라 '포장'(포장김치)·'맥주'(집술)
같은 애매한 말은 넣지 않는다.

**개인화 비용**: 습관 예측은 이미 타임라인용으로 메모리에 올라와 있는 `window.mealHistory`
를 로컬에서 훑을 뿐이라 **추가 저장·네트워크가 0**이다. 비용은 시트 열 때 CPU뿐이고
실측으로 기록 500건 4ms · 3,000건 17ms · 10,000건 72ms (피커 열기는 0.1~0.5ms).
10,000건은 하루 3끼 9년치라 당분간 문제되지 않는다. 더 커지면 축별로 3번 도는 정렬을
1번으로 합치거나 최근 N개월로 자르면 된다.

이 기록에 실제로 입력된 사실이 과거 통계보다 우선한다. 무엇을 텍스트·어디서 입력이
바뀔 때마다 실시간 재합성되고, 지우면 회수된다. 어느 쪽이든 점선 추측일 뿐 —
확인 없이 저장되지 않는 원칙은 동일하다. GPS(사진 위치→집 앵커) 원천은
photo_gps_present 존재율 계측 결과와 앵커 프라이버시 설계가 나온 뒤 3번째 원천으로 검토.

**쓰기 경로**: 확정 시 2페이지 칩이 렌더돼 있으면 그 칩을 클릭해 기존 동작(서브태그·라우팅)을
그대로 태우고, 빠른입력이 꺼져 칩이 없으면 confirmed 값만 남겨 저장 시 병합한다.
이때 `resolveEntrySaveFields`의 조용한 '기타' 폴백보다 **사용자가 탭한 값이 우선**이다
(칩이 없으면 mealType·withWhom이 '기타'로 채워져 확정값을 덮는 문제).

### 시트는 2단계다

어디서·누구와 전용 페이지('more')를 **제거**했다. 맥락 한 줄이 1페이지에서 세 축을
모두 처리하므로 그 페이지에 남는 것이 없었다. 다만 전체 축 섹션 자체는 지우지 않고
1페이지의 **'자세히' 접힘**으로 내렸다 — 맥락 줄이 다루지 않는 입력(건너뜀 칩,
장소·사람 서브태그, 누구와 상세)이 거기 있어서, 통째로 지우면 입력 경로가 사라진다.

| 단계 | 내용 |
|---|---|
| 1 뭘 먹었어요? | 사진 · 무엇을 + ✨제안 · 맥락 한 줄(+ 인라인 피커) · 자세히(접힘: 전체 축 섹션) |
| 2 어땠어요? | 만족도 · 포만감 · 시간 · 공유 · 메모 |

메모는 이 재설계 이전에 이미 3층(어땠어요)으로 옮겨져 있다.

**피커는 스크롤 없이 한 번에 보인다**: 칩은 가로 스크롤이 아니라 줄바꿈으로 전부 펼치고,
열릴 때 시트 높이 잠금을 재측정해 시트를 키운 뒤 잘린 만큼만 자동으로 끌어온다.
사용자가 선택지를 보려고 직접 스크롤할 일이 없다.

| 뎁스 | 항목 |
|---|---|
| 0 (바로 보임) | 사진 · 무엇을 텍스트 · ✨카테고리 제안 · 맥락 한 줄(어떻게·어디서·누구와) |
| 1 (탭 1회) | 세그먼트 인라인 피커(축별 칩) · 카테고리 전체 칩 · 장소 검색 · 자세히 펼침 |
| 2 (2단계·조건부·승격) | 만족도·포만감·시간·메모 · 배달 업체(어떻게=배달/포장) |

미구현 잔여: 간식 맥락 줄(간식 place 입력률 데이터를 본 뒤 — entry-sheet-redesign.md §3
"간식 어디서 예측" 판단 유지), placeType의 어디서 통계 반영, snackType→category 축 통합.

## 6. 하지 않는 것

- **과거 데이터 재작성** — 원문 불변 원칙. 모든 정리는 읽기 계층에서.
- **간식에 '어떻게' 강제 도입** — 정보 가치 미검증.
- **태그 편집 UI 즉시 제거** — 편집률 계측 후 결정. 순서: 신규 사용자 기본 태그
  고정 → 편집 진입점 축소 → 데이터 확인 → 제거.
- **mealType 저장 필드 개명** — '어떻게'는 라벨이지 스키마가 아니다. 필드명을
  갈아타면 차트 연속성만 깨진다.
