# 기록 시트 재설계 — "입력하는 시트"에서 "확인하는 시트"로

작성: 2026-08-12
관련: [food-category-auto-classification.md](food-category-auto-classification.md) (자동 분류 설계 — 본 문서의 부품)

## 0. 설계 의도 vs 실사용 검증

원래 의도: **"꼭 기록하고 싶은 정보까지만 기록하고 탈출"** — 3단계 점진 노출.
1단계(사진·무엇을·메모) > 2단계(어디서·누구와) > 3단계(기타).

7/1~8/12 일반 기록 4,042건으로 검증한 결과:

### 맞은 것

- **탈출 구조 자체는 옳았다.** 1단계 코어(사진 63% / 텍스트 75%)와
  2단계(어디서 36% / 누구와 25%), 3단계(만족도 23%)의 낙차가 명확하다.
  단계 구분의 방향은 실사용과 일치한다.
- **사진+텍스트가 기록의 실체다.** 사진만 20%, 텍스트만 32%, 둘 다 ~43% — 95%의
  기록이 이 둘 중 하나로 성립한다.

### 어긋난 것

1. **카테고리 칩은 1단계에 있지만 1단계 시민이 아니다.** 실제 선택률 23%.
   63%는 텍스트만 쓰고 지나가서 '기타' 자동 폴백을 받는다. 1단계에 "고민이 필요한
   선택지"가 끼어 있는 것 — 의도(고민 없이 탈출)와 정면 충돌하는 유일한 요소다.
2. **메모는 코어가 아니다.** 18%. 의도상 1단계였지만 실사용은 3단계급.
3. **2단계는 기록별 선택이 아니라 사용자별 이분법이다.** 10건 이상 기록자 기준
   어디서를 거의 안 쓰는 사람 28명 vs 항상 쓰는 사람 6명 — 중간이 적다.
   즉 "이번 끼니는 어디서를 적을까"가 아니라 **"나는 어디서를 적는 사람인가"**로
   갈린다. 그런데 시트는 모두에게 같은 화면을 보여준다.
   쓰는 사람들 안에서는 최빈값 편중이 크다(어디서·누구와 최빈값 점유율 중앙값 62~63%,
   누구와는 35%의 사용자가 한 값을 80% 이상 반복). "집 · 혼자"를 매번 다시 고르고 있다.
4. **자유 텍스트가 만능 탈출구로 해킹되고 있다.** 체중("51.3kg/⭕️/5300보"),
   인증 마크(⭕️), 식사구분의 '하루소감' 전용(21명·128건) — 구조화 필드가 못 받아주는
   기록이 전부 텍스트로 흘러들어온다. 이건 결함이 아니라 신호다:
   **텍스트는 계속 무제한이어야 하고, 구조는 텍스트에서 추출해야 한다.**

## 1. 설계 원칙 3개

> ### 1. 사용자는 입력하지 않는다. 확인한다.
> 모든 구조화 필드는 시스템이 먼저 값을 제시하고, 사용자는 맞으면 지나가고 틀리면 고친다.

> ### 2. 사실-유도와 습관-추측을 구분한다.
> - **사실-유도** (텍스트에서 파생: 카테고리) — 무시하고 저장해도 자동값 기록 OK.
>   사용자가 쓴 텍스트가 근거이므로 데이터를 지어내는 게 아니다.
> - **습관-추측** (과거 패턴에서 예측: 어디서·누구와) — **탭 한 번의 명시적 확인 없이는
>   절대 저장하지 않는다.** 오늘은 식당에서 먹었는데 "집"이 조용히 저장되면 데이터 오염이다.

> ### 3. 시트가 사용자에게 적응한다. 사용자가 시트에 적응하지 않는다.
> 필드 사용은 사용자별 이분법이므로(§0-3), 각자의 "기록 레시피"를 학습해
> 그 사람이 쓰는 필드만 펼치고 나머지는 접는다.

기존 3단계 점진 노출은 폐기가 아니라 **개인화로 승격**된다. 단계의 경계가 전역 고정이
아니라 사용자별로 이동하는 것.

## 2. 새 시트 구조

### 1층 — 코어 (모두에게 항상 펼침)

```
┌─────────────────────────────┐
│ [사진 추가]  (큰 터치 타깃)     │
│ ┌─────────────────────────┐ │
│ │ 무엇을 드셨나요? (텍스트)   │ │
│ └─────────────────────────┘ │
│ ✨ 단백질식 ✕   ← 자동 분류 제안 │
└─────────────────────────────┘
```

- 사진 + 텍스트 하나. 선택지 없음, 고민 없음. 여기서 저장하고 나가면 완결.
- 카테고리 칩 그리드는 1층에서 **제거**. 대신 텍스트 입력 중 자동 분류 제안 칩이
  점선+✨로 나타난다 (동작·저장 규칙은 자동 분류 설계 문서 §4).
  제안을 탭하거나 "직접 선택"을 열면 전체 칩이 나온다.
- '기타' 조용한 폴백 제거 (자동 분류 설계 §2).

### 2층 — 맥락 (한 줄 요약, 습관-추측 제안)

```
│ 🏠 집 · 👤 혼자  [맞아요✓]  [고칠래요▾] │
```

- 어디서·누구와를 칩 그리드 2개 대신 **예측된 한 줄**로 압축.
  예측 근거: 그 사용자의 (식사구분 × 평일/주말)별 최빈값. 로컬 계산, 네트워크 없음.
- `맞아요` 탭 = 둘 다 확정 저장 (`source='user'`). **탭 없이 저장하면 두 필드 모두
  빈 값** — 원칙 2. 추측은 확인 없이 데이터가 되지 않는다.
- `고칠래요` = 기존 칩 그리드 펼침 (기존 UI 재사용).
- 예측 불가(이력 부족)이거나 그 필드를 안 쓰는 사용자면 이 줄은
  `+ 어디서·누구와` 접힌 링크로만 존재.

### 3층 — 심화 (접힘, 개인화 승격)

- 만족도·포만감·메모·시간 조정·공유. 기본 접힘.
- **승격 규칙**: 최근 10건 중 5건 이상 쓴 필드는 그 사용자에게 자동 펼침.
  (만족도를 매번 쓰는 5명에게는 만족도가 처음부터 보이고,
  안 쓰는 40명에게는 영원히 접혀 있다.)
- 반대로 승격됐던 필드를 10건 연속 안 쓰면 다시 접는다.
- 구현: 사용자 설정에 필드별 최근 사용 이력(비트 배열 or 카운터) —
  기존 `entry-quick-input.js`의 필드별 on/off 개념을 자동화하는 것.
  수동 on/off는 유지하되 "자동" 상태를 기본값으로 추가.

## 3. 데이터 흐름 요약

| 필드 | 1차 소스 | 제안 방식 | 미확인 시 저장값 |
|---|---|---|---|
| 텍스트(무엇을_상세) | 사용자 타이핑 | — | 입력값 그대로 |
| 카테고리 | 텍스트에서 추론 (사실-유도) | ✨점선 칩, 자동 적용 | `categoryAuto` (source='local'/'ai') |
| 어디서·누구와 | 과거 패턴 (습관-추측) | 한 줄 요약 + 맞아요 | **빈 값** (추측 저장 금지) |
| 만족도·포만감·메모 | 사용자 입력 | 승격/접힘만 개인화 | 빈 값 |

## 4. 텍스트 해킹의 수용 (후속 과제, 본 설계 범위 밖)

체중·인증·소감이 텍스트로 들어오는 것은 막지 않는다. 대신 분류기와 같은 방식으로
**텍스트에서 구조를 추출**하는 확장을 열어둔다:

- `51.3kg` 패턴 감지 → "하루기록지표에 체중으로 기록할까요?" 제안 (사실-유도이므로 제안 가능)
- 사진만 있고 텍스트 없는 20%의 기록 → 2층 backfill 시 사진 기반 분류(Gemini vision)
  검토 — 비용 확인 후 별도 결정

## 5. 적용 순서

| 단계 | 내용 | 비고 |
|---|---|---|
| 1 | 자동 분류 1단계 (분류기 + ✨제안 + 필드) | 선행 문서 그대로 |
| 2 | 1층 개편: 카테고리 칩 그리드를 제안+펼침으로 교체, 메모 3층 이동 | 시트 레이아웃 변경 |
| 3 | 2층 개편: 어디서·누구와 예측 한 줄 + 맞아요 | 예측 로직은 로컬 최빈값 |
| 4 | 3층 승격 규칙 (필드 자동 펼침/접힘) | entry-quick-input 확장 |
| 5 | 서버 backfill + 과거 데이터 (선행 문서 2단계) | 병렬 진행 가능 |

측정은 자동 분류 문서 §7의 3지표에 추가로:

- **저장까지 걸린 시간** (시트 열림→저장): 중앙값 감소가 이 재설계의 최종 성공 기준
- **맞아요 탭률**: 2층 예측의 품질 지표. 낮으면 예측 로직 수정, 높으면 유지
- **어디서·누구와 입력률**: 현 36%/25% → 예측 확인이 쉬워지면 상승해야 정상.
  하락하면 "맞아요" 동선이 기존 칩보다 불편하다는 뜻

## 6. 하지 않는 것

- 습관-추측 값의 무확인 자동 저장 (원칙 2 — 어떤 편의보다 데이터 정직성이 우선)
- 필수 입력 추가 — 탈출 구조는 이 설계의 보호 대상이지 개선 대상이 아니다
- 모든 필드 한 화면 노출 — 원래 의도가 옳았다. 우리는 경계를 개인화할 뿐이다
